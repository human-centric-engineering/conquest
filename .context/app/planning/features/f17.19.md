# F17.19 — Ingestion-time Adaptive Scope candidacy check

> Every part of Adaptive Scope is manual and undiscoverable: an admin has to already know the
> feature exists, open the Adaptive scope tab, and click "Run" — for a document that is, in many
> cases, already telling them exactly how to route it. This feature closes that gap in phases.
> **Phases 1–2 are done; Phases 3–4 are open.**

## The four phases

1. **Candidacy detection at ingestion — DONE.** A cheap, fail-soft capability
   (`app_detect_adaptive_scope_candidacy`) runs during every fresh ingestion (all four entry
   points: new ingest + re-ingest, plain + streaming) and decides whether the uploaded document's
   own words describe conditional routing. Resolved at the `routing` tier, not the analyst's
   `reasoning` tier — this runs unconditionally on every upload, so it has to stay cheap.
2. **Gap-aware Routing Analyst — DONE.** `routingAnalysisSchema` carries a `gaps[]` field so the
   analyst reports routing language it recognized but could not formalize into a topic or hard
   rule, instead of silently dropping it.
3. **Auto-trigger wiring — open.** When Phase 1 flags a document, auto-invoke the existing
   Routing Analyst SSE endpoint from the Topics tab (no new job infrastructure — the same call the
   manual "Run" button already makes) so a reviewed draft is waiting without the admin needing to
   discover the feature. Never auto-enables `adaptiveScope.enabled` — that stays a deliberate,
   separate admin action, preserving the "off by default, inert by construction" invariant.
4. **Questionnaire Pack "Adaptive scope" section — open.** A 7th, off-by-default Pack section
   explaining the topics/rules/routing logic in plain language for a stakeholder audience.

### Eligibility — skipped, not just found-nothing

The check does not run at all (no LLM call, no `AppAiRun`) when the version already has
`adaptiveScope.enabled`, already carries a topic an admin or the analyst authored (`source !==
'seeded'`), or already has a pending Routing Analyst draft. This is a detector for a **fresh,
unrouted** document, not a recheck of one an admin has already looked at — re-ingesting onto an
already-routed draft is a deliberate no-op here.

### It never throws

Every failure path — an unmocked/unreachable eligibility query, the agent not seeded, no provider,
a dispatch failure, an unparseable reply, even a failure to write the version cache after a real
verdict — resolves to `null` (or, for the cache write, a swallowed error alongside the still-valid
verdict). An early version of this shipped with an unguarded eligibility check and agent lookup;
either throwing turned a 500 into every ingest route's happy path. Both are covered by dedicated
regression tests (`tests/unit/app/api/v1/app/questionnaires/_lib/scope-candidacy.test.ts`).

### Cost control

The document text handed to the check is capped at 20,000 characters
(`MAX_CANDIDACY_DOCUMENT_CHARS`) — far less than the Routing Analyst's uncapped read. The sections
that announce conditionality (an intro, a "how to use this" page, a routing tab) are concentrated,
not spread evenly across a long instrument, so this is enough to decide candidacy without paying
for an exhaustive read on every single upload.

### Why `sourceQuote` is required on a gap, not optional like it is on a topic or rule

A topic or rule can be legitimately _inferred_ — the analyst says so via an absent `sourceQuote` and
a false `fromDocument`. A gap has no equivalent inferred form: it exists specifically to admit "the
document said something here that I could not turn into a topic or a rule." A gap with no quote would
be the analyst inventing a problem rather than reporting one, so the schema refuses it outright.

### Not persisted to the live topic set

`gaps` never reaches `AppQuestionnaireTopic` — accepting a draft posts only `topics`, `rules` and
`maxConditionalTopics` (`routing-analyst-card.tsx`'s `accept()`). A gap is advisory: the admin reads
it, and either authors a topic/criterion/rule by hand or accepts that the instrument is silent enough
there to leave it alone. This mirrors how `AppQuestionnaireTopicDraft.topics` already stores the whole
`ProposedTopicSet` as one JSON blob — no migration was needed to add the field.

## Follow-ups

- Nothing yet surfaces the ingestion-time candidacy verdict anywhere an admin can see it — Phase 3 is
  what makes the check matter (auto-running the analyst and pointing the post-ingest UI at the Topics
  tab). Until then, `AppQuestionnaireVersion.adaptiveScopeCandidate` is written but read by nothing.
- The document-text cap (20,000 chars) is a first guess, not validated against a real long
  instrument whose routing pages sit past that point. Revisit if a real client document is flagged
  incorrectly negative.
- Gaps are shown but not actioned — there is no "turn this gap into a topic" shortcut. If admins
  routinely see the same class of gap (a data slot the instrument implies but the extractor never
  produced), that is a stronger signal than this tracker can act on alone.
