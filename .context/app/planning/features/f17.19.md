# F17.19 — Ingestion-time Adaptive Scope candidacy check

> Every part of Adaptive Scope is manual and undiscoverable: an admin has to already know the
> feature exists, open the Adaptive scope tab, and click "Run" — for a document that is, in many
> cases, already telling them exactly how to route it. This feature closes that gap in phases.
> **All four phases are done.**

## The four phases

1. **Candidacy detection at ingestion — DONE.** A cheap, fail-soft capability
   (`app_detect_adaptive_scope_candidacy`) runs during every fresh ingestion (all four entry
   points: new ingest + re-ingest, plain + streaming) and decides whether the uploaded document's
   own words describe conditional routing. Resolved at the `routing` tier, not the analyst's
   `reasoning` tier — this runs unconditionally on every upload, so it has to stay cheap.
2. **Gap-aware Routing Analyst — DONE.** `routingAnalysisSchema` carries a `gaps[]` field so the
   analyst reports routing language it recognized but could not formalize into a topic or hard
   rule, instead of silently dropping it.
3. **Auto-trigger wiring — DONE.** When Phase 1 flags a document, the Topics tab auto-invokes the
   existing Routing Analyst SSE endpoint on mount (no new job infrastructure — the same call the
   manual "Run" button already makes) so a reviewed draft is waiting without the admin needing to
   discover the feature. Never auto-enables `adaptiveScope.enabled` — that stays a deliberate,
   separate admin action, preserving the "off by default, inert by construction" invariant.
4. **Questionnaire Pack "Adaptive scope" section — DONE.** A 7th, off-by-default Pack section
   explaining the topics/rules/routing logic in plain language for a stakeholder audience. See
   [What Phase 4 shipped](#what-phase-4-shipped) below.

### Eligibility — skipped, not just found-nothing

The check does not run at all (no LLM call, no `AppAiRun`) when the version already has
`adaptiveScope.enabled`, already carries a topic an admin or the analyst authored (`source !==
'seeded'`), or already has a pending Routing Analyst draft. This is a detector for a **fresh,
unrouted** document, not a recheck of one an admin has already looked at — re-ingesting onto an
already-routed draft is a deliberate no-op here.

### It never throws

Every failure path — an unmocked/unreachable eligibility query, the agent not seeded, no provider,
a dispatch failure, an unparseable reply, even a failure to write the version cache after a real
verdict — resolves to `null` (or, for the cache write, a swallowed error alongside the still-valid
verdict). An early version of this shipped with an unguarded eligibility check and agent lookup;
either throwing turned a 500 into every ingest route's happy path. Both are covered by dedicated
regression tests (`tests/unit/app/api/v1/app/questionnaires/_lib/scope-candidacy.test.ts`).

### Cost control

The document text handed to the check is capped at 20,000 characters
(`MAX_CANDIDACY_DOCUMENT_CHARS`) — far less than the Routing Analyst's uncapped read. The sections
that announce conditionality (an intro, a "how to use this" page, a routing tab) are concentrated,
not spread evenly across a long instrument, so this is enough to decide candidacy without paying
for an exhaustive read on every single upload.

### Why `sourceQuote` is required on a gap, not optional like it is on a topic or rule

A topic or rule can be legitimately _inferred_ — the analyst says so via an absent `sourceQuote` and
a false `fromDocument`. A gap has no equivalent inferred form: it exists specifically to admit "the
document said something here that I could not turn into a topic or a rule." A gap with no quote would
be the analyst inventing a problem rather than reporting one, so the schema refuses it outright.

### Not persisted to the live topic set

`gaps` never reaches `AppQuestionnaireTopic` — accepting a draft posts only `topics`, `rules` and
`maxConditionalTopics` (`routing-analyst-card.tsx`'s `accept()`). A gap is advisory: the admin reads
it, and either authors a topic/criterion/rule by hand or accepts that the instrument is silent enough
there to leave it alone. This mirrors how `AppQuestionnaireTopicDraft.topics` already stores the whole
`ProposedTopicSet` as one JSON blob — no migration was needed to add the field.

### The durable "already tried" signal is the analyst's own `AppAiRun`, not a new column

`isEligibleForScopeCandidacy` (Phase 1) answers "should the **check** run" — it does not know
whether the **analyst** has since run, and re-querying it from the Topics route would just be a
second, possibly-inconsistent read of facts the GET handler already has (topics, draft, settings).
So `loadAutoTriggerState` takes those three as parameters and only queries two things itself: the
cached verdict, and whether an `AppAiRun` of kind `routing_analysis` already exists for the version.
That second query is what stops a discarded auto-proposal from re-proposing itself every time the
admin reopens the tab — the draft a discard deletes is not durable, but the run record is, and it is
written for a failed run inside `drive()` just as much as a succeeded one.

**What it does not cover:** the analyse/stream route's own early-return paths — rate limited, no
questions on the version, agent not seeded — sit ahead of any model call and record no `AppAiRun`.
An auto-trigger that hits one of those stays `pending: true` on the next visit and will retry. Judged
acceptable rather than fixed: retrying something that was never actually attempted is correct
behaviour, not a bug, and the rate-limit case in particular self-resolves within the same minute.

### Client-side, not server-triggered from ingestion

The auto-run fires from `RoutingAnalystCard`'s mount effect, not from the ingest route itself. Two
reasons: it reuses the exact browser-side call the manual "Run" button already makes (the spec's "no
new job infrastructure"), and an admin lands on the Overview tab after upload, not Topics — firing
from ingestion would mean either a background job (the thing being avoided) or an admin who never
opens Topics never getting a draft at all. "A reviewed draft is waiting" therefore means waiting for
whenever the admin next opens the tab, which is also the first moment the browser could make the
call anyway.

### Silent failure by design

A `{ silent: true }` run drops both branches that would otherwise call `setError` — the pre-stream
non-2xx path and the terminal SSE error — the same fail-soft posture as Phase 1's check. A rate limit
or an unseeded agent surfacing as a red banner on a tab load the admin didn't initiate would read as
the product being broken; the button stays available underneath, and a manual retry reports normally.

Full design rationale lives in
[questionnaire-pack.md](../../questionnaire/questionnaire-pack.md#whats-in-the-document) rather than
duplicated here — this tracker exists for the phase history, not the feature's permanent home.

**The section states a fact rather than hiding when scope isn't on.** `enabled: false` on the model
still renders the section — "Adaptive scope is not enabled for this version — every respondent is
asked the full instrument" — the same choice `PackEvaluations.hasRun: false` made for a
never-evaluated version: a toggle whose meaning shifts depending on what happened to the data behind
it is a toggle nobody can trust.

**A rule is a sentence, not a schema.** `describeScopeRule` resolves `ScopeRule.topicKey` /
`dataSlotKey` to their authored labels and renders `SCOPE_RULE_ACTION_LABELS` /
`SCOPE_RULE_OPERATOR_LABELS` into one line — "Always include "Talent & culture" when "Engagement" is
greater than "50"." — because the audience for this section has never seen (and shouldn't need to
learn) `ScopeRuleOperator` or `ScopeRuleAction`. An unresolved key (a rule pointing at a deleted
topic or data slot) falls back to the raw key rather than dropping the rule silently, matching this
feature's existing "unresolvable keys are skipped, never crash" posture everywhere else.

## Follow-ups

- The document-text cap (20,000 chars) is a first guess, not validated against a real long
  instrument whose routing pages sit past that point. Revisit if a real client document is flagged
  incorrectly negative.
- Gaps are shown but not actioned — there is no "turn this gap into a topic" shortcut. **DONE** —
  see [`f17.20.md`](./f17.20.md). A remaining, deliberately unbuilt idea: if admins routinely see the
  same class of gap (a data slot the instrument implies but the extractor never produced), that is a
  stronger signal than a per-gap shortcut can act on alone.
- Phase 3's auto-trigger can silently not-retry forever in the three early-return cases named above
  if an admin never revisits the tab after the first miss (no questions on the version, agent never
  seeded). Not fixed now because none of the three is expected to persist — a version with candidacy
  but no questions is itself unusual, and an unseeded agent is a deployment bug, not a steady state.
- Auto-trigger has no reservation/lock — two tabs open on the same fresh version can both auto-fire
  before either produces an `AppAiRun` row (`resolveAutoTriggerPending` in `scope-candidacy.ts`).
  Not fixed: the manual "Run" button already carries the same class of risk with no lock, the
  failure mode is a doubled LLM call plus a last-write-wins draft (not corruption — the draft table
  is unique per version), and it needs two tabs racing within one request window to happen at all.
- Phase 4's pack section reads live topics/rules from `AppQuestionnaireTopic`, never a Routing
  Analyst draft's `gaps[]` — a draft is not-yet-accepted, and the pack is meant to describe what the
  instrument actually does. An admin who wants gaps in a stakeholder document still has to turn each
  one into a real topic or rule first, which is the same manual step Phase 2 already leaves them.
