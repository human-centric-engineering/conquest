# F17.32 — An unreviewed routing proposal must not launch silently

> Asked as a design question: when ingestion detects that a document describes routing, should the
> platform turn Conditional Topics **on** by itself, or make turning it on a **compulsory** launch
> step? The answer is neither — and looking for it turned up the hole that actually mattered.

## Why not either of the two proposals

**Not auto-on.** At ingest time enabling is a no-op or worse: every topic seeded during
`persistIngestion` is `core`/always-asked, so the switch changes nothing until a proposal is
accepted — and enabling _after_ auto-accepting one would put natural-language criteria and data-slot
rules nobody read in charge of what real respondents are asked. A wrong rule silently _hides_
sections, and nothing at runtime reports a skipped section as an error. The candidacy check is tuned
to prefer false negatives, but its false positives would then narrow every session on the strength
of a triage call.

This is not the "prefer auto-detect over admin toggles" case. That rule is for toggles gating
**correctness** the admin cannot reason about (PDF table extraction — nobody wants it off). "Ask
everyone everything" is a legitimate, common choice, and detection proves the _document_ describes
routing, not that the _operator_ wants routed delivery. Those come apart constantly: a document
written for a paper facilitator, a pilot that wants full coverage, a cohort report that needs
comparability.

**Not a compulsory "turn it on" step.** A blocker whose only exit is "enable the feature" gets
resolved by whichever path is cheapest — deleting the conditional topics, or flipping it on without
reading the rules. Both are worse than the F17.22 warning. It would also need a dismiss for the
legitimate everyone-everything case, and a blocker with a dismiss is a warning with extra clicks.

## What was actually wrong

The launch checklist counted **accepted** conditional topics
(`appQuestionnaireTopic.count({ phase: 'conditional' })`). A version where candidacy fired, the
analyst proposed, and the admin never opened the Topics tab has none of those — so the checklist was
silent, every row passed, and the version launched looking clean with an unread proposal beside it.
The non-streaming ingest path is worse still: it does not run the analyst at all, so there is not
even a draft — just a cached verdict and an auto-trigger waiting for a tab visit that may never come.

## What shipped

1. **`conditionalTopicsReview` — a blocking checklist row** for a pending
   `AppQuestionnaireTopicDraft`, or a flagged document whose proposal has not been produced yet
   (`resolveAutoTriggerPending`). Legitimate as a blocker because the exit is _look at it_ — accept
   and discard both clear it — not _agree with it_. Fails open when the analyst cannot run.
2. **`includeConditionalTopicsReview`** on `loadLaunchReadiness`, passed `false` by the preview gate:
   rehearsing the draft is how an admin decides what to do about a proposal.
3. **"Turn on" on the `conditionalTopicsOff` warning row**, and its link relabelled Review — the row
   stated a misconfiguration whose only remedy was knowing the Topics tab has a switch on it.
4. **`metadata.launchedOverWarnings`** on the `questionnaire_version.status` audit entry:
   `assertLaunchable` now returns the failing non-blocking checks instead of discarding them.

Net effect: detection and proposal stay automatic, review becomes unskippable, and the product
decision — route or don't — stays with the human, where the accept dialog already put it.

## Two defects the code review caught, and what they cost

Both were found by `/code-review` on the first commit. Neither is a slip of the fingers; each is a
place where the row's promise ("the exit is _look at it_", "it fails open") was asserted in a
docblock and not actually delivered by the code beneath it.

**The row could not clear when the analyst was unseeded.** `resolveAutoTriggerPending` counts spent
retries from `AppAiRun` rows, and only `dispatchRoutingAnalysis` writes a `failed` one. The analyse
route returns ahead of it on three paths; a rate limit resets and a null `buildRoutingAnalysisInput`
implies zero questions (already a blocker), but an **unseeded Routing Analyst agent** is permanent —
`failures` stays 0 forever. On such a deploy every flagged draft was unlaunchable, exits limited to
"turn Conditional Topics on" or "hand-author a topic": exactly the coercion this feature exists to
avoid, reached by accident. Compounded by the Topics tab's auto-run being `{ silent: true }`, so an
admin following the gate message would find an empty page and no error. `detectedButUnreviewed` now
declines to raise the row when the analyst is unseeded. The pending-draft half is untouched — a
draft that already exists is resolved locally, so it stays a blocker even then.

**A fork resurrected a settled review.** `forkVersionIfLaunched` copied `conditionalTopicsCandidate`
(F17.19) but not the two facts recording how it was settled: the draft is not copied, and `AppAiRun`
is keyed on `versionId`. So a fork of a version whose proposal had been DISCARDED read as "never
looked at" — one redundant billed analyst run per edit-fork before this feature, and an unlaunchable
fork after it. The fork now drops the verdict, matching `duplicateQuestionnaire`. Note this reverses
the explicit F17.19 decision to carry it; the two tests pinning that behaviour were replaced, not
deleted.

## Deliberately not done

- **No blocker on `conditionalTopicsOff`.** See above — it stays a warning, now audited.
- **No "acknowledge this warning" checkbox in the launch dialog.** The audit entry answers the same
  question after the fact without adding a click to every launch.
