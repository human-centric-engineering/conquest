# F17.22 — Adaptive Scope should author itself

> "Adaptive scope is off — how do I turn it on?" … "I expected the AI agents to work through this,
> based on the doc, so that the conditional topics were set up for me. Adding the conditional topics
> is hard for the user. When the info has been provided in the doc upload, the conditional topics
> should be either automatically specified during upload processing or the user should be able to
> press a button in the designated area to get AI help for AI to do it."

## What is wrong

Nothing here is a missing agent. The **Routing Analyst already does this job well** — it proposes
conditional topics with criteria, hard rules and a breadth limit, and its rubric explicitly permits
inferring conditionality from the questions alone when the document states no rules
(`analysis-prompt.ts`, the `fromDocument: false` path).

What is wrong is everything **around** it: a conservative gate, a lazy trigger, a card in the wrong
place on the page, and a manual last step that nothing ever prompts. An admin can upload a document
that plainly describes routing and still arrive at a tab where every topic is `core`, no AI has run,
and no surface says AI is available.

Five concrete faults, all verified in the working tree at time of writing:

1. **A `false` candidacy verdict is invisible.** `routing-analyst-card.tsx` renders the candidacy
   banner only when `candidacy?.isCandidate`. When the check ran and declined, the admin is told
   nothing — so they never learn there is an analyst to press.
2. **The only button is far from the work.** `Propose topics from the document` sits on the analyst
   card, above the settings card, the preview card, the quality card and the evaluation card — and
   the Topics editor, where an admin would otherwise hand-author the same topics, has no AI
   affordance at all.
3. **The candidacy check is tuned to say no, and reads only the head of the document.**
   `MAX_CANDIDACY_DOCUMENT_CHARS = 20_000`, and the rubric forbids inferring conditionality from
   question variety ("When in doubt, answer false"). Routing/Guardrails pages at the back of a long
   instrument are never seen.
4. **A failed run suppresses the automation permanently.** `resolveAutoTriggerPending` treats any
   prior `routing_analysis` `AppAiRun` as "already tried", including one the route logged as
   `status: 'failed'`.
5. **Nothing closes the loop to `enabled`.** `acceptTopicDraft` deliberately never touches it, and
   the launch checklist's Adaptive Scope row appears **only when already enabled**
   (`launch/readiness.ts`) — so "conditional topics exist but are being asked to everyone" is a
   state the product never reports.

## The invariant this must not break

**Off by default, inert by construction.** `adaptiveScope.enabled` defaults `false` and
`resolveScope` short-circuits to full scope. Every phase below stays inside that: proposals are
inert until accepted, and `enabled` still moves only on an explicit admin act. Phase 4 offers that
act one click earlier; it does not perform it unasked.

---

## Phase 1 — put the button where the work is · **DONE** (2026-08-23)

Surface the analyst at the point of need, and stop hiding it when the candidacy check declined.

- A primary `Set up conditional topics with AI` action in the **Topics** section header
  (`topics-panel.tsx`), which triggers the analyst and scrolls to its review card. Wired with the
  `{ nonce }` request-prop pattern the tab already uses for `focusTopic` / `seedTopic`, so asking
  twice still fires twice.
- A real empty state on the analyst card when the verdict was `false` or the check never ran: say
  that no explicit routing instructions were found, and that the analyst can still propose
  conditional topics from the questions themselves.

No new AI, no new route, no migration. The free-text steer ("the routing rules are in the notes
before the questions") already exists on the card and on `runRoutingAnalysisSchema` — nothing to add
there.

## Phase 2 — run it during upload processing · **DONE** (2026-08-25)

When candidacy fires, dispatch the analyst inline in the **streaming** ingest and reingest routes
under a new `proposing_scope` phase, after `checking_scope`, and `saveTopicDraft` before the stream
closes. The admin is already watching ingest progress, so the added time is visible rather than
mysterious. Non-streaming ingest keeps the existing lazy tab-visit trigger — there is no background
job queue in this repo to hand a 180s run to, and no request should be held open for one. Fail-soft
throughout, same discipline as the candidacy check.

### What it took

**The analyst run moved out of the SSE route** into `_lib/routing-analysis.ts`, split in two:
`dispatchRoutingAnalysis` (runs it, re-validates the payload, records the **failed** `AppAiRun` on
both failure paths) and `persistRoutingAnalysis` (saves the draft, counts uncovered questions,
records the **succeeded** run + the admin audit entry). The SSE route keeps its phase events and
the `done` payload; it owns nothing else, and its 23 existing tests passed unchanged through the
move.

That split is the load-bearing part. The `routing_analysis` run row is the "already tried" signal
`resolveAutoTriggerPending` reads, so a duplicated implementation that forgot to record one would
re-propose on every tab visit — a paid model call each time — and one that recorded the wrong
status would disable the automation for the life of the version. Both halves now have exactly one
home. The run's `detail.trigger` and the audit metadata's matching field (`admin` | `ingest`)
answer "where did these topics come from" afterwards.

**`proposeScopeDuringIngest` never throws.** Missing agent, no analysable version, provider outage,
unusable reply, thrown query — all resolve to `null`. An upload that completed must never be
reported as failed because an optional proposal could not be made.

**The event contract gained two things**: the `proposing_scope` phase, and
`adaptiveScopeProposal: { topicCount, conditionalCount }` on `done`. The upload dialog renders
phase `message` generically, so it needed no change to show the new stage; the `done` payload is
there for a later surface that wants to say "6 topics are waiting for review" rather than leaving
the admin to find the tab.

**`maxDuration = 300` on both streaming ingest routes.** Neither declared one, and the worst case
is now extraction (120s) + candidacy (20s) + analyst (180s). The analyse route has always run a
180s call on the default, which is a separate pre-existing question, left alone.

### Tests

- `_lib/routing-analysis.test.ts` (**new**) — the failed run is recorded on both dispatch failure
  and unusable shape, the succeeded run only in the persist half, the steer is forwarded only when
  given, uncovered questions are counted, the trigger is audited, and `proposeScopeDuringIngest`
  returns `null` (never throws) for every failure mode including a rejected dispatch
- `stream/route.test.ts` and `reingest-stream/route.test.ts` — `proposing_scope` fires after
  `checking_scope` and only when the verdict was a candidate, the counts ride the `done` frame, a
  pre-check-ineligible re-ingest never proposes, and a failed proposal still completes the upload
  with no `error` frame

## Phase 3 — stop the gate swallowing documents that do say it · **DONE** (2026-08-25)

- Replace the 20k head-slice with head + tail + any section whose title matches
  routing / eligibility / guardrails / how-to-use / scoring.
- Pass the extracted structure (section titles, question prompts) to the candidacy check alongside
  raw text, so role- and segment-shaped instruments register — verdict stays quote-preferring.
- Exclude `status: 'failed'` runs from the `resolveAutoTriggerPending` suppression check.

### What it took

**The excerpt is composed, not sliced.** `selectCandidacyExcerpt`
(`lib/app/questionnaire/scope/candidacy-excerpt.ts`, pure and separately tested) spends the SAME
20k budget on the head, the tail, and a ~2k window around every passage using routing vocabulary,
in document order, with `[…]` marking each elision. Windows are capped at 8 — an excerpt shredded
into forty fragments reads and quotes worse than a contiguous one, and quoting is what this check
is graded on. The rubric gained a section telling the model the text may be an excerpt and never to
quote across a seam, which is the failure mode composition introduces: two distant spans joined at
an elision would otherwise yield a `sourceQuote` that appears nowhere in the document.

Anchoring on **routing vocabulary rather than section titles** as the plan's bullet suggested:
title-matching assumes the parser produced clean headings, which is exactly what fails on the
flattened workbooks this is for. The term list is domain-neutral by construction — the same
instrument shape turns up in clinical screeners, procurement questionnaires and staff surveys.

`matchedTerms` is logged. It answers the question the old code could not: whether "it said no" means
_it read the routing page and disagreed_ or _it never reached the routing page_.

**Structure travels with the text.** Section titles (≤120) and question wordings (≤300, truncated
at 200 chars) are read from the just-persisted version inside the check itself rather than threaded
through all four ingest callers — the graph is written before the check runs in every path. The
read is fail-soft like everything else here: losing the structure is a reason to check with less,
not a reason not to check. The rubric keeps its bias — a title addressing a kind of respondent is
stated routing; a long list of varied titles is still not.

**Failures no longer suppress forever.** Only a `succeeded` run is conclusive; failures are counted
and tolerated up to `MAX_AUTO_TRIGGER_ATTEMPTS` (2). Unbounded retry was rejected: a misconfigured
provider would turn a silent auto-run into a recurring bill. Legacy rows still read as conclusive —
`AppAiRun.status` defaults to `succeeded`, so no backfill.

The capability's DB `functionDefinition` gains the two new parameters. Nothing depends on that row
being fresh: the dispatcher validates against the in-memory Zod schema (`handler.validate`), and the
`functionDefinition` is what agents are _shown_, not what constrains a direct dispatch.

### What the code review then changed

Seven findings; six were real and are fixed in the same branch.

- **The excerpt's window budget affords ~3 windows, not the 8 the cap implied**, and first-come
  allocation over one flat term list let a scoring rubric early in a document spend the lot. Terms
  are now **strong** (can only be a routing instruction) and **weak** (real signals that are also
  ordinary words); strong takes windows first, wherever it sits. Head trimmed 10k → 8k to widen the
  window budget.
- **`maxChars` was not honoured below 14,000** — head and tail were added unconditionally. They now
  scale down with the requested budget.
- **The structure caps were counts, not characters.** Titles had no per-item truncation at all.
  Each item is now truncated and the two lists share an 8,000-character ceiling.
- **Questions were read version-wide by `ordinal`**, which is only globally ordered by ingestion's
  own convention — the Structure editor counts within a section. Now read through sections, the
  shape `buildRoutingAnalysisInput` already used.
- **`maxDuration = 300` was justified by a wrong number** (extraction is bounded at 300s, not the
  120s the comment claimed) and the worst case does not fit it. The inline proposal — the one
  skippable stage — now checks elapsed time first and defers to the tab's auto-trigger past 90s,
  because being killed mid-stream reports a failed upload for a questionnaire that persisted.
- **The ingest path never re-checked eligibility before writing**, so the race the candidacy check
  protects against ended with `saveTopicDraft` overwriting an admin's own pending draft.
- **`adaptiveScopeProposal` had no consumer.** The routes now emit a second phase message naming
  the counts, and the re-ingest dialog reports them on its result screen — the only surface where
  the admin is still standing when the run finishes.

### Tests

- `scope/candidacy-excerpt.test.ts` (**new**) — a short document is untouched; routing language at
  60k and at the very back both survive; the head is still carried; elisions are marked; the budget
  holds; a term on every page cannot shred the excerpt; `matchedTerms` reports terms already inside
  the head
- `scope/candidacy-prompt.test.ts` — the structure blocks render numbered and vanish when empty or
  absent, the excerpt/elision rule is stated, and the "variety alone is not routing" bias survives
  the new section
- `capabilities/detect-scope-candidacy.test.ts` — structure reaches the prompt, empty lists produce
  no blocks, and `redactProvenance` records counts rather than titles or prompts
- `_lib/scope-candidacy.test.ts` — the dispatch carries an excerpt that reaches the back of a long
  document, blank titles are dropped, a structure read that throws still checks; and for the
  auto-trigger: the succeeded-only query, one failure still fires, two do not, a success outranks
  any number of failures

## Phase 4 — close the loop to the switch · **DONE** (2026-08-25)

- **Readiness warning** when `conditionalCount > 0 && !enabled`. Highest value-to-effort item in
  this tracker: it converts a silent misconfiguration into a checklist row.
- **Accept-dialog offer:** when the accepted proposal contains conditional topics, an _unchecked_
  "Turn adaptive scope on now" box in the accept confirmation. Still an explicit act; one click
  instead of scroll-and-hunt.
- Link the Try-it card's "Adaptive scope is off" line to the switch.

### What it took

The warning row was the smaller half. The larger half was that **readiness had no notion of a
non-blocking check**: `launchReadinessChecks` returned `{ key, ok, label }`, and four separate
surfaces turned that into a verdict with their own `!c.ok` — `isLaunchReady`, the server
`loadLaunchReadiness`, the status route's `assertLaunchable`, and the checklist UI. Adding an
advisory row without touching them would have made it refuse launches in three places.

So every check now carries an explicit `severity: 'blocker' | 'warning'`, and one exported
`blocksLaunch(check)` is what all four ask. Explicit on every check rather than
optional-with-a-default: a new check must **state** that it blocks rather than block by accident,
and — the failure that would actually hurt — cannot become advisory by omission. The status
route's exhaustive `LAUNCH_MISSING_MESSAGE` map keeps an (unreachable) entry for the warning key
for the same reason: the map's exhaustiveness is what stops a future blocking check from shipping
without a gate message.

The count reaches the server seam as one indexed
`appQuestionnaireTopic.count({ where: { versionId, phase: 'conditional' } })` folded into the
existing `Promise.all`, rather than a conditional query serialised after the settings load.

### The third bullet, and why it is a sentence rather than a link

F17.25 put the master switch in a status header that is **always visible at the top of the tab**,
above the sub-tabs. Linking the preview card's off-line to a control already on screen would have
been a link to nowhere, so the line now names where the switch is instead. The same pass fixed a
copy bug next door: the accept dialog told an admin "adaptive scope stays off until you turn it on
yourself" even when the feature was **already on**.

### Tests

- `launch/readiness.test.ts` — the row's singular/plural label, that it is `severity: 'warning'`
  and never blocks, that it is silent when the feature is on or no conditional topic exists, and a
  pin that every pre-existing check is still a `blocker`
- `_lib/launchability.test.ts` — `ready` stays `true` with the warning present, and the row is
  absent both with zero conditional topics and with the feature on
- `launch-checklist.test.tsx` — renders as `(warning)` rather than `(not ready)`, is left out of
  the "remaining steps" count, leaves Launch enabled, and links to the Adaptive scope tab
- `_lib/topic-draft.test.ts` — `enable: true` persists `enabled: true` in the upsert; an absent
  `enable` leaves an off version off and an on version on
- `topics-draft-route.test.ts` — `enable: true` is forwarded and audited (`scopeEnabled`,
  `enabledByAccept`); `enable: false` is a 400 before anything is accepted; the body still carries
  neither `enabled` nor an unasked-for `enable`
- `routing-analyst-card.test.tsx` — the box is unticked, an untouched accept sends no `enable`,
  ticking sends `enable: true`, a cancelled tick is forgotten, and the box is absent (with the
  right sentence instead) both when the feature is already on and when the proposal has no
  conditional topic
