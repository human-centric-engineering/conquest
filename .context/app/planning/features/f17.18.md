# F17.18 — the routing map

> A zoomable canvas of the decision pipeline, opened from the Adaptive scope tab. Read-only, derived
> entirely from the payload the tab already holds, and carrying no new route, setting or migration.

## What was wrong

Nothing drew the routing.

The Adaptive scope tab is seven cards — explainer, findings, Routing Analyst, dry-run, routing quality,
settings, topic list — and every one of them states the routing in **prose or in lists**. All correct;
none of them a picture.

That matters more here than it would elsewhere, because what is being authored is a pipeline with a
**fixed order** — hard rules, then the agent's judgement, then guardrails — and the author's most common
mistake is misreading where a control sits in it. The settings card is numbered specifically to fight
that: an admin who reads `maxConditionalTopics` as a request the model tries to honour, rather than a
limit applied to its answer, will debug the wrong thing every time. A numbered list is the cheapest way
to say it. A drawing is a better one.

## What it does

A **"Routing map"** button at the top of the tab opens a near-full-screen dialog:

```
start ──> opening topics ──> hard rules ──────────────────────────┐
      │                  └─> planner ──> guardrails ──> conditional topics
      └──────────────────────────────────> always asked (core + closing)
```

Pan, zoom, minimap, legend. Click a node for its detail; a topic node also offers "Edit this topic",
which closes the map and expands that row in the list below.

## Confirmed decisions

- **There are no topic-to-topic edges, because there is no such mechanism.** The obvious diagram —
  arrows between topics — would draw a state machine the runtime does not have. Topics do not flow into
  one another; a topic is selected or it is not. What Adaptive Scope _is_ is a decision pipeline, so the
  pipeline is what is drawn.

- **The geometry is the argument.** A rule edge runs straight from the rule to its topic, **skipping over
  the planner and the guardrails** — because `applyGuardrails` seats rule includes before the cap and
  never truncates them. That is the exact misreading the numbered settings card exists to prevent, made
  into a shape. The always-asked band hanging off `start` and bypassing everything is the same claim
  about the other end: the planner touches the `conditional` phase and nothing else.

- **Structural, never predictive.** No fills exist at authoring time, so no rule can be evaluated and no
  plan can be known. Every rule draws its edge and the guardrails draw a candidate edge to every
  conditional topic. `evaluateScopeRules` / `plannerCandidates` are deliberately **not** called: both
  need a session's fills, and a map that pretended to have them would be a preview that lies — quietly,
  and in the one direction an author cannot check. The dialog says so in its subtitle and points at the
  dry-run, which is the surface that answers "what would this actually do".

- **The one thing the structure can settle is where a rule reads its evidence from**, and it is
  classified **exactly as `validateAdaptiveScope` classifies it** — opening, `core`, or neither. Solid
  from the opening topic that gathers it; amber dashed, _timing not guaranteed_, from a `core` topic; and
  from an explicit **"Not gathered in the opening"** node when nothing reachable gathers it at all.

  That node is the point of the treatment. `rule_veto_always_fires` is the sharpest finding this feature
  has — a veto reading an ungathered slot fires for **every** respondent and every plan it produces looks
  reasonable — and today it is one warning in a list. On the map the rule visibly hangs off nothing.

  The two computations are independent (the validator words a warning, the builder picks an edge), which
  is precisely the pair that drifts silently. Four tests assert they agree.

- **The pure builder imports no `@xyflow/react`.** `scope/graph.ts` emits its own neutral
  `{ nodes, edges }` with `x`/`y` already assigned, and the component maps that onto React Flow. That
  keeps `scope/**` the pure leaf the rest of the feature relies on, and lets the entire layout be
  asserted without a DOM — which is where the real test value is.

- **A rule's action is part of its node _kind_, not a field beside it.** `ruleInclude` / `ruleExclude`
  rather than `rule` + an action. Include and exclude are the one pair on this map that must never be
  confused at a glance, and splitting them means the renderer picks its colour and icon by exhaustive
  lookup with no branch that could fall through to the wrong direction. It also removed a string-sniffing
  helper (`badges.some(b => b.label === 'Include')`) that the React Compiler lint rightly rejected.

- **The always-asked band collapses, and its head node never leaves the canvas.** Ingest seeds one `core`
  topic per section, so fifteen-plus is the ordinary first sight and drawing them individually crowds out
  the only band any decision is taken about. It renders as one priced head node with a toggle. The head
  survives expansion because it is the band's **anchor**: `start` points at it, and a weak-evidence edge
  from a collapsed `core` topic falls back to it. React Flow silently drops an edge whose endpoint is
  missing, so a head that came and went would take those edges with it — hence the test that no edge ever
  names an absent node.

- **Controls are named generally; only the data is version-specific.** The band toggle first read
  "Show the 3 always-asked topics", which made a general affordance look like a hardcoded fact about
  whichever questionnaire was open. A control names what it **does**; the count belongs on the band node
  it acts on, where it already was. This is the shape of the whole feature — Adaptive Scope is a product
  offering tailored per customer **through config**, so nothing on the map may name a topic, a key or a
  quantity of its own. The builder holds no instrument-specific string; every one it emits is the
  feature's own vocabulary (Cap, Fallback, Blind-spot check, Phase, Depth), and everything else arrives
  from `TopicsPayload`.

- **A modal, not a sixteenth workspace tab.** The sub-nav already carries fifteen, and a permanent entry
  for a read-only view of another tab's data would say the map is a peer of the thing it depicts. The
  dialog says the truer thing and gives the canvas room.

- **No fetch, no route, no setting, no migration.** The map is a pure function of `TopicsPayload`, so
  "always synced with the settings" is a property of the construction rather than something anyone has to
  remember. The dialog is `key`-remounted on the payload for the reason its neighbours are: a picture is
  only true of the settings that produced it.

- **Read-only, with one way back.** Authoring on a canvas would put a second editor beside the topic list
  that could disagree with it. The single affordance is "Edit this topic", and it carries two details
  worth naming: the dialog **closes first** (the row is behind the overlay, so leaving it open reads as
  the button having failed), and the request carries a **nonce** beside the key, because asking for the
  same topic twice must still move the list — a bare key is unchanged state the second time and the
  effect never re-fires. `TopicListEditor` also **clears its filter** before expanding: a row the filter
  hides has nothing to open, and honouring an explicit request beats preserving a view preference.

- **Selection is not cleared when the graph is rebuilt.** The dialog resolves the selected id against the
  graph it just built, so a node that survives stays selected and one that does not resolves to null on
  its own — which is what an author wants when they expand the band while reading a topic's detail. An
  earlier version cleared it in the canvas effect; that was both unnecessary and, with setters whose
  identity changes, a way to clear the selection on every render.

## Follow-up: the detail panel earns its numbers

The map shipped with a panel that printed `Full depth 1m 17s` / `Light depth 16s` and, beneath them, the
author's criteria as one block of text. Both were wrong for the same reason: a reader could not get from
what was on screen to what it meant.

**The durations had no provenance.** Three questions an author actually has — what is counted, where the
number came from, and whether it describes the **chat** — were all unanswerable from two bare figures, and
the reasonable reading of an unexplained duration is that someone measured it. Nobody did: it is
`scope/budget.ts` charging a per-type rate per item.

- `ScopeNodeTiming` now carries the arithmetic. One line per **rate** (`4 × Likert @ 8s → 32s`), grouped
  by rate rather than by type so two matrices of different heights stay two lines. The column adds up to
  the headline.
- The **authored depth is marked** — one of the two figures is what this topic costs, the other is
  context.
- The **light sample is named**, not just priced, through the same exported `membersAtDepth` the interview
  resolves with. This is why `TopicQuestionRef` / `TopicDataSlotRef` now carry `weight`: showing the light
  duration while guessing at the light members would print a named set that disagreed with the number
  beside it.
- The headline figures still come from the server's `costs`. The breakdown is derived from the same
  per-item seconds — a second pricing implementation in the browser is the drift `scope/budget.ts` warns
  about.
- **Members whose key no longer resolves are counted and stated.** Silently short arithmetic is worse than
  none.
- **The chat caveat sits in the panel, not behind the ⓘ.** It is answering time only; the agent's turns,
  follow-ups and re-asks are not in it. An author who reads the figure as a stopwatch sets a session
  budget that halves their instrument. The ⓘ carries the longer version, including that this is
  nonetheless the arithmetic `applyGuardrails` fits the plan with.

**The criteria were a list rendered as a blob.** Authors and the Routing Analyst both write the same
shape — a lead-in sentence, then one line per signal with a priority marker — and every reader was
re-deriving it by eye. `scope/criteria-format.ts` recovers that structure and the panel draws it: prose,
bullets, a bolded term, a priority chip.

It **recovers, never rewrites.** Every character reaches the screen; only the bullet marker and the
priority marker move. Anything it cannot read falls through as a verbatim block with its line breaks
intact — which is exactly how the old panel rendered everything. The term split is deliberately
conservative (dashes only, never a colon; ≤48 characters, ≤7 words; refused if the fragment ends a
sentence or leaves nothing after it), because a wrongly-split term bolds a fragment and reads as a typo.
The failure mode is always "no term", never "the wrong term".

The panel also moved out of `routing-map-dialog.tsx` into its own file: two of its three parts stopped
being label/value rows.

## Tests

- `tests/unit/lib/app/questionnaire/scope/graph.test.ts` — 32 cases, and the weight is on the two claims
  the shape makes: that a rule edge bypasses the planner and the guardrails, and that **no edge ever
  names a node that is not on the canvas**. Plus the four agreement cases against
  `validateAdaptiveScope`, ordinal ordering, the collapsed/expanded band, and the structural-not-
  predictive pair (a rule-excluded topic still gets its candidate edge; the whole pipeline draws while
  the feature is off).
- `tests/unit/components/admin/questionnaires/topics/routing-map-dialog.test.tsx` — the shell: the canvas
  is not mounted until the dialog opens, the off-banner and the nothing-conditional note, the band
  toggle's node count, and that "Edit this topic" both fires and closes. `@xyflow/react` is stubbed with
  the `vi.hoisted` pattern from `workflow-canvas.test.tsx`.
- `tests/unit/components/admin/questionnaires/topics/topic-list-focus.test.tsx` — the jump, including the
  two ways it can silently do nothing: a filtered-out row, and a repeat request for the same topic.
- `tests/unit/lib/app/questionnaire/scope/criteria-format.test.ts` — 18 cases, governed by **nothing is
  lost**: the real pilot criteria string, every bullet character an author or a word processor produces,
  Windows line endings, indented continuations, and the four ways a leading fragment is refused as a term.
- `tests/unit/components/admin/questionnaires/topics/routing-map-detail.test.tsx` — the panel states its
  provenance: both figures with what each covers, the authored depth marked, every rate line, the named
  light sample, the unresolved-member note, and — asserted deliberately — the chat caveat visible
  **without opening the ⓘ**.
- The timing block's own agreement test in `graph.test.ts` prices the same five members through
  `estimateTopicCosts` and asserts the breakdown matches what the planner would charge.

Verified against the real pilot instrument (16 topics, 12 conditional, the G02 veto) by building the graph
from the live `GET …/topics` payload: 18 nodes / 18 edges collapsed, 21 / 21 expanded, no dangling edge in
either, and the veto rendered as `ruleExclude` reading a **solid** evidence edge — which agrees with that
version's zero findings, since its opening does gather `commercial_outcome`.

## Still open

The three overlays this deliberately does not carry, each with its data source already built:

- **The dry-run's verdict, lit onto the path it took.** `proposedKeys` already distinguishes "the agent
  never picked this" from "the agent picked it and a guardrail took it back" — the single most useful
  thing that could be painted onto these edges. The highest-value follow-up.
- **Routing analytics (F17.16)**, weighting each conditional topic by how often it was really selected,
  excluded or amended — so a criteria sentence that never fires is visible as a thin edge.
- **Coherence findings pinned to the nodes they name**, rather than listed above the map.

Also open: nothing exports the map as an image for a client deck, and the canvas is desktop-only in
practice — the detail panel is hidden below `md`.
