# F14.16 — Ingest fidelity

> A trial ingest of the Conditional Topics routing corpus' **easiest** document — the one rated
> "trivial", where "failure implicates plumbing, not judgement" — found four defects. None of them
> is about routing intelligence. The analyst scored well: all six expected conditional topics,
> correct phases, zero fabricated quotes. Everything below is the plumbing around it.

The corpus did its job on the first document anyone pointed it at, which is the argument for
running the other nine.

---

## 1. `.csv` was never ingestible

`tests/fixtures/.../01-medication-review.csv` could not be uploaded at all:

```
UNSUPPORTED_FORMAT — Allowed extensions: .pdf, .docx, .md, .txt, .xlsx
```

The parser router has always had a `.csv` branch (`parseCsv`, RFC 4180 with delimiter sniffing);
the questionnaire allowlist simply never listed it. So the corpus' baseline document — the one
whose entire purpose is to be the friendliest possible input — was the one document that could not
be run as authored.

### The drift underneath it

The allowlist was one of **seven** hand-maintained lists of accepted formats: the server constant
plus six admin `accept` attributes, none derived from the others. They had already come apart —
`topics/supporting-documents-card.tsx` offered `.csv` in its file picker that the server rejected
with a 400. A shipped bug, on the Conditional Topics tab, from the same root cause.

Both ends now derive from one place (`lib/app/questionnaire/constants.ts`):

| Constant                                                | Contents                         | For                                                                                                            |
| ------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `UPLOAD_EXTENSIONS` / `UPLOAD_ACCEPT_ATTR`              | `.pdf .docx .md .txt .csv .xlsx` | Routes that flatten workbooks first: ingest, re-ingest, supplementary documents                                |
| `PARSEABLE_UPLOAD_EXTENSIONS` / `PARSEABLE_ACCEPT_ATTR` | the same, **minus `.xlsx`**      | Routes that call `parseDocument` directly: intro-background parse, scoring-schema extract, round-context parse |

A unit test asserts the picker strings stay derived, so re-introducing a literal fails in CI rather
than in someone's upload.

### The `.xlsx` half, found on the way

`parseUploadGuard` reused the **full** list while all three of its consumers hand the buffer
straight to `parseDocument` — which has no workbook branch and **throws** on one. Uploading an
`.xlsx` to intro-background parse, scoring-schema extract or round-context parse produced a thrown
parse error rather than a clean 415. Their pickers happened to exclude `.xlsx`, which is why nobody
had hit it through the UI. Now guarded by `hasParseableExtension`.

### Why this improved the result rather than just unblocking it

`parseCsv` renders each row with its column names inline:

```
Section: Adherence | Question ID: AD2 | Question: What tends to get in the way… | When to ask: Only where PC2 is 4 or more
```

Every row carries the routing column, labelled. That is a materially stronger signal than raw
comma-separated text — the fidelity critic flagged **zero** questions on the CSV run against four
on an earlier `.txt`-copy workaround. **A `.txt` copy is therefore not a substitute for the real
CSV path**, and any corpus result recorded that way is not comparable.

## 2. The critic argued with the authoring schema

Doc 01 has one `Rating 1-5` question with no qualitative anchors. The extractor typed it `numeric`
and said why: _"Used numeric because the source gives 'Rating 1-5' without qualitative anchors."_
Correct. The critic then flagged it:

> `type_mismatch` — "Source response type is Rating 1-5, but extracted as numeric instead of a
> rating/likert scale."

The repair specialist duly built an unanchored likert, `likertWriteConfigSchema` rejected it, and
the pipeline discarded the correction and kept the original:

```
WARN  ingest repair: corrected config invalid; keeping original
      {"originalKey":"pm1_pain_control_current_medicines"}
```

The right answer, reached by accident, after ~5.1s and ~$0.008 on a round-trip that could never
have validated.

**The policy already existed in three places** — the write schema (whose error message says
_"or use the numeric type for an unlabelled rating"_), the extractor prompt, and the repair prompt.
It was missing from exactly one: the critic's rubric, which listed the types a rating must **not**
be (`single_choice` / `multi_choice` / `free_text`) and never said which type was right. The model
generalised from the omission.

Fixed by adding a `NEVER flag these` clause to `verify-prompt.ts` naming `numeric` as correct for
an unanchored rating — with the reason, so the rule survives a reword — while still flagging a
rating the source **does** anchor.

> The critic gained **no** new check for missing numeric bounds. That would open a fresh class of
> repair calls on every ingest carrying a bare rating scale. §3 fixes the bounds at the source.

## 3. A bounded rating lost its bounds

`Rating 1-5` persisted as `numeric` with `typeConfig: {}` — no `min`, no `max`, though
`numericConfigSchema` has always accepted both. The respondent got an unbounded box and the report
had no scale to read the answer against.

The extractor prompt taught `min`/`max` for likert (_"ALWAYS include integer min and max"_) and for
matrix scales, and said nothing for numeric; the output example demonstrated choice, likert and
matrix configs and omitted numeric entirely. Both now covered, and mirrored into the repair prompt
so a repaired numeric does not lose what the extractor kept.

PM1 now persists as `numeric` with `{"min":1,"max":5}`.

## 4. `AppAiRun` did not record the model that ran

F14.15 documents these fields as _"Resolved provider slug + model id that actually served the call
(post-fallback)"_. They held the agent row's **configured** values — and these agents ship with an
empty `provider`/`model` on purpose so they bind to the reasoning tier at call time. So:

| Recorded                                     | Actually served by    |
| -------------------------------------------- | --------------------- |
| `''` (`extraction_verify`)                   | `openai/gpt-5.4`      |
| `'n/a'` (`scope_candidacy`)                  | `openai/gpt-4.1-nano` |
| `'resolved-at-runtime'` (`routing_analysis`) | `openai/gpt-5.4`      |

`RESULTS.md` instructs the next person to read resolved models from `AppAiRun`. That instruction
could not be followed — scoring the trial run meant joining `ai_cost_log` on a timestamp.

### The fix, and the four sites that needed it

The capabilities already resolve the binding immediately before dialling and were discarding it at
`return this.success({ result: completion.value })`. They now return it, and callers read it
through `readResolvedBinding` (`lib/app/questionnaire/ai-run/resolved-binding.ts`) — a defensive
parse, so a capability predating the wider data type degrades to the sentinel rather than throwing
inside a provenance write.

| Site                                 | Run kind            |
| ------------------------------------ | ------------------- |
| `_lib/scope-candidacy.ts`            | `scope_candidacy`   |
| `_lib/routing-analysis.ts`           | `routing_analysis`  |
| `_lib/orchestrate-extraction.ts`     | `extraction_verify` |
| `…/glossary/analyse/stream/route.ts` | `glossary_analysis` |

A raw grep for the sentinel strings suggested thirteen sites. **Nine were already correct**, and
each now carries a comment saying so, because the obvious "fix" makes them worse:

- **Failure paths** (`routing-analysis`, `glossary`) — the dispatch never reached a provider, so
  no model can honestly be claimed.
- **`house-rules/suggest`, `opening-examples/suggest`** — success paths already record
  `result.provider` / `result.model`; only their failure paths use the sentinel.
- **`edit-agent/apply`** — documented and true: the LLM ran in the _preview_ request, so no
  binding is resolvable at the apply seam.
- **`lib/orchestration/evaluations/run-worker.ts`** — a `logCost` marker row, not an `AppAiRun`. A
  zero-cost `EVALUATION_BATCH` join key for analytics; no model serves it.

`'n/a'` is now the single spelling for "no model served this", via `UNRESOLVED_BINDING`. A second
spelling would split any "runs by provider" rollup in two.

### The `??` trap

`verification.provider ?? 'n/a'` looked right and was not: an agent that resolves at call time
reports an **empty string**, which is not nullish, so the fallback never fired and the column
stored `''`. `normaliseBinding` treats empty and nullish alike. Pinned by a regression test.

## Upstream

The capability→caller provenance gap is a platform seam, not an app problem: `CapabilityResult`
has a `metadata` channel but `BaseCapability.success()` cannot write to it, so an LLM-backed
capability must widen its own `TData` to report its binding. Sunrise never hits this — none of its
built-in capabilities are LLM-backed — which is why it survived as an unnoticed gap.

Filed upstream as [sunrise#676](https://github.com/human-centric-engineering/sunrise/issues/676).
**No platform file was patched here.** Drop the fork-side workaround if it lands.

## What this did not fix

The analyst swept doc 01's `Always`-marked AD1 into a conditional topic gated on _"Only where PC2
is 4 or more"_, so a patient on one to three medicines would never be asked the section's only
universal question. It filed an honest `gap` naming the mix, then resolved it by widening.

An earlier run of the same document split it correctly, so this is analyst variance on the one
wrinkle the corpus README flags — not a regression here; nothing in this feature touches the
analyst prompt. Parked as **T01** in the ledger's new `Candidate tweaks` table rather than acted
on: a prompt edit made from one observation of a case already seen going both ways is as likely to
encode the noise as fix the fault.

**Nine corpus documents remain unrun, including the entire restraint band (07, 08, 10)** — the
band that decides shippability. Nothing here says the pipeline is safe to ship.
