# F21.3 — The respondent surface

> Phase C of [the P21 plan](./f21-sectioned-interviews.md). Shipped in the same commit as
> [F21.2](./f21.2.md).

## What shipped

`sectionTabs` and `sectionClose` joined `RESPONDENT_SLOTS` and `ESSENTIAL_SLOTS`. The `satisfies
LayoutRegistry` gate then refused to build until all four layouts classified them, and the registry
test refused to pass until all four rendered them.

| Layout         | `sectionTabs`                                  | `sectionClose`               |
| -------------- | ---------------------------------------------- | ---------------------------- |
| **Classic**    | region: a strip above the conversation card    | region: beside the composer  |
| **Focus**      | region: a compact menu in the trailing cluster | region: beneath the composer |
| **Broadsheet** | region: the margin                             | region: the margin           |
| **Horizon**    | overlay via gesture, alongside folded history  | region: above the stage      |

Each placement is the layout's own argument, not a house rule copied four times. Focus strips chrome
deliberately, so a full strip would reintroduce what the layout exists to remove. Broadsheet's margin
already holds the two things the respondent DOES, and choosing which area to work in is a third.
Horizon folds everything that is not the current question, so a permanent seven-item strip is exactly
the accumulated wall it exists to put away — while `sectionClose` stays on screen, because it is an
action on the current question rather than a record of past ones.

## Two things worth keeping

**Whether a version runs in sections is resolved server-side and passed in**, like
`answerPanelScope` and for the same reason: the layout differs from the first paint, and a strip
that appears a moment after the conversation reads as a glitch. It also means an unsectioned
questionnaire never calls the strip endpoint at all. The first build had the hook fetch on mount
unconditionally, putting an extra round-trip on every respondent session of every questionnaire to
be told the feature was off. The existing workspace tests caught it by asserting an exact fetch
count, and the cause was the right thing to fix rather than the assertion.

**"Bring the section's answers into focus" cannot be one behaviour**, because three of the four
layouts omit `answersPanel` entirely. The container branches on `placements.answersPanel.kind` — the
idiom `reviewTrigger` already uses — and on the panel-less layouts marks the review trigger as having
new content rather than forcing a sheet open on every tab click. That is a deliberate softening of
the original requirement, recorded rather than silently implemented: on three of four layouts the
answers come into focus **when the respondent looks at them**.

## The strip never ships its membership

`SectionTabView` carries a label, a position, a status, availability and a reopen count — and not
`questionKeys`. Shipping the membership would put the questions of a section the respondent has not
reached into the browser, which is the reasoning `answered_only` panel scope already applies to
pending prompts.

## Known, left as-is deliberately

The answer panel's own header counts the section it is showing and does not say so, so question mode
can read "3 of 5 answered" over the active section while the top bar reads the whole interview. This
is the same two-figures trade as the tabs, one level down. The fix is a wording decision ("3 of 5 in
this section"), and inventing one mid-build is how a surface ends up with three ways of saying the
same thing.
