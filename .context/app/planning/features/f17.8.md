# F17.8 — Time as a budget: the cost model (C7, part a)

> Part of §1 of [`f17-followups.md`](./f17-followups.md), the largest of the P17 follow-ups. Split
> deliberately in two: **this** prices the instrument and shows the arithmetic; **F17.9** makes the
> planner obey it. Shipping the diagnostic half first means an author can see what an interview
> costs — and check the numbers against their own expectations — before anything starts dropping
> topics on the strength of them.

## What was wrong

`adaptiveScope.maxConditionalTopics` is a topic **count**, and it was standing in for **duration**.

The pilot client workbook's famous "no more than three routed sections" (G01) is not a preference, it is
arithmetic: a 600-second session, minus a mandatory floor of ~266s, leaves ~334s, which the three
most expensive routed sections fill almost exactly and a fourth cannot. Three is the answer for that
instrument at that budget, and the count records only the answer — not the question.

Two consequences. A client who says "make it fifteen minutes" needs a code change rather than a
setting. And the count cannot see that one topic is ten likerts and another is three, so it treats
areas that cost a respondent wildly different amounts of attention as interchangeable.

## Confirmed decisions

- **Additive, not a replacement.** `sessionBudgetSeconds` bounds **duration**;
  `maxConditionalTopics` still caps **breadth**. Both apply. They answer different questions and
  neither implies the other: three topics is not a length, and "under ten minutes" is not a
  statement about how many areas an interview should cover. Replacing the count would also change
  the meaning of every existing version's config at once.

- **`0` means no budget, and it is the default.** So no existing version changes behaviour. The
  narrowing deliberately does **not** clamp a small value up to the floor — `5` reads as 0, not as
  30 — because clamping would invent a budget the author never set and quietly start dropping
  topics.

- **Estimates, and named as such.** Real durations vary by respondent, question difficulty, and how
  much someone wants to talk. The estimate's job is to make relative cost visible and the fit
  decidable, not to predict a stopwatch. The two anchors are the client's own — **8s per likert**,
  **45s per free text** — and everything else is interpolated by how much of a decision the type
  actually asks for.

- **A matrix is priced per ROW.** It is N ratings wearing one prompt. Costing it as a single item is
  how a 12-row grid ends up looking cheaper than the three likerts beside it, which is exactly
  backwards.

- **An unrecognised stored type prices as free text** — the most expensive guess. Under-costing an
  unknown is how a budget silently over-fills.

- **An unusable per-type override is DROPPED, not defaulted to zero.** A type costed at nothing makes
  every topic using it look free, which is the one failure a time budget cannot survive.

- **`light` depth is priced through the resolver the interview actually uses.** `topicSeconds` calls
  `membersAtDepth` (now exported) rather than re-deriving "the top two by weight". Duplicating that
  rule is how a cost model and a resolver drift apart without anyone noticing — and the blind-spot
  check's cost is exactly the number F17.9 must not treat as free.

- **The arithmetic is computed server-side**, in the topics route, and shipped on the payload as
  `costs`. Same reasoning as `issues`: one implementation, so the number an author reads on the tab
  and the number the planner will work to cannot disagree.

- **Two new coherence findings**, because a budget below the floor is not a tight interview but a
  broken one — the planner has nothing to spend and the instrument silently stops adapting:
  `budget_below_floor` (**error**: the always-run questions already exceed the budget) and
  `budget_admits_no_topic` (**warning**: the leftover cannot fit even the cheapest conditional
  topic).

**Tests** — new `budget.test.ts` (18) asserts what a count could not: two same-sized topics costing
different amounts, a matrix priced per row, `light` priced through the real resolver and its weights,

narrowing, including `0`-means-off and the dropped-override rule. `validate.test.ts` covers both new
findings.

## A note on the worked example

`budget.test.ts`'s worked example has the **shape** of the pilot client derivation — a floor spent before
any routing decision, then an allowance a specific number of topics happens to fit — but **invented
item counts**. The real workbook is deliberately kept out of this repo, and reproducing its figures
would mean fabricating the client's question set. The test asserts the properties the model must
have, not that any particular instrument comes to any particular number.

The example is tuned so the blind-spot check does **not** fit inside the allowance the three chosen
topics leave. That is the finding `f17-followups.md` §1 records — the workbook's own arithmetic omits
G04's two items — and F17.9 must count the check topic rather than treating it as free.

## The admin readout

Landed after a coordination pause: a peer session was concurrently rewriting the same three
components (the "Adaptive scope" tab rename, the collapsing topic rows, the numbered decision-order
settings card) and handed the budget UI over once its work was committed as `7d538b664`.

- **Settings card** — "Session length budget" sits in the step-2 grid as a **sibling** of the topic
  limit, not ahead of it. The peer suggested demoting the count; declined, because breadth and
  duration are genuinely different bounds. Beneath the field, `BudgetReadout` states the arithmetic:
  _"about 4m 26s goes to the questions every respondent gets, leaving ~5m 34s for conditional
  topics"_, or a plain warning when the floor already exceeds the budget.
- **Topic rows** — `· ~Ns` on the collapsed summary line, where a skim can use it.
- **`topics-panel.tsx`** — the three new fields added to the PATCH body, plus a comment recording
  that the enumeration is load-bearing rather than an oversight: `rules` reaches the server through
  the same PATCH but is edited as its own list, so a spread would push through fields the settings
  card does not own.

One deliberate departure: the per-topic estimate is computed **in the browser** from the per-item
seconds the route already sent, not read off `costs.byTopicKey`. That row shows an unsaved draft, and
a server-sourced figure would sit unchanged while an author added three questions — worse than none.
It calls the same exported `membersAtDepth`, without weights (the resolver's own fallback), so a
`light` topic may land a few seconds from the server's figure.
