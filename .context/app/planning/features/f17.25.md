# F17.25 — The status header and the master switch

Phase 2 of the tab simplification.

## What was wrong

The tab is ~5,700 lines across 18 components, rendered as one unbroken vertical stack **ordered by
the runtime pipeline rather than the authoring job**. The AI proposer leads, the verification cards
sit in the middle, and the topic list an admin edits most is last, below roughly 4,000 lines of
other surface.

The master switch — on which the feature's whole "off by default, inert by construction" invariant
rests — lived in the header of the **tenth card**. That is the last place someone arriving at the
tab to ask "is this even on?" would look, and there was nothing above it that answered.

## What shipped

**`ScopeStatusHeader`** — presentational only, above everything. Props are counts and booleans; no
payload, no fetching, no derived state beyond formatting, so it cannot grow a second source of
truth about whether the feature is on. It answers both arriving questions at once: the on/off state
with a sentence saying what that state _means_, the topic and conditional counts, uncovered
questions, the always-asked cost, and the time limit.

**`ScopeIssueStrip`** — the summary half of the two-level pattern `config-conflicts.tsx`
established. `ScopeIssues` stays as the full read, moved down to sit against the topic rows it is
about. Both render the same `validateConditionalTopics` output, so they cannot disagree about what is
wrong; the difference is how much each says and where.

## Confirmed decisions

- **The switch is controlled by `payload.settings.enabled`, never a local draft.** That is what
  makes a declined fork correct: `authoringMutate` throws `ForkCancelledError`, the panel writes
  nothing, and the next render puts the switch back. A drafted switch would sit in the clicked
  position describing a version that was never written.
- **Single-writer discipline, enforced in three places.** `enabled` is gone from the settings
  card's control, from its remount key, and from the panel's enumerated PATCH body. Left in the
  key, a header toggle remounts the card and eats unsaved settings work; left in the body, the
  card's stale draft re-writes whatever the header just set. The card still _carries_ the field —
  its draft is a whole `ConditionalTopicsSettings` — but it has no control that writes to it, and the
  panel is what stops it reaching the wire.
- **The toggle sends `{ enabled }` alone.** Which is exactly the shape F17.24's Zod-coupling test
  was written for: the server side is a read-merge-write over a schema whose every field is
  optional, so a lone-field body is the one most likely to expose a regression there.
- **Issue rows are buttons, not anchors.** `ConfigConflict` carries a `sectionId` and links to
  `#anchor`; `ScopeIssue` carries only `code` and an optional `topicKey`, so there is no anchor —
  the thing that fixes a finding is a topic row whose DOM id is a client-side detail.
- **A topic-scoped row reuses the existing focus handoff** rather than growing a second mechanism.
  A finding about a topic and a routing-map node about a topic want the identical thing to happen,
  so they ask for it the identical way — the same nonce, the same effect, and the same
  "waits while hidden" gate F17.24 added.
- **A whole-setup finding renders as plain text.** `no_opening_topic` is about the set, not a row;
  a button that moved the page somewhere unrelated would be worse than no button.
- **`budgetSeconds === 0` renders "no time limit set", never "0m".** Zero is the off value because
  a duration of zero is not a usable one, and `formatSeconds(0)` would print a limit so tight
  nothing could run.

## What changed

| Path                             | Change                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------- |
| `topics/scope-status-header.tsx` | **New.** Presentational header: state sentence, switch, counts, coverage, time          |
| `topics/scope-issue-strip.tsx`   | **New.** Summary strip, errors first, capped at four rows, topic rows jump              |
| `topics/topics-panel.tsx`        | Mounts both; `toggleEnabled`; `goToIssue`; `enabled` dropped from the PATCH and the key |
| `topics/scope-settings-card.tsx` | Switch removed; the conditional-copy gate reads props; description points at the header |

No API change, no migration — the header reads fields the payload already carried after F17.24.

## Tests

- `scope-status-header.test.tsx` (**new**) — the off-state sentence, the switch reporting rather
  than flipping itself, disabled while busy, `0` rendering as "no time limit set" and never "0m",
  and the uncovered-question line appearing only when there is one
- `scope-issue-strip.test.tsx` (**new**) — nothing when coherent, "blocks launch" rather than
  "errors", warnings not called blockers, errors sorted first, the four-row cap, and the
  button/plain-text split on `topicKey`
- `topics-panel.test.tsx` — the toggle PATCHes `{ enabled }` alone and the body carries no
  `enabled` on a settings save; a declined fork leaves the switch where it was; a strip row drives
  the focus handoff
- `scope-settings-controls.test.tsx` — the "master switch" block becomes "no longer owns the master
  switch": no switch rendered, the conditional copy follows props, and the card cannot mutate
  `enabled` on the way through

7,769 tests pass across the questionnaire component, lib and integration suites.
