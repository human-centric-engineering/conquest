# F17.10 — Cross-scale normalisation (C8 / G06)

> Closes §3 of [`f17-followups.md`](./f17-followups.md). Capability C8 of the pilot client research notes,
> guardrail G06 of its workbook.

## What was actually wrong

The follow-up recorded this as a pilot-client problem: Section 14 runs a **1–6** agreement scale, Sections
1–13 run **1–5** extent, and `scoreSession` combined the raw values, so a composite spanning them was
arithmetic over two rulers.

Checking the code before building it found the trap is **wider than the pilot instrument and already live**.
Nothing constrains a scoring item to a likert question:

- `scoring-builder.tsx` offers **every** question and every data slot as an item — it prints the type
  in the label and no more.
- `scoringSchemaContentSchema.superRefine` validated scale keys and band ranges. Never types.

So a `numeric` question ranged 0–50 could already sit in a scale beside 1–5 likerts, where it does not
merely skew the mean — it decides it. The pilot instrument's 1–6 section is the mild version. That reframing is why
this shipped as a platform correctness fix rather than a client workaround, and it is what the
client-facing question ("should the client standardise on 1–5?") is now independent of: **a 6-point scale
has no midpoint, which forces a lean rather than a fence-sit, and may well be deliberate.** The build
does not depend on the answer.

## Confirmed decisions

- **Off by default, and that default is load-bearing.** `normalise` changes what `raw` means. Any
  other default would silently restate every existing schema's scores in units nobody authored.

- **Normalise to 0–1, and refuse the save when bands disagree.** The alternative considered was
  rescaling onto a common target range (say 1–5) so existing cutoffs survive, or auto-rewriting the
  author's cutoffs on flag flip. Both were rejected: the first adds a field to explain for a benefit
  only some authors get, the second silently edits numbers a human wrote, and is simply wrong when
  bands were authored against a `sum`. Instead `scoringSchemaContentSchema` **rejects** a save whose
  cutoffs fall outside 0–1 (0–_n_ under `sum`, one per item) with a message naming the range. Without
  it the failure is invisible: `bandFor` matches nothing, every respondent gets `band: null`, and the
  cohort report's band breakdown empties out with no stated cause.

- **An unbounded item is dropped, not passed through.** Under `normalise`, an item whose question has
  no numeric range cannot be placed on the ruler. Letting it through in raw units would reintroduce
  precisely the mixing the flag exists to prevent — and it would be the worst version of it, since
  the un-normalised item is the one with the widest range. The drop is visible as `itemCount` falling
  short of `totalItemCount`, and the builder warns before the save.

- **`matrix` deliberately supplies no bounds.** It carries a shared scale at `typeConfig.scale`, so
  widening `itemBounds` to read it looked obvious. It is dead code: a matrix answer is a composite
  `{rowKey: point}` object, `asFiniteNumber` rejects it, and a matrix item therefore contributes
  nothing to any scale today. Returning bounds would advertise a capability the engine does not have.
  `numeric` **is** covered, but only when the author set both ends — an open "how many reps?" has no
  ruler, and inventing one would be worse than admitting it.

- **No migration, no version stamp on the score row.** `AppRespondentScore.scores` is a denormalised
  snapshot with no record of the flag it was computed under, which looks like a gap until you follow
  the write path: the schema PATCH route already recomputes every non-preview session on save, so a
  schema edited through the UI self-heals. The copy/import paths that carry a schema forward create
  versions with no sessions attached, so there is nothing stale for them to leave behind.

- **The builder warns in both directions.** The scoring-schema GET now returns the real `bounds`
  behind each key (it already returned `type`), so `rulerWarnings` can say two different things: with
  normalisation **off**, that a scale mixes ranges and its arithmetic is meaningless; with it **on**,
  that named items will be left out. Warnings, not errors — an author may know exactly what they are
  doing.

## What shipped

| File                                                 | Change                                                                                                                                                                                          |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lib/app/questionnaire/scoring/types.ts`             | `ScoringSchemaContent.normalise?: boolean`; `EMPTY_SCORING_SCHEMA` sets it false                                                                                                                |
| `lib/app/questionnaire/scoring/score.ts`             | Per-item 0–1 rescale after reverse-scoring; unbounded/degenerate items dropped; the private `normalise()` band-span helper renamed `bandPosition()` to free the name                            |
| `lib/app/questionnaire/scoring/compute.ts`           | `likertBounds` → exported `itemBounds`, covering `numeric` with both ends set                                                                                                                   |
| `lib/app/questionnaire/scoring/schema-validation.ts` | Flag in the strict Zod + the lenient narrow (absent ⇒ false); band-range check under `normalise`, ceiling 1 for `mean` and the scale's item count for `sum`                                     |
| `lib/app/questionnaire/scoring/extract.ts`           | The extraction prompt learns when to set the flag and that cutoffs then live in 0–1                                                                                                             |
| `…/versions/[vid]/scoring-schema/route.ts`           | Returns `bounds` per question key; audit metadata records the flag                                                                                                                              |
| `components/admin/.../scoring-builder.tsx`           | "Put items on a common ruler" checkbox + `FieldHelp`; `rulerWarnings`; the flag added to the PATCH body literal (it is explicit, so an omission would have been silently dropped on every save) |

**Tests** — `score.test.ts` gains a `normalise` block asserting the _difference_ from raw arithmetic
rather than merely that a number came out (4-of-5 and 4-of-6 → 0.675, not 4), plus drop-on-no-bounds,
degenerate bounds, weights on normalised values, and 0–1 band matching. `schema-validation.test.ts`
covers the band-range error both ways and the narrow default. `compute.test.ts` gains `itemBounds`,
including the matrix case.

## Still open

Nothing from §3. The wider finding it turned up — that a scoring item's type is unconstrained — is
now _surfaced_ by the builder's warnings but still not _enforced_, which is the right side of the
line: an author combining a bounded numeric with likerts under a common ruler is doing something
legitimate.
