# F18.6 — Cross-boundary lints, and conflicts at launch

## What was wrong

**Two things, both about a warning nobody could see.**

`detectConfigConflicts` had seventeen checks and never mentioned `adaptiveScope`. But the two
features meet at exactly one point neither surface shows: the Scope Planner runs once, the moment
the opening topics are covered, and decides the rest of the interview from what the respondent said
there — while the questioning approach decides how that opening is asked. Set the approach to
`targeted` with Adaptive Scope on and the planner has one narrow answer to route a whole interview
from. Nothing errors and nothing is empty, because `planScope` never throws; it falls back. The
instrument simply asks less than its author believes it asks.

Separately, the sharpest existing check — `house-rules-overpromise-anonymity`, a rule promising more
anonymity than the questionnaire actually offers — is `warning` severity and lived **only** on the
Settings tab. It never blocked anything and an admin who did not open that tab never saw it, though
it is a claim the client has to stand behind afterwards.

## What shipped

**Three cross-boundary checks**, all gated on `adaptiveScope.enabled` and all anchored to
`interviewer-strategy` — that is the setting the admin would change, and it is the one on this tab:

| id                                | Severity | When                                                                 |
| --------------------------------- | -------- | -------------------------------------------------------------------- |
| `adaptive-scope-targeted-opening` | warning  | `targeted` leaves the planner nothing to read                        |
| `adaptive-scope-no-probes`        | warning  | a zero opening allowance means a vague answer can never be clarified |
| `adaptive-scope-guided-openings`  | info     | written example openings steer the routing, not just the tone        |

**The banner beside the launch checklist.** The version overview page renders the existing
`ConfigConflictBanner` above `LaunchChecklist`, so a draft's settings conflicts are in front of the
admin at the moment they are deciding to go live.

## Confirmed decisions

- **No new launch-readiness gate.** Readiness rows are pass/fail gates; `detectConfigConflicts` never
  emits `error` by design, because it is guessing at intent from keyword matches. Wiring a
  never-blocking lint into a blocking checklist would misrepresent both. The banner sits _beside_
  the checklist instead — advisory, exactly as it is on Settings.
- **No new query anywhere.** `ConfigEditor` has had `config.adaptiveScope` in its props all along
  (`CONFIG_SELECT` selects it) and simply never read it; the overview page already loads the full
  `graph.config` and `questionCount` for the checklist.
- **`readiness.ts` and its four callers are untouched.** The narrow `loadLaunchReadiness` select
  stays narrow — nothing there needed to change to put this in front of an admin.
- **Two `ConfigConflictInput` builders, deliberately.** The editor keeps building its input from
  **unsaved** local state so the banner reacts as the admin types; `configConflictInputFromConfig`
  builds from the **saved** `ConfigView` for surfaces describing a version as it stands. Those are
  genuinely different questions and the launch checklist must answer the second. They cannot drift
  silently: `ConfigConflictInput` has no optional fields, so a new one breaks both at compile time —
  which is exactly what happened when the three adaptive-scope fields were added.
- **`ConfigConflictBanner` gained an optional `basePath`.** Its rows link to `#<sectionId>` anchors,
  which resolve to nothing off the Settings page. The overview passes the settings path so each row
  is a link to the control that fixes it. Default `''` keeps the Settings tab on a bare fragment (no
  navigation), so nothing there changes.
- **`captureEnabled` is derived, not read.** There is no such column — the editor computes it from
  `profileFields.length > 0`, and the new builder had to do the same or the two surfaces would
  disagree about what "capture is on" means for one version. Pinned by a test.
- **All three new checks obey the file's three governing rules**: never `error`, worded as "may
  not", and quiet unless there is something real to say (the guided-openings note stays silent when
  no example is actually written — check 8 already says that setting is inert, and claiming it
  steers the routing too would describe an effect that is not happening).

## Still open

- **Nothing checks the reverse direction.** These describe what the interviewer does to Adaptive
  Scope. Whether the topic criteria are written against the kind of answer the opening actually
  invites is a judgement, not a rule — that is the policy judge panel.
