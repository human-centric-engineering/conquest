# F20.4 — The prompt-cache audit, and why the prompt was left alone

> [F20.1](./f20.1.md) said interviewer phrasing is 46% of a turn and is the stage whose first token
> ends the wait, so Phase 4 was meant to make its prompt cacheable. The audit found the prompt is
> indeed uncacheable — and that fixing it would buy almost nothing while risking the reply contract.

## What was measured

Not estimated. Every turn already persists the phraser's real prompt and per-call latency on
`inspectorCalls`, so all three numbers below come from actual traffic on the dev database.

### 1. The prompt caches nothing today

The cacheable prefix is the leading text two consecutive turns share. Measured across 13 sessions:

|                                             |                                 |
| ------------------------------------------- | ------------------------------- |
| System prompt                               | ~1,600–2,700 tokens             |
| Whole prompt (system + user)                | ~1,785–3,031 tokens             |
| **Shared prefix between consecutive turns** | **~560–750 tokens**             |
| Where the prefix breaks                     | **always inside `<this_turn>`** |

OpenAI's automatic prompt caching applies only to prefixes of **1,024 tokens or more**. The shared
prefix never reaches it, so **no turn is a cache hit** — every one re-processes 1,800–3,000 tokens
from scratch.

The cause is structural. `<this_turn>` is the third section and changes every turn, so only `<role>`
and `<rules>` precede it. Everything after — including the large, entirely static `<output_format>`
and `<message_shape>` — is re-read each time.

### 2. Fixing it means inverting a deliberate precedence hierarchy

The prompt's convention is **later sections win**, and three comments in `question-stream.ts` depend
on it. The relevant one:

> `<house_rules>` … Deliberately placed AFTER `tone` — a client's policy outranks the admin's voice
> dials … — but BEFORE `output_format`/`message_shape`, which must keep governing the reply contract
> no matter what a rule asks for.

The stable, cacheable content is exactly the content deliberately placed LAST, because last means
highest precedence. Hoisting `<output_format>` + `<message_shape>` (~650 tokens) ahead of
`<this_turn>` would take the prefix to ~1,200 tokens and start caching — and would simultaneously
make a client house rule ("answer in bullet points") outrank "conversational prose only", which the
chat surface renders and parses as prose.

**The prompt's precedence design puts its most stable content precisely where a cache cannot use
it.** That is a genuine tension, not an oversight.

### 3. …and the payoff would have been negligible anyway

The premise was that phrasing is slow because it re-reads a large prompt. The persisted telemetry
says otherwise — latency barely tracks input size:

| Model   | n   | Avg latency | Avg tokens in | Avg tokens out | corr(latency, in) | corr(latency, out) |
| ------- | --- | ----------- | ------------- | -------------- | ----------------- | ------------------ |
| gpt-4o  | 18  | 1,732 ms    | 1,741         | 63             | **0.21**          | 0.28               |
| gpt-5.1 | 7   | 3,947 ms    | 2,065         | 84             | **0.22**          | 0.31               |

A correlation of ~0.2 between prompt size and latency means prefill is a small share of the call.
Caching would remove the prefill of ~1,200 of ~2,500 tokens — a fraction of a component that is
already weakly related to the total.

So the trade was: invert a safety-relevant precedence hierarchy, in exchange for a saving the data
says is close to nil. **Not taken.**

## What shipped instead

The section order was an unwritten contract — three comments and nothing executable. Given that
Phase 4 has now established a standing temptation to reorder exactly those sections in pursuit of a
cache win, that gap was the thing worth closing.

`question-prompt-order.test.ts` pins the full section order as a behaviour contract, including the
three precedence rules with their concrete failure modes. Hoisting the reply contract to the front —
the precise change a future cache attempt would make — fails four of its six tests.

No production code changed. No prompt text changed. Chat behaviour is bit-identical.

## The bigger finding, which is not ours to act on

The same telemetry shows something larger than anything in P20: **the interviewer agent is
configured to `gpt-5.1`, which averaged 3,947 ms against `gpt-4o`'s 1,732 ms — 2.3× slower — on
comparable input (2,065 vs 1,741 tokens) and comparable output (84 vs 63 tokens).**

That gap is ~2.2 s/turn, more than every latency saving in P20 combined.

It is deliberately **not** acted on here. Moving the interviewer's model is the "drop classifiers to
a cheaper tier" idea the plan excluded on 2026-08-30 as a direct quality trade, and the interviewer's
prose is the product. Two caveats before anyone treats the number as established:

- **n=7 for gpt-5.1**, drawn from different sessions and questionnaires than the gpt-4o rows. Input
  and output sizes were comparable, so the gap is not explained by workload — but it is not a
  controlled comparison either.
- gpt-5.1 latency varied 1,893–8,569 ms on near-identical inputs, so the variance is large and its
  source is not established here.

A controlled A/B — same questionnaire, same questions, judged on output quality as well as speed —
is the way to settle it. That is a piece of work, not a config change.

## Follow-up worth recording

**We cannot currently confirm a cache hit empirically.** The phraser records `tokensIn`/`tokensOut`
but not OpenAI's `cached_tokens`, so the "nothing caches" conclusion above is derived from the
measured prefix plus the documented 1,024-token threshold rather than observed directly. Capturing
`cached_tokens` in the usage rollup would make it observable, and is a small change.

## How to re-run the measurement

Both figures come from `AppQuestionnaireTurn.inspectorCalls`, which stores each call's full prompt,
latency and token counts for every session:

1. **Prefix**: group `Interviewer phrasing` prompts by session in turn order, take the longest
   common prefix of consecutive system prompts, and count its tokens with `estimateTokens`.
2. **Latency drivers**: correlate `latencyMs` against `tokensIn` and `tokensOut`, split by `model`.
