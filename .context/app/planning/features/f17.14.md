# F17.14 — the plan preview

> Phase 1 of the Adaptive Scope II plan. The first of three read-only phases: build the instruments
> before changing the engine.

## What was wrong

Nothing in the product simulated a plan.

`validateAdaptiveScope` checks that a setup is **well-formed** — no orphaned questions, no
unreachable rule, a budget above the floor. It says nothing about what the setup will _do_. So for a
capability whose entire premise is "the model makes a judgement you cannot fully specify in advance",
the author's only feedback loop was: write prose criteria, switch on, run a whole interview as a
respondent, and infer the plan backwards from which questions arrived.

That is slow enough that in practice nobody does it more than once, which means criteria ship
unverified — and a criteria sentence that never fires is invisible. The topic simply never appears in
anyone's interview, and no surface reports it.

## What it does

`POST …/topics/preview` takes a synthetic opening — typed answers plus hand-set data-slot fills — and
returns the plan the version's current settings would produce. Same rules, same agent, same
guardrails, same order. It creates no session and writes no plan.

The card sits on the Adaptive scope tab between the settings it reads and the topic list it is a
verdict on, and hides itself entirely when no topic is conditional (there is no decision to preview).

## Confirmed decisions

- **The decision trace is the feature, not the plan.** An author staring at a topic that missed the
  cut needs to know which layer dropped it: the criteria, the cap, the seconds, or a rule. The plan
  already carries `source` on every topic in and out. The one distinction it _cannot_ carry is "the
  agent never picked this" versus "the agent picked it and a guardrail took it back" — the difference
  between a criteria bug and a limit that is too tight — so `proposedKeys` comes back beside the plan,
  read from the planner's own pre-guardrail output snapshot.

- **Synthetic only; no replay over real sessions.** Replay would be strictly more faithful and was
  deliberately not built: it puts respondent answers into an authoring surface. The cost is real and
  is stated in the card rather than hidden — the author is testing against their own imagined
  phrasing, which is the phrasing least likely to break the routing. Replay stays an open follow-up.

- **The fills are hand-set, and that is the point.** In a live interview a fill is an extraction FROM
  the answers, so setting one by hand is a hypothesis rather than a prediction; the panel says so.
  Running the real extractor over the typed text would have been more faithful and much slower — and
  would have made the one demonstration that matters _harder_. A `not_exists` veto fires on an
  **absent** fill, so the slots a veto watches are marked in the form and leaving one empty is
  presented as a deliberate act rather than an unfinished field.

- **No `AppAiRun`.** `ai-run/types.ts` is explicit that interactive previews an admin is merely
  exploring with are not provenance: nobody acts on the verdict, it changes no durable config, and it
  is not an output anyone would defend to a client. This was a change from the written plan, which
  had assumed a new `scope_preview` kind was needed to keep the spend visible — it is not.
  `planScope` already routes every call through `logCost`, so passing a `preview:<versionId>`
  reference keeps preview spend both visible and separable without adding provenance rows nobody
  will read.

- **One loader, two callers.** A preview that prices or projects the instrument differently from the
  interview is a preview that lies, and it would lie quietly — a topic the author saw seated in the
  panel and never sees seated in a real plan. The live trigger's inline topic query was replaced with
  the `loadTopics` every authoring route already used, and its private `loadPlanBudget` moved to
  `_lib/plan-inputs.ts` where both callers reach the same arithmetic. The session-side half
  legitimately differs and stays where it is.

- **20/min per admin.** Looser than the Routing Analyst's 8/min because the honest loop here is
  genuinely iterative — adjust criteria, re-run, see whether the plan moved. Throttling that to eight
  would make the feature annoying enough to stop using, which costs more than the calls do.

- **The snapshot reader lives with the schema.** `readProposedTopicKeys` sits in `planner.ts`, not at
  the call site, and validates with the planner's own Zod schema rather than casting. The module that
  _writes_ the snapshot is the one that should know how to read it; a reader defined anywhere else is
  a second hand-rolled description of a shape that already has one, and it drifts the moment the
  schema changes. Writing it this way immediately caught a route-test fixture that was missing a
  field the real response always carries.

## Tests

- `tests/unit/lib/app/questionnaire/scope/preview-form.test.ts` — the form offers the opening's
  questions in interview order, skips members whose question no longer exists, de-duplicates a key
  two opening topics both claim, and marks a slot as veto-watched only for `not_exists` (never for
  `exists` / `equals`, which cannot demonstrate anything by being left empty).
- `tests/integration/api/v1/app/questionnaires/topics-preview-route.test.ts` — the gates; that the
  route creates no session and updates no plan; that the planner is handed each answer paired with
  the question it answered; that an omitted fill stays omitted rather than being materialised as an
  empty one; and that `proposedKeys` / `skippedModelReason` come back.

The existing suites were the real check: `plan-scope.test.ts` and `messages-route.test.ts` still pass
against the same mocked topic query, which is what shows the trigger refactor preserved behaviour
rather than routing around it.

## What the review changed

`/code-review high` found six issues, all real, and the two mediums were the same class of mistake:
**the preview trusted a record that is wrong about the case the preview exists for.**

1. The "a limit removed it" note was gated on `source !== 'llm'` — which suppressed it for exactly
   the headline case, since a proposal the **cap** trims is stored as `source: 'llm'` with the
   rationale "nothing in the opening pointed at this area". The card showed the agent's best pick
   under a sentence telling the author their criteria were wrong. `proposedKeys` now overrides both
   the badge and the rationale.
2. The excluded list reused `SCOPE_DECISION_SOURCE_LABELS`, so an ordinary non-selection was badged
   **"Chosen by the agent"** under the heading "Not in this interview". It has its own vocabulary now.
3. `skippedModelReason` was gated on `provider === null`, so the **confidence-floor** path — a real
   call, answered, then discarded — said nothing at all. It is now named explicitly, with both
   percentages.
4. "The planner could not be reached" was also being shown when no call was attempted. `confidence`
   disambiguates: `0` is a failed call, `1` is nothing to decide.
5. The card had no `key` tied to the payload, so a verdict survived an edit-and-save and sat next to
   criteria that no longer produced it. Its two neighbours both carry that comment; this one needed
   it more, because a plan is only true of the settings that produced it.
6. Answer/fill keys were bounded by `TOPIC_KEY_MAX_LENGTH` (64) — but these are _question_ and
   _data-slot_ keys, which nothing bounds at 64. One long key would have 400'd the whole preview with
   a generic "Invalid request body".

## Still open

- **Replay over completed sessions.** Deliberately excluded above; the highest-value follow-up here.
- **The preview cannot show the extractor's own behaviour.** An author who wants to know whether
  their opening questions actually _produce_ the fills a rule depends on still has to run a real
  interview. That is a data-slot question rather than a scope one, but it is the gap this card is
  most likely to be blamed for.
