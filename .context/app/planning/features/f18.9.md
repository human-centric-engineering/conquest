# F18.9 — A questionnaire chooses which interviewers it offers

> Built-in persona mode was all-or-nothing at the library level: an admin could pin one voice, or
> hand every respondent the whole set of ten. There was no way to say "this client's respondents may
> choose, but only between The Coach and The Empath."

## What was wrong

`personaSelection` carried a pinned `defaultPersonaKey` and an `allowRespondentSwitch` flag, and the
respondent picker was fed straight from `BUILT_IN_PERSONAS`. Turning switching on therefore offered
the **entire** library — the comedian and the curmudgeon included — to a safeguarding questionnaire
that wanted two gentle voices. The only lever was switching off, which collapses the choice to one.

## What shipped

`personaSelection.availableKeys` — the admin's tick-box subset of the fixed library, on the Settings
tab's **Interviewer tone & persona** group under **"Interviewers available"**, with **Select all** /
**Deselect all**. Only ticked interviewers reach a respondent, and only a ticked one can be the
pinned default.

Two invariants carry the feature, enforced in the panel, re-checked in Zod, and re-applied on the
read path so a hand-crafted PATCH or a legacy row cannot break them:

```
at least one is always offered   → the last tick-box is disabled; "Deselect all" keeps the default
the default is always offered    → un-ticking it re-pins the first survivor
   ⇒ exactly one offered ⇒ that one IS the default, with nothing pinned
```

## Confirmed decisions

- **`[]` means "offer everything", not "offer nothing".** It's what an untouched row reads as, and
  what the panel saves once every box is ticked — so a questionnaire that offers the whole library
  keeps offering it if the library ever grows. Storing the ten concrete keys instead would silently
  freeze the offer for every questionnaire whose config was ever saved. Tested from both ends: the
  empty shape resolves to the full library, and ticking the last box normalises back to `[]`.
- **No migration.** `availableKeys` lives inside the existing `personaSelection` Json column, and
  `narrowPersonaSelection` reads a row without it as the empty "all" shape — so every live
  questionnaire behaves exactly as it did. Read-path narrowing, not a backfill.
- **"Deselect all" leaves the pinned default, it does not empty the list.** A questionnaire with no
  interviewer has no voice to run with, and a Save button that silently refuses is worse than a
  button that does the only sensible thing. The button disables itself once one is left.
- **The one-offered rule is enforced three times, deliberately.** The panel re-pins on change (so
  the admin sees it), Zod rejects a default outside `availableKeys` (so an API caller can't store
  the contradiction), and `narrowPersonaSelection` re-pins on read (so a legacy or hand-edited row
  still resolves to a real voice). Only the third is strictly load-bearing; the first two make the
  failure visible rather than silently corrected.
- **A stale respondent choice falls back to the default, it does not resurrect an un-ticked voice.**
  `resolveEffectiveTone` confines `selectedPersonaKey` to the offered set — otherwise a respondent
  who picked the comedian before the admin removed it would keep hearing it for the rest of their
  session.
- **`allowRespondentSwitch` goes inert, not false, with one interviewer offered.** The stored flag
  is left alone (un-tick a persona, tick it back, and the admin's switching preference is still
  there) but the toggle disables and `resolveSessionPersonas` refuses the picker, which already
  needed **two** personas. The Questionnaire Pack reports it as "No" for the same reason: saying
  "Yes" would describe a picker that never renders.
- **The library stays global; only the OFFER is per-version.** No admin-editable personas, no
  per-questionnaire prose. This is a visibility filter over `BUILT_IN_PERSONAS`, nothing more.

## Still open

- **No respondent-facing reason.** A respondent offered two interviewers sees two cards with no hint
  that others exist — which is the point, but it also means an admin can't explain the choice they
  curated. The picker's copy is fixed.
- **The pack lists the offered names, not the pinned one's prominence.** "Interviewers available:
  The Coach, The Empath" doesn't say which one a respondent starts on; that's the separate
  "Interviewer voice" row above it, and a reader has to join them.
- **Forking carries the offer verbatim.** `personaSelection` copies whole through
  `copy-version-graph`, so a fork inherits the tick-boxes. Right for a version fork, arguably wrong
  for a fork into a different client — unexamined.
