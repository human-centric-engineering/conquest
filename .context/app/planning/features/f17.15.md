# F17.15 — Comparability and coherence checks

> Two families of finding added to `validateConditionalTopics`. One is new work
> (**comparability** — what routing does to a scoring scale); the other is the duplicate-membership
> check listed under §10 of [`f17-followups.md`](./f17-followups.md).

## What was wrong

**Every check on the Conditional topics tab was about the topic set alone.** Orphans, criteria, rule
reachability, the budget floor — all of them ask whether the routing configuration is coherent with
itself. None of them asks what routing does to anything downstream of it.

Scoring is downstream of it, and the interaction is sharp. A scale combines items; Conditional Topics
decides which items get asked. Put together, a scale can be computed from a different subset of
itself for every respondent — and `scoreSession` returns a number either way.

F17.13 fixed the reporting half: `buildCohortDataset` computes a scale's mean and band distribution
only over respondents asked the **whole** scale, and counts the rest as `partiallyAssessed`. That is
the right behaviour, and it has a consequence nobody was told about at authoring time:

> A scale that no plan can ever cover completely is excluded for **every** respondent. The cohort
> report says "not reportable", and the author discovers it after the instrument has been fielded.

Nothing on the authoring surface could have predicted that, and the arithmetic behind it is entirely
deterministic — a scale drawing items from five conditional topics, on a version that seats at most
three, will never be wholly assessed by anyone. The information existed; nothing read it.

The duplicate-membership half is smaller and had been sitting on the follow-ups list. A question
claimed by two topics is tolerated at runtime, so it was recorded as an authoring smell — but it is
not free: costs are priced per topic and summed, so a shared member is charged once per claiming
topic and the whole time budget shifts.

## Confirmed decisions

- **The count is taken from unavoidable topics, not touched ones.** "Can a plan cover this scale?" is
  a set-cover question — an item claimed by two topics is asked if _either_ is seated — and a greedy
  cover can OVERSTATE what is needed. Overstating means telling an author "no respondent is ever
  asked all of this" when one might be, which is worse than saying nothing. So the count comes from
  items with exactly **one** owning topic: those topics are in every cover, the number is a lower
  bound, and the finding cannot cry wolf. `scale_split_by_scope` deliberately uses the wider
  touched-topic count, because its claim ("some respondents will be partial") holds either way.

- **Both limits, not just the cap.** A scale can be uncoverable because its topics outnumber
  `maxConditionalTopics`, or because they cost more seconds together than the routed allowance. Both
  are checked, the message names which one bit, and the budget test is skipped entirely when no
  budget is set — `routedAllowance` is 0 then, and testing against it would fail every scale.

- **They run while the feature is off.** Every other whole-setup check is inert until `enabled`,
  because it describes a live behaviour. These describe what would happen to a score if routing were
  turned on, which is precisely the question to answer **before** turning it on. The messages say
  "while Conditional Topics is on" so a finding read against a switched-off version is not mistaken for a
  live one.

- **`light` depth is not modelled.** A conditional topic seated as the blind-spot check contributes
  only two members, so a scale drawing on it is partially assessed even when the topic IS seated.
  Modelling it would make `scale_split_by_scope` more precise without changing the fix it points at —
  and the finding is already an understatement rather than an overstatement, which is the safe
  direction.

- **A stale scoring reference is a warning, never an error** (added under review). Deleting a
  question does not prune `AppScoringSchema.content`, so a scoring item can point at a key the
  version no longer has. Treating that as `scale_item_unowned` would block launch _and_ preview
  while pointing the admin at the Topics tab, where the key is not shown — unfixable from the
  surface the message names. The two cases are separated by the version's key inventory
  (`scale_item_stale` vs `scale_item_unowned`), and a caller supplying no inventory gets the
  warning, because an error nobody can prove is worse than a warning they can act on.

- **Rule-included topics do not count against the cap** (added under review). `applyGuardrails`
  seats hard-rule includes _before_ the cap and never truncates them, so a plan can legitimately
  exceed `maxConditionalTopics`. Counting them warned "no respondent is ever asked the whole scale"
  about a scale every respondent is asked in full — precisely the false alarm the unavoidable-count
  design exists to prevent. A topic a later rule vetoes back out counts again.

- **Only one comparability finding is an `error`, and it never blocks alone.** `scale_item_unowned`
  fires when a scale scores a key belonging to no topic — the same key that already raises
  `orphaned_questions` or `orphaned_data_slots`, both errors when enabled. So the launch gate's
  behaviour is unchanged; what is new is that the finding names the **scale** that quietly loses an
  item, which the orphan check cannot.

- **Duplicate membership is reported regardless of `enabled`, and aggregated.** Regardless, because
  the consequence — an over-priced interview — is visible in the cost panel today, whether or not
  anything is routing. Aggregated per kind, because the way this mistake actually happens is someone
  duplicating a topic, and forty findings for one act is a surface an author stops reading.

## What changed

| Path                                                  | Change                                                                           |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| `lib/app/questionnaire/scope/comparability.ts`        | **New.** The scale-reach analysis and its three findings                         |
| `lib/app/questionnaire/scope/validate.ts`             | Optional `scoring` + `seconds.byTopicKey` inputs; the duplicate-membership check |
| `lib/app/questionnaire/scoring/compute.ts`            | **New** `loadScoringSchemaContent` — one narrowed read, two callers              |
| `.../[vid]/topics/route.ts`                           | Loads the schema and passes per-topic seconds, so the tab shows the findings     |
| `app/api/v1/app/questionnaires/_lib/launchability.ts` | Same inputs, so the launch gate and the tab cannot disagree                      |

No migration, no new setting, no UI change: `scope-issues.tsx` renders findings by severity and
message, so new codes surface on the Conditional topics tab without touching it.
