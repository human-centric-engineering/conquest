# F18.5 — Per-question fidelity in the exports

## What was wrong

`InstrumentQuestion` carried `number`, `key`, `prompt`, `type`, `required`, `weight`, `guidelines`,
`tags`, `options` and `constraint` — and dropped `q.fidelity`, which was sitting on the source row
and already selected by `getVersionGraph`.

So the Questionnaire Pack described an instrument without recording which of its questions **are**
instruments. A reader given a prompt could not tell a question that will be put word for word, with
its scale read out, from one the interviewer may never ask aloud at all. Both are in the document;
only one of them is a script.

This was an omission rather than a decision: the feature's own carriage table (in
`question-fidelity.md`) lists fork, definition import/export and the settings-registry summary, and
its "Pack / audit summary" row pointed only at the **version-level gate** — which is exactly the
blind spot that let the per-question dial slip out of both exports.

## What shipped

`InstrumentQuestion.fidelity: QuestionFidelityLevel | null`, resolved once per question inside
`buildInstrumentModel`, and printed by all six renderers beside the type and the required flag.

The pack and the brand-free instrument export share this one model — deliberately, so "the two
exports can never render it differently" — so this is one field and six one-line changes:
`build-instrument-text.ts`, `build-instrument-csv.ts`, `build-pack-markdown.ts`,
`build-pack-csv.ts`, and the two duplicated `QuestionBlock` components in
`instrument-pdf-document.tsx` and `pack-pdf-document.tsx`.

## Confirmed decisions

- **`null` when the version-level gate is off, and the renderers then print nothing.** With the gate
  off every question resolves to `balanced`, so a uniform column would be noise on the large
  majority of questionnaires that never opted in. A test per renderer pins that a gate-off export
  contains no mention of fidelity at all.
- **Resolved through `resolveQuestionFidelity`, never read off `q.fidelity`.** This is the
  anti-pattern the feature doc names: an admin may pre-set sliders on the Structure editor before
  switching the feature on, and reading the column raw would report a dial that is not in force. A
  test pins that case specifically.
- **The two CSV writers keep the column either way** and leave the cell empty. A stable shape is
  what a spreadsheet consumer needs; a column that appears and disappears between exports is worse
  than an empty one. Both files maintain their header array and their cell array separately, so the
  instrument CSV also gained a test that every row is the same width as the header.
- **No new `PackInclude` flag.** Fidelity is a property of a question, not a section of the pack, so
  it rides the existing `questions` toggle.
- **Gate read once per model, not once per question** — it is version-level, and a large instrument
  would otherwise resolve the same answer several hundred times.
- **The two PDF `QuestionBlock`s were left duplicated.** They are byte-identical and deduping them
  is a real refactor of two documents' component trees; out of scope here, and noted rather than
  half-done.

## A note on the test fixtures

Adding a required field to `InstrumentQuestion` broke six fixture builders at compile time, which is
the type system working: every one of them had to state what fidelity it meant. They all now say
`fidelity: null` — the gate-off default, which is what those tests were already implicitly
asserting. Three existing tests pinned the CSV header as twelve named columns; those move to
thirteen.
