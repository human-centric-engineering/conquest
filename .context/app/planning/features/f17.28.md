# F17.28 — The master switch on the Settings tab

## What was wrong

F17.25 moved the master switch out of the tenth card and into a status header, because "is this
even on?" is the first question an admin arrives at the Adaptive scope tab with.

The same question gets asked from the other end. An admin auditing how a version behaves at run
time opens the **Settings** tab — every other run-time switch is there, grouped, with a conflict
banner across the top. Adaptive Scope's was not. The one setting that decides whether half an
instrument gets asked was two tabs away from the place that lists what the instrument does.

## What shipped

An **Adaptive scope** group on the Settings tab: the switch in the group header (the same
`On`/`Off` header-switch pattern the Progress-milestones group uses), a sentence saying what the
current position means, an ⓘ explaining what the feature is for, and a button through to the
Adaptive scope tab.

Only the switch is mirrored. Topics, criteria, the budget and the planner's settings stay on the
Adaptive scope tab, where the surface that explains them is.

## Confirmed decisions

- **The key is sent only when this editor changed it.** Every other field on the Settings tab has
  exactly one editor, so sending it unconditionally can only rewrite it with itself. This one has
  two. A Settings tab loaded before someone turned scope on elsewhere, then saved for an unrelated
  reason, would silently turn it back off. The PATCH is partial by contract, so omitting the key is
  precisely "I did not touch this" — and that is the whole safety argument for mirroring the switch
  at all.
- **This does not reopen F17.25's two-writer race.** That race was two controls in one render,
  decided by whichever rendered last. These are two tabs, each seeded from the server's value and
  resynced from it on every refetch, with one of them declining to write unless asked.
- **No route change.** `…/config` has accepted `adaptiveScope` since the settings export/import
  round-trip needed it, merging through `patchAdaptiveScopeSettings` — the same helper the Topics
  tab's own PATCH uses — inside the same fork decision. An edit to a launched version forks once.
- **The conflict checks read the editor's live switch, not the saved config.** Turning scope on
  should raise `adaptive-scope-targeted-opening` and its two siblings while the admin is still
  deciding, not after a save and a reload. The opening-probe inputs to those checks have no editor
  on this tab and stay read from the saved config.
- **They stay anchored to `interviewer-strategy`.** The switch is now on the same tab as those
  findings, but turning the feature off is not the fix any of the three is asking for.
- **The body copy admits the inert case.** "A topic with no condition on it is still asked of
  everyone — so if nothing on the Adaptive scope tab has a condition yet, everyone is asked
  everything." Turning the switch on from a tab that cannot see the topic set otherwise looks like
  it did nothing.

## What changed

| Path                                                  | Change                                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `admin/questionnaires/config-editor.tsx`              | New `adaptive-scope` group; `adaptiveScopeEnabled` state + resync; conditional PATCH key |
| `lib/app/questionnaire/authoring/config-conflicts.ts` | Comment only — the anchoring rationale, which claimed the switch was not on this tab     |

No API change, no migration, no new component: the group is built from the same `SettingsGroup`,
`Switch` and `FieldHelp` primitives as its neighbours.

## Tests

`config-editor.test.tsx` — seven added:

- the group renders, with the link resolving to `…/v/ver-1/topics`
- the switch reflects the stored `adaptiveScope.enabled`
- the state sentence changes with the switch (matched on the sentence, not the group description,
  which deliberately says something similar)
- toggling on sends `adaptiveScope: { enabled: true }`; toggling off sends `false`
- **an untouched switch is absent from the body entirely**, asserted on a save that changed
  something else — the drift guard, and the one that fails if the send is made unconditional
- a new `config` prop resyncs the switch

117 pass in that file; 7,141 across 447 files in the questionnaire component, lib and admin-page
suites.
