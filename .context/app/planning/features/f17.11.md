# F17.11 — Open-vs-close reconciliation (C9 / G05)

> Closes §4 of [`f17-followups.md`](./f17-followups.md). Capability C9 of the pilot client research notes,
> guardrail G05 of its workbook, which is unusually direct about why it matters:
> _"Disagreement between what they say they need and what the scores show is the most valuable
> output the tool produces."_

## The question that shaped it

Asked whether this was really code, or "something we do via the custom respondent report engine" —
the admin already has free-text `instructions` / `structure` / `backgroundContext` fields, so why not
write "compare their goal against their scores" into one of them?

The output side genuinely **is** the report engine, and that is where this shipped: a prompt block
beside `notAssessedRules`, output into the existing `sections[]`, no new pipeline, and the new
settings sit on `generation` alongside its siblings. What config could not reach was the **input**
side, in two places verified before building:

- The user message is `buildAnswerTranscript` — answered slots, flattened, **`slotKey` dropped**. The
  goal answer and the closing ask arrive as two undifferentiated lines among seventy.
- **Scores were absent entirely.** No respondent-report code read `AppRespondentScore` or called
  `scoreSessions`. Told to compare, the writer would re-derive an impression from raw likert values
  in the transcript — blind to reverse-scored items, weights, band cutoffs and C8's normalisation,
  which is precisely what scoring exists as a separate deterministic layer to avoid.

So the feature is three inputs the engine did not have, plus one rules block. Config alone yields an
impression of reconciliation; it cannot hold a computed number against a stated sentence, because the
number never arrives.

## Confirmed decisions

- **Explicit refs, with phase-derived defaults.** `statedGoalRefs` / `askedForRefs` name question or
  data-slot keys; empty means derive from Adaptive Scope topic phases. Explicit-only was rejected
  because a feature nobody configures produces nothing; phase-only was rejected because it cannot
  tell "what do you want to achieve?" from any other opening free-text question. Resolved **per end**,
  so an instrument can name its goal question precisely and let the close derive.

- **A configured ref that matches nothing does NOT fall back to the phase derivation.** Falling back
  would silently substitute the whole opening phase for the one key an admin named — a comparison
  they did not ask for and have no way to see is wrong. It yields nothing, and `goalSource` records
  `configured` so the record is honest about what was attempted.

- **Derivation reads free text only.** A likert under an opening topic is a rating, not a statement
  of what someone needs. Quoting "4" as their stated goal would be worse than saying nothing.

- **Scores computed fresh, not read from `AppRespondentScore`.** That table is written only when a
  scoring schema is saved, so for most sessions the row is absent or stale. A report that
  contradicts a respondent using an out-of-date number is worse than one that does not contradict
  them. `buildScoringInputs` + `scoreSessions` is the same path the cohort report takes, so the two
  surfaces cannot disagree. Wrapped in try/catch: a reconciliation block is an enhancement, and a
  scoring schema that will not load must not cost the respondent their whole report.

- **The living paraphrase wins over the stored value.** The paraphrase is the sentence the panel
  showed the respondent as theirs; quoting anything else would have the report arguing with words it
  told them were their own.

- **The instruction is deliberately one-sided — and bounded.** Every other rule in the writer's
  prompt pushes toward caution (ground it, do not infer, say less where answers are thin), and a
  writer under that much restraint reconciles by finding agreement. So it says _SAY SO PLAINLY_. It
  equally forbids manufacturing a disagreement, forbids inventing a score where no schema exists,
  marks a partially-assessed scale as a weaker basis for contradicting someone, and states that an
  area nobody assessed has no score and its absence is **not** a poor result — the specific slip a
  comparison invites.

- **Seated after the scope blocks.** The writer must read `notAssessedRules` before being asked to
  reconcile, or it will read a missing measurement as a bad one.

- **Output into the existing `sections[]`.** A new key on `RespondentReportContent` would mean
  touching validation, `report-body.tsx` and `session-pdf-document.tsx` for a block whose shape is
  prose either way.

**Tests** — new `reconciliation.test.ts` (16) covers both identification paths, the deliberate
no-fallback, free-text-only derivation, the paraphrase preference, and every guard in the prompt
block. `generate.test.ts` gains 7 wiring tests (the real risk is the block silently not reaching the
prompt), including real scores reaching it and scoring failure not failing the report.
`settings.test.ts` covers ref narrowing.

**One gap the tests caught:** `config-schema.ts`'s definition-export Zod is `.strict()`, so a version
with the new setting could not be re-imported. Fixed in the same change.

## Deliberately not built

- **The config preview does not render the block.** A synthesised respondent has no typed answers to
  score — `PreviewStructure` carries no question types and `SampleReportInputs` exposes no per-key
  answers — so a preview could only show the statements half, and would print "no scores were
  computed" for a version that _does_ have a schema. That misdescribes the admin's own
  configuration, which is worse than showing nothing. Making it faithful means widening
  `PreviewStructure`, `SampleReportInputs` and the preview route.
- **`generateRunReport` (F15.4b) does not pass it.** A journey report spans legs whose scores do not
  compose; it already drops `notAssessed` for related reasons.
