# F17.26 — Three sub-tabs: Topics · Rules & limits · Check

Phase 3 of the tab simplification.

## What was wrong

~5,700 lines across 18 components in one unbroken vertical stack, **ordered by the runtime
pipeline** — proposer, verification, then the topic list an admin edits most, last. Nothing about
that order helps someone doing the job; it helps someone reading the engine.

## What shipped

Three tabs named after the job, not the machinery:

| Tab                | What is on it                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| **Topics**         | Suggest topics from your document · the coherence detail · the topic list and editor                         |
| **Rules & limits** | Hard rules, how many, how long, the blind-spot check, fallbacks, what the respondent is told, extra guidance |
| **Check**          | Preview the decision · what happened in real interviews · AI review of this setup                            |

`ScopeExplainer`'s four steps are now deep-links: steps 1–2 → Topics, step 3 → Rules & limits.
Step 4 stays plain text — it is the header switch a few pixels above, so a jump would be theatre.
That mapping is the strongest argument the split was worth doing: the sequence this panel has
always described finally has somewhere to point.

## Confirmed decisions

- **A local history-based hook, not `useUrlTabs`.** The platform hooks write with `router.replace`,
  which on this route is a full RSC round-trip — `next.config.js` sets no `staleTimes`, so every
  tab click would re-run `loadKeyInventory`, `estimateTopicCosts`, `validateConditionalTopics` and
  `loadTopicDraft` to render markup that did not change. Worse, a `loading.tsx` exists at the
  parent segment: a query-only navigation that fell into that Suspense fallback would unmount the
  subtree and with it everything the split exists to preserve. `useScopeTabs` writes with
  `history.replaceState`; Next patches the history methods, but a `replaceState` that changes only
  the query does not re-run this route's server components, which is the property being relied on.
  Same `?tab=` addressability, no refetch. The **initial** value is read through
  `useSearchParams()` rather than `window.location` — see below.
- **Beside its consumer, not in `lib/`.** Adding a `navigate` option to `lib/hooks/use-url-tabs.ts`
  would be a fork-and-edit that re-conflicts on every upstream sync, for a behaviour only this
  route needs — and `lib/app/**` is required to stay framework-agnostic (ESLint enforces it), so a
  hook reading `useSearchParams` cannot live there either. It sits in the components folder next to
  `authoring-mutate.ts`, which is a non-component module there for the same reason.
- **`replaceState`, not `pushState`.** A tab is a view of one page, not a place in history; pushing
  would make Back walk the admin through every tab they looked at.
- **`forceMount` on all three panels.** Radix unmounts an inactive panel, and five things here hold
  state that must survive a switch — most sharply the analyst's in-flight SSE run, which has no
  `AbortController`, so unmounting does not stop the paid model call, it only orphans the result.
- **`topics-panel.tsx` stays the shell** rather than being demoted under a new
  `conditional-topics-view.tsx`. The plan called for the split, but the panel already _is_ the shell —
  it owns every piece of cross-cutting state (`busy`, `error`, `forkNotice`, the three nonce
  handoffs, the mutation runner) and that state has to live above `<Tabs>` either way. Extracting
  it would have moved ~40 shell tests to a new file to prove the same behaviours about the same
  code. The Rules and Check bodies are thin enough to be inline; only Topics is substantial.
- **Empty states on the Check tab.** `PlanPreviewCard` and `RoutingQualityCard` used to return
  `null`. Fine as two of a dozen cards on a long page; on a tab of their own, silence reads as a
  page that failed to load. Each names the one thing that would fill it.
- **The issue strip picks the tab, and the registry has a FALLBACK rather than a
  `Record<Code, Tab>`.** There are 23 codes and more will come; a total record would make every new
  finding a compile error in a file its author has no reason to open. A source-reading test asserts
  every code the validator can emit is either mapped or deliberately on the default.

## What code review caught

Three things, all found after the phase was written and all now fixed and pinned by tests:

- **The routing map stopped reaching the editor.** Its trigger sits above the tabs and is reachable
  from all three, but `onEditTopic` only set `focusTopic` — it never switched to Topics, which the
  new `active` gate now requires. From Rules & limits, "Edit this topic" did nothing visible _and_
  left a request that fired later as an unexplained jump. Both callers now go through one
  `openTopic`, because two callers doing this by hand is exactly how the map's version lost the
  switch when the tabs arrived.
- **The issue strip queued a topic focus for findings fixed on the Rules tab.**
  `always_topic_named_as_choice` and `rule_names_always_topic` both carry a `topicKey`, but what is
  wrong is the rule or the list pointing _at_ that topic. Same parked-request symptom.
- **A hydration mismatch on every `?tab=` deep link.** The initial value came from
  `window.location`, which resolves to the default on the server and to the real tab on the client
  — and this panel _is_ server-rendered. Radix then emitted different `data-state` / `hidden` /
  `aria-selected` between the two passes, on precisely the shareable link the hook exists to serve.
  Now read through `useSearchParams()`. The static-generation cost that hook carries does not apply
  here: the route is dynamic, so it is never prerendered.

Two smaller ones: the strip's React key (`code` + `topicKey`) is not unique — both producers above
can emit the same pair twice — and its overflow line said "…and N more **below**" when the full
list had moved onto the Topics tab, so it was false on two of the three tabs.

## Tests

- `conditional-topics-tabs.test.ts` (**new**) — labels and hints for every tab, the `?tab=` narrow,
  issue→tab routing, and a `leak-guard`-style pass over `validate.ts` asserting no code is
  accidentally unmapped
- `topics-panel.test.tsx` — opens on Topics, honours `?tab=`, falls back on nonsense, writes the
  URL **without** a router navigation, keeps hidden panels mounted, tells the editor when its tab
  is not showing, and routes a rule-shaped finding to Rules & limits
- `plan-preview-card.test.tsx` / `routing-quality-card.test.tsx` — the empty states replace the
  old "renders nothing" assertions, and the quality card still makes no request

## One thing this found

`history.replaceState` is global, so jsdom keeps one URL per test file. A tab click in one test
leaked its `?tab=` into every test after it, and the fork-redirect assertion started seeing a query
it never set. The panel suite now resets the URL in `beforeEach` — and the query-carrying test from
F17.24 was rewritten to drive the real tab control rather than stubbing `window.location`, so it
exercises the path production uses.
