# F17.35 — A question that is added must belong to a topic

> Found while checking whether the design judges understand Conditional Topics
> ([`f17.34.md`](./f17.34.md)). They did not — and the same investigation showed that applying one of
> their suggestions could silently make a question unaskable.

## What was wrong

With Conditional Topics on, `isQuestionInScope` is `!scope.active || scope.questionKeys.has(key)`
(`scope/resolve.ts`), so **a question belonging to no topic is never asked**. `scope/types.ts`
already named that as the failure that matters: an orphaned question "can never be asked, and nothing
else in the system would ever tell you."

Topic membership was written at ingest and by the Topics tab, and by nothing else. Every other way a
question comes into existence created one nothing claimed:

| Path                                            | Was                                                                    |
| ----------------------------------------------- | ---------------------------------------------------------------------- |
| `evaluation-apply.ts` `applyAddQuestion`        | creates a slot, no membership                                          |
| `evaluation-apply.ts` `split_question`          | creates the second half, no membership                                 |
| `sections/[sectionId]/questions/route.ts`       | manual add — no mention of `topic` in the file                         |
| `extraction-review-routes.ts` `create-question` | no membership                                                          |
| `import-definition.ts`                          | imports the file's own topics; a file with none imports fully orphaned |

`seedTopicsForVersion` would not have helped even if it had been called: it treats a section as
covered when _any_ of its questions is claimed, so a new question in an existing section stays
orphaned forever.

Deletion was the more dangerous half. `delete_question` (and the manual delete, and extraction
review's) removed the slot and left a dead key in every topic's `members`. That is not a crash —
`resolveScope` skips a key resolving to no question — but **`empty_topic` counts RAW member keys**,
so a conditional topic whose members have all been deleted read as non-empty, passed every coherence
check, and resolved to nothing at runtime.

And the launch gate only exists once the feature is on (`launch/readiness.ts`,
`_lib/launchability.ts`), so with it off — the default — orphans accumulated silently and became
blocking the moment someone flipped the switch.

## The question this raised, and how it was answered

**Should membership be inherited automatically, or confirmed?** Automatically. The orphan is a silent
failure the codebase itself calls the worst outcome, and a confirmation step is a decision the admin
has no basis to reason about ([[prefer-auto-detect-over-admin-toggles]]). Where inference declines to
guess, the outcome panel says so rather than the launch gate finding out weeks later.

## What shipped

### Phase 1 — the banner, first

`getVersionTopicsCached` and `TopicsPayload.coverage.uncoveredQuestions` already existed, computed by
the topics GET through `uncoveredQuestionKeys` — the same function `orphaned_questions` uses,
including its "stay silent when the version has no topics" suppression. So the review queue's banner
is a page prop plus a presentational banner, touching no write path.

It landed **before** the write changes on purpose: it makes the orphans that already exist visible on
the dev DB, which is the before/after for everything below.

### Phase 2 — three pure helpers

`withTopicQuestionKey` / `withoutTopicQuestionKey` (`scope/types.ts`, beside the bound they respect)
and `inheritTopicForQuestion` (`scope/seed.ts`, beside `planDataSlotAttachment`).

Two decisions worth keeping:

- **Same object identity on a no-op.** Load-bearing rather than tidy: it lets a caller walking every
  topic write `if (next === topic.members) continue` and issue one UPDATE instead of one per topic
  across a 30-topic version. `attachDataSlotsForVersion` already skips its no-ops the same way.
- **`inheritTopicForQuestion` lives next to `planDataSlotAttachment`, not in `types.ts`.** It _is_
  that function with a different input, and the whole point is one definition of "which topic does
  this belong to" — three modules apart, they drift. Same majority, same ordinal-ascending strict
  `n > best`, so ties break to the lower ordinal. A tie is the _ordinary_ case (a section split
  across two topics), so bailing on it would orphan exactly the questions this exists to place;
  `null` is reserved for no topic owning any sibling.

### Phase 3 — topic-safe apply

`split_question` copies the parent's membership onto the new half — it already inherits type, config,
`required`, `weight`, `fidelity` and guidelines for the same reason. `delete_question` prunes the key
from every topic. `add_question` inherits from the target section's questions, using the
**collision-suffixed key actually written**, not the judge's proposed one.

Four constraints, each with a real failure behind it:

1. **Read and write on `editVersionId`, never `scoped.id`.** `scoped` is in hand and is the natural
   thing to reach for — and writing there mutates a _launched_ version's topic rows.
   `copy-version-graph.ts` copies topics 1:1 including `members`, and membership is keys not row ids,
   so inheritance resolves identically on the fork.
2. **Inside the transaction** that already does the slot write and the finding stamp.
3. **Every write is `updateMany`, never `update`.** The Topics tab saves with `replaceTopics`, a
   `deleteMany` + `createMany`, so a concurrent save can remove the row between the read and the
   write. With `update` that is a P2025 — and a thrown query inside a Postgres transaction aborts it,
   so the catch does not save us: the finding stamp then fails and the question write rolls back too.
   Losing a question because its membership lost a race is strictly worse than the orphan. A zero-row
   `updateMany` is not an error, so the race degrades to today's behaviour and the banner reports it.
4. **`source` is never stamped.** `scope-evaluation-apply.ts` stamps `source: 'manual'`, so copying
   it looked right. It is not: `isEligibleForScopeCandidacy` and `launchability.ts` both gate on
   `source: { not: 'seeded' }`, so flipping a seeded topic because a question landed in it would
   **silently suppress the Routing Analyst candidacy check** for that version. There the admin
   approved a change to a topic; here, to a question.

The emptied topic is deliberately **left in place**: it still carries a label, a phase and criteria an
author wrote, and `empty_topic` is the warning that says it now asks nothing — pruning is what makes
that warning fire. `reconcileTopicsForVersion` does delete such topics, but only on a wholesale
structure rewrite, where the subject really is gone.

### Phase 4 — the light-topic delete guard

`delete_question` is refused when its target sits in a `light` topic that would fall below
`LIGHT_DEPTH_MEMBER_COUNT`. A light topic contributes only its two highest-weight members — it is the
blind-spot check, whose whole value is being a sample of something — so taking one from a topic
already at that floor leaves it reporting on half of what it claims.

**Code, not rubric.** The judge cannot see depth or member counts, and prompt guidance is persuasion;
`applyFinding` already treats every op as an accelerator rather than a trust boundary, so this is the
layer that can hold the line. It runs in `validateOpAgainst`, before the fork, so a doomed op never
strands an orphan draft.

`topic_sample_too_small` is its own `UnapplicableReason` rather than another `op_invalid`, because the
two want opposite responses: `op_invalid` means the edit no longer fits and the reviewer should
re-run; this means the edit fits and would quietly degrade a check, and the reviewer should narrow the
question instead. One message cannot say both. The finding stays accepted, so fixing the topic and
applying again picks it up.

### Phase 5 — the same seam everywhere else

The three helpers moved to `_lib/topic-membership.ts` — one implementation, four callers — and the
manual question routes, extraction review (`create-question`, `delete-question`, `delete-section`)
and definition import all use it. `create-section` on revert is the one case inheritance cannot
serve, because the section's questions have no siblings in an existing topic; that gets
`seedTopicsForVersion`, gated on the version already having topics so a revert never resurrects a
topic set an admin deliberately deleted.

## A green bar the tests were hiding

Writing the manual-route test found that the existing prisma mock had no
`appQuestionnaireTopic.findMany` — so the `.catch()` that keeps inheritance best-effort was
swallowing a `TypeError`, and the suite would have gone green over a feature that did nothing. The
mock now carries the delegate and the tests assert the write.

## Deliberately not done

- **No optimistic locking on `members`.** It is a plain `Json` column with no version stamp, so a
  concurrent Topics-tab save can still overwrite a membership written here. An etag on a JSON blob is
  a lot of machinery for a race between one admin's two open tabs, and the banner reports the outcome.
- **No change to `seedTopicsForVersion`'s section-level "already covered" test.** It is correct for
  seeding a fresh graph; the fix for incremental adds is the inheritance helper, not loosening the
  seeder.
- **Not the pattern at `evaluation-run-detail.tsx`'s unawaited `versionDataSlotsAssign` follow-up.**
  A correctness fix cannot depend on a browser request the user can navigate away from, so topic
  membership gets a server-side transactional write where data slots got fire-and-forget.
