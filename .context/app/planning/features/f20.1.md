# F20.1 — Where a turn's time goes

> A respondent waits through four to six sequential model calls before the first token of a reply
> appears. Nothing could say which of them the wait actually was.

## What was wrong

Diagnostics already reported a turn's **end-to-end** wall-clock — average and p95, from the
`durationMs` column. That says a turn took 5 seconds. It does not say whether those 5 seconds were
the answer extractor, the seriousness judge, the phraser, or the database.

Without that split, every latency idea was a guess. "Parallelise the classifiers" and "the overhead
is all Postgres" were equally consistent with the evidence, and they imply opposite work.

## What it does

`getStageLatency(sessionIds, from, to)` splits the window's turn wall-clock by pipeline stage, and
`DiagnosticsView` renders it as a **Where the time goes** panel above the invitation table.

Per stage: how many calls ran, the average and p95 of a single call, and — the number to compare
rows on — **what the stage adds to an average turn**. Plus a final row, _Not in a model call_: the
wall-clock left over once every call is subtracted, which is the database, embedding and persistence.

## The thing worth knowing

**It needed no migration and captures nothing new.** Every turn already persists an
`AgentCallTrace[]` on `inspectorCalls` — label, latency, tokens, cost — for _every_ session, not
just previews; only the SSE emission of that trace to the admin drawer is preview-gated. The data
had been on disk since F8.5. Two raw queries unnesting a jsonb array were the whole feature.

Three decisions inside it that are not obvious from the code:

- **Group by the call's own `label`, not a stage enum.** A hard-coded enum is a second list to keep
  in sync, and it fails closed — a stage added later would be silently invisible in the surface
  meant to find it. Grouping by the recorded label means a new call appears by itself.
- **Both queries are restricted to turns with a `durationMs`.** The stage totals and the residual
  then describe exactly the same set of turns, so "per turn" divides by the denominator it claims
  to. Turns predating the telemetry columns have neither a duration nor calls and drop out of both.
- **`perTurnMs` divides by turns, not by calls.** A stage that runs on half the turns costs the
  conversation half its own average, and that is the figure a decision should be made on. Both are
  shown, so the gap between them is visible rather than hidden.

## What the first reading said

Run over the dev database — **10 turns from one data-slot-mode questionnaire, a small sample whose
shape is indicative rather than authoritative**. Average turn 5.1 s end to end:

| Stage                      | Per turn     | Avg call |
| -------------------------- | ------------ | -------- |
| Interviewer phrasing       | **2,334 ms** | 2,334 ms |
| Answer extraction          | 879 ms       | 2,196 ms |
| Adaptive data-slot ranking | 598 ms       | 1,494 ms |
| Data-slot selector         | 500 ms       | 1,249 ms |
| Seriousness judge          | 371 ms       | 1,237 ms |
| Sensitivity detection      | 279 ms       | 696 ms   |
| **Not in a model call**    | **133 ms**   | —        |

The residual is **2.6%**. The turn is model-bound essentially end to end, which is the finding the
rest of P20 was made contingent on — and it reorders the plan: phrasing alone is 46% of the turn,
so the prompt-cache work aimed at time-to-first-token matters more than its position suggested.

## The one caveat that will age

**The residual stops being a measurement once stages overlap.** It is `wall-clock − Σ call latency`,
which is only meaningful because every call in a turn currently runs strictly one after another.
P20 Phase 3 deliberately overlaps three of them; from then on the sum can exceed the wall-clock and
the residual clamps to 0. That still reads honestly — the turn was model-bound throughout — but it
becomes a floor, not an overhead figure. Written on the type, in the domain doc, and pinned by a
test that feeds it an over-long sum and asserts the clamp.

## Tests

The pre-existing test mocked `$queryRawUnsafe` with one flat `mockResolvedValue`. With three raw
queries in play that hands all three the same fixture, so each test would silently exercise
whichever query happened to tolerate it. The mock now routes by a marker unique to each SQL — which
is why the existing tests were touched.

New coverage: grouping and the per-turn/per-call distinction; the residual; the clamp when summed
latency exceeds wall-clock; the empty short-circuit issuing no query at all; a null label dropped
rather than rendered as an unnamed stage; `residualShare` null (nothing measured) rather than 0.

The panel has its own six tests, aimed at the two ways it could mislead rather than at its markup:
rendering the per-call average where the per-turn figure belongs (which points latency work at the
wrong stage), and dropping the residual row when overhead is small (which hides the one reading that
would send the plan back). Both were checked by mutation — reverting either behaviour fails the
suite.

The SQL itself is invisible to a mocked-Prisma unit test, so it was additionally run against the
real dev database — which is where the reading above came from.
