# F20.2 — The honest wait

> Four to six sequential model calls, and one static `Thinking…` over all of them. A normal turn and
> a stuck turn looked exactly the same.

## What was wrong

[`F20.1`](./f20.1.md) measured it: an average turn is ~5 seconds, model-bound essentially end to end.
For all of that the respondent saw one unchanging label — no account of what was happening, no proof
the request was still alive.

Two things were already in place and unused. The platform's `ChatEvent` has carried a `status`
variant all along, and the respondent client (`use-questionnaire-session-stream.ts`) simply dropped
it — `parseSessionEvent` did not even narrow it. The pipe was built. Nothing was pushed through it.

## What it does

Four stage labels, streamed as the turn crosses each boundary, plus an elapsed clock once the wait
is long enough to need one.

| Stage       | Covers                                               | On screen                                  |
| ----------- | ---------------------------------------------------- | ------------------------------------------ |
| `reading`   | extraction, sensitivity detection, seriousness judge | Reading your answer…                       |
| `checking`  | contradiction detect + refine                        | Checking that against what you've told me… |
| `choosing`  | next-question / next-slot selection                  | Choosing what to ask next…                 |
| `composing` | the phrasing stream, until its first token           | Writing the next question…                 |

## Getting it out of a pure orchestrator

`runTurn`'s contract is that all I/O belongs to the route and the core only decides. Emitting frames
mid-run had to not break that, and the route being an async generator meant a plain callback could
not `yield`. Hence two pieces:

- An optional **`StageEmitter`** on `runTurn` / `runDataSlotTurn` — synchronous, side-effect-only,
  no I/O, cannot fail the turn. A test asserts the `TurnResult` is byte-identical with and without
  one. Omitting it is always valid, which is why every pre-existing caller and test was untouched.
- A **channel**: `emit` fills a queue, `drain` lets the route pull from it concurrently with the
  pipeline promise. `streamStageStatus` re-throws the pipeline's rejection unchanged, so the route's
  catch — the path that persists the failure and unlocks the surface for a retry — still works.

`composing` is emitted by the route, not the core, because composing is the route's own work.

## The decisions worth keeping

- **Coarser than the pipeline, on purpose.** `reading` is three model calls under one sentence.
  Three labels would flicker past in under two seconds, and telling a respondent their answer is
  being assessed for sincerity is true but is not a thing to say out loud.
- **A stage never reached is never announced.** A kickoff has no message, so it opens at `checking`
  — "Reading your answer…" would be the first thing a respondent ever saw, and false. An offer turn
  skips `choosing`. An abandoning abuse turn stops at `reading`. A replayed idempotent retry emits
  none at all, because it does no work.
- **App-owned indicator, not a prop on the platform's.** `ThinkingIndicator` is Sunrise's (verified
  against `upstream/main` at `226998ea6`); a prop there would need re-applying on every sync. The
  dots are re-implemented in `TurnProgress` for a few lines. The platform component still serves the
  opening choreography's scripted ~1s beat, which is not a server wait — a clock on it would be
  nonsense.
- **The clock waits 4s.** Below that it is clutter that makes a normal wait look like a problem.

## The one that took two tries: exactly one live region

The composer already had an `sr-only` `role="status"` cue, because a disabled field's placeholder is
not announced. The first cut pointed it at the live stage label — so both it and the new
`TurnProgress` were polite live regions announcing the same sentence, **twice per stage, eight times
across a five-second wait**, drowning the reply that followed.

Resolved by splitting what is _shown_ from what is _announced_: the composer's placeholder shows the
live label silently (a placeholder is not announced, so it may change freely), while its
`role="status"` line keeps the stable `composerHint`. `TurnProgress` is the single live region on
the stage, and its ticking clock is `aria-hidden` — a new number read out every second is a barrier,
not reassurance.

## Two claims that turned out to be false, and were removed

Both found by mutating the code and watching the tests stay green.

- **The `Promise.race` in `drain` is defensive, not load-bearing.** Its comment said that without it
  a pipeline emitting nothing would hang forever. Removing it kept every test green — because `wake`
  is assigned synchronously inside the promise executor, with no `await` between it and the `settled`
  check, so there is no window to lose. The comment now says what is actually true: it is insurance
  against a future edit that _introduces_ such a window.
- **The stage label was cleared twice.** A clear on send plus a clear in the teardown. Removing the
  send-path clear broke nothing, because the teardown runs on every exit and therefore already
  guarantees the next turn starts empty. Deleted rather than kept with a comment overclaiming its
  purpose. The teardown clear was itself uncovered until a test was added for the case that actually
  needs it — a stage arriving and _then_ the connection dropping with no content, which is the only
  path the first-delta clear cannot reach.

## Tests

51 added across six levels, chosen so the feature is pinned where it could actually break:

- **The channel (12).** Its worst failure is a _hang_, not a wrong answer — a drain waiting on a
  resolver nobody will call means a stream that never closes and a composer locked for the rest of
  the session. Every test carries a real timeout so such a regression fails rather than hangs.
  Covers ordering, a pipeline that emits nothing, emit-and-settle in the same tick, de-dup, error
  propagation, per-turn isolation, and that stages arrive _while_ the pipeline runs rather than
  batched at the end — the last being the difference between this feature and the static label it
  replaced.
- **The orchestrator (9).** Stage order, no `reading` on a kickoff, stopping at the abuse abandon,
  no `choosing` on an offer turn, and the purity assertion — repeated against the data-slot pipeline,
  because a respondent cannot tell which one their questionnaire runs and the account of the wait
  must not differ between them.
- **The route (4).** The end-to-end proof: real orchestrator, real channel, real SSE framing. All
  four labels in order and all before the first content frame; the kickoff omission; `error` + `done`
  still terminal when the pipeline throws mid-stage; and no frames at all on an idempotent replay.
- **The hook (5).** Observing a mid-turn label needed two attempts — recording renders showed
  nothing, because draining a whole stream inside one `act` batches every update into a single
  render; and gating frames failed too until the `act` scopes stopped nesting. The working shape is
  documented on the helper so the next person does not repeat it.
- **The component (9)** and **the parser (3).**
- **The two formatters (17).** Added because `check:missing-tests` named them: `formatElapsed` is
  now shared by three surfaces and was lifted out of one precisely so they could not drift, and
  `formatShare` carries the em-dash-vs-zero distinction the residual reading depends on. The gate's
  one remaining finding is `diagnostics-view.tsx` — a large pre-existing server component this only
  touched to mount a panel that has its own tests. Left as it was.

Mutation-checked: the per-turn figure, the residual row, the first-delta clear, and the teardown
clear each fail the suite when reverted.
