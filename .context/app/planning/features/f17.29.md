# F17.29 — Conditional Topics

One branch, six commits, two jobs: rename the feature, then close what
[`f17-followups.md`](./f17-followups.md) still had open.

---

## 1. The rename

**Adaptive Scope** described the mechanism — a scope that adapts. What an admin actually authors is
a set of topics, some of them conditional. So that is what it is called now, and the rename went all
the way down rather than stopping at the labels, because a half-renamed layer is a thing everyone
who touches it afterwards has to remember.

| Layer                   | Then                                             | Now                                       |
| ----------------------- | ------------------------------------------------ | ----------------------------------------- |
| Config column           | `AppQuestionnaireConfig.adaptiveScope`           | `.conditionalTopics`                      |
| Candidacy column        | `AppQuestionnaireVersion.adaptiveScopeCandidate` | `.conditionalTopicsCandidate`             |
| Capability slug         | `app_detect_adaptive_scope_candidacy`            | `app_detect_conditional_topics_candidacy` |
| Audit action            | `questionnaire_adaptive_scope.update`            | `questionnaire_conditional_topics.update` |
| Instrument export field | `adaptiveScope`                                  | `conditionalTopics`                       |

**Both columns were renamed in place**, which is why there is no back-compat read shim anywhere: a
column rename cannot leave a row behind, so every configured version stayed configured and one that
never opted in stayed off.

Three seams needed real work rather than a substitution:

- **The capability slug.** Seed `090` upserts on `slug`. On any database seeded before the rename it
  would have created a **second** capability row and stranded the original — with the operator's
  edits to `name` / `description` / `isActive` on it. So `090` renames its own row before its upsert.
  Verified by simulating a pre-rename row on a real database and re-seeding: same row id, new slug.
- **The wording on seeded rows.** `089`–`092` keep `name` / `description` / `systemInstructions`
  operator-owned on update, which is right for a re-seed and wrong for a rename — a seeded row would
  say "Adaptive Scope" for ever. New seed `097` **substring-replaces** the phrase instead, so an
  operator who rewrote a description keeps their wording and still gets the new name. It repairs the
  article the substitution breaks, too: "an Adaptive Scope candidate" → "**a** Conditional Topics
  candidate", which showed up in the real DB row before it was fixed.
- **Instrument import.** A definition file exported under the old name still imports its routing
  design; `parseDefinitionImport` folds the legacy `adaptiveScope` field into `conditionalTopics`
  and drops it, so nothing downstream sees two names. Export only ever writes the new one.

**Not renamed, deliberately.** The `scope/` module and the runtime's `SessionScope` / `resolveScope`
name what the planner computes — the part of the instrument in scope for one respondent — not the
feature. The route segment stays `…/v/[vid]/topics`, as F17.26 already decided. And audit rows
written before the rename keep the old action string: history is not rewritten.

## 2. The Routing Analyst reads more than one document (§9)

The follow-up asked for a multi-document input. It needed more than that: **there was no way to put
a second document on a version.** Re-ingest replaces the structure extracted from the first, so an
admin with a question bank and a separate routing memo could have one or the other, never both.

`AppQuestionnaireSourceDocument.role` now says what each row IS — `primary` (the document the
questions were extracted from, written only by ingest and re-ingest) or `supplementary` (a companion
an admin attached, which carries guidance and never questions). The analyst reads the newest primary,
then every supplementary one in attachment order.

- `POST/GET …/versions/[vid]/documents` and `DELETE …/documents/[docId]`, with a card under the
  Routing Analyst on the tab. There is no way to POST a `primary` document — that role belongs to the
  routes that extract a structure from it in the same pass — and no way to DELETE one.
- Only the companions are budgeted: 40,000 characters between them, oldest first. The primary
  document is passed whole, as it always was; bounding it would change what the analyst proposes on
  versions nobody has touched. A companion that overruns is cut at a marked seam; one the budget
  cannot reach is named but not shown. **Silence was the failure worth designing against** — a
  proposal that missed a routing page with nothing saying it had.
- The prompt states each document's role, forbids inventing a question key from a companion, and
  sends a genuine contradiction to `gaps[]` rather than resolving it quietly.

**A defect this exposed:** source documents did not fork with a version at all. Fork a launched
version and the analyst — whose whole job is to read the author's guidance — had none to read, so it
inferred from question wording and reported `fromDocument: false`. `copyVersionGraph` now copies
every document, `createdAt` included, because the readers order by it.

## 3. A plan may ask part of a topic (§2 / C6)

`depth` is a dial with two stops and no way to say _which_ items. `PlannedTopic.members` is the
missing expression — an optional explicit subset, absent on nearly every planned topic.

- **It can only narrow**, intersected with what the topic claims, in authored order.
- **An empty intersection falls back to the depth.** "In scope and asks nothing" is a topic that
  reports as covered while contributing no answer.
- **Narrowing one half says nothing about the other**: a subset of questions leaves the data slots
  at their depth.
- **The fit prices the subset** on the items it names. Charging `full` for three-of-ten drops a
  topic that would have fitted and shows the author a budget that lies. Without per-item prices a
  subset is charged at its depth — an over-estimate, which is the safe direction.
- **What the planner is shown is bounded three ways** (per question, per topic, per prompt). A topic
  whose items do not fit is printed as _"choose this topic whole or not at all"_ rather than having
  its first twelve listed: a subset chosen from an arbitrary window is worse than no subset.

The session viewer shows "3 of 10 asked" beside a narrowed topic, counted against what the topic
holds **today** — the instrument can be edited after an interview runs, and a total stored on the
plan would answer a question nobody puts.

## 4. The amendment cue gate stops excluding non-English interviews (§10)

`AMENDMENT_CUES` is a list of English phrasings, so on a version whose `audience.locale` says the
interview is held in another language it could only ever return false — silently, every turn, for
the whole feature. That locale is a configuration the product already honours: the interviewer is
told to respond in it.

**Not a translated cue list.** Authoring cue phrasings for every language the product might run in
is work nobody here can check, and a bad list fails the same silent way. The **topic labels** are
language-neutral — written in the instrument's own language by whoever wrote the instrument — so a
non-English version gates on "does this message name an excluded topic", and a hit goes straight to
the model tier. Naming a subject is not asking for it ("we sorted talent last year"); the cue list is
what tells those apart in English, and without one that judgement is the agent's.

The cost moves rather than disappearing: English still pays **nothing** on an ordinary turn (the
locale rides in on the turn context the route already loaded), and a non-English version pays one
indexed query per turn plus a model call only when a topic was named.

`labelTokens` also now splits on Unicode letters instead of `[a-z0-9]`, which had been shredding
"Prissättning" into "priss" + "ttning" — harmless while the tokens were a precision tweak for
English, load-bearing now that the label match is the whole gate.

## 5. Topics drag into order (§10)

`@dnd-kit`, the same primitive the section and question editors use, with the up/down buttons kept:
a drag is what forty topics need, the buttons are what a keyboard reaches without learning a chord.
The handle is its own control rather than the card being draggable — the collapsed line IS the
expand button and the open row is full of inputs.

Both are disabled under a filter, for the reason that predates the drag: "up" means the row above in
the full set, which is not the row above on screen.

The drop logic is `reorderDrafts`, exported and pure. dnd-kit reads element geometry and happy-dom
reports every rect as zero, so a simulated drag never produces a drop — the pure function is where
the behaviour is pinned, including the case that matters: a drop outside the list is a no-op, not a
move to index `-1`, which `arrayMove` reads as "the end".

## 6. Three overlays on the routing map

The three [`f17.18.md`](./f17.18.md) left open, all of which had their data source already built:
the last **try-it run** lit onto the path it took, the real **selection rate** per topic, and the
**coherence findings** pinned to the nodes they name.

`annotateScopeGraph` is its own module and takes a built graph, returning a new one — `graph.ts`'s
invariant is _structural, never predictive_, and a layer mixing a session's outcome into the
structure would quietly end it.

- **The state worth having** is "the agent chose it and a limit took it back". On the plan alone that
  is indistinguishable from "the agent never wanted it"; `proposedKeys` beside the plan is what tells
  them apart, and it is the whole reason this overlay earns its place.
- **A rate is a fact; whether it is a problem is a judgement.** A topic that never fires may be a
  rare-case safety net working as designed, so the badge states the share with the sample size and
  stops.
- **A toggle is offered only when it has something to say.** One that switches on nothing reads as
  "the overlay found nothing", which is not the same statement as "nobody has pressed Try it yet".

The dry-run and analytics data are handed up by the two cards that already own them rather than
fetched again — a map that re-fetched could show a number the card beside it disagrees with.
