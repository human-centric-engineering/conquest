# F18.4 — The turn evaluator learns the interviewer policy

> The first of six phases closing the ring around the three interviewer-policy features. It goes
> first because it is the only one of the six that was producing **wrong output** rather than
> missing output.

## What was wrong

Four behaviour layers landed in ten days — house rules, the funnel arc, question fidelity, and
Conditional Topics before them — and every one of them writes into the interviewer's system prompt. The
turn evaluator, which grades what comes out, was told about none of them.

`buildObjectivesContext` projected exactly four things: `goal`, `audience`, `selectionStrategy` and
`tone`. Meanwhile the rubric scores `openEndedness`, `nonLeading` and `specificity` on a 1–10 scale
and collects `violations`.

So a `must_ask` question — one the author marked as an instrument, which the interviewer is required
to put **verbatim** and, for a typed question, to state the options of — read to the judge as closed,
leading and unnaturally specific. It was marked down for doing exactly what it was told. The same
held for a `targeted` questioning approach (meant to be narrow) and for any turn shaped by a house
rule the judge could not see.

`tone` was already in that context for precisely this reason: an admin-configured voice should not
read as a fault. The argument had simply never been extended to the layers that followed it.

## What shipped

**Five new context fields**, four describing the version's configured policy (`houseRules`,
`interviewerStrategy`, `questionFidelity`, `conditionalTopics`) and one describing _this_ turn
(`questionFidelityLevel`).

**Rendered from `SETTING_DESCRIPTORS`, not from the prompt builders.** The settings registry already
holds one definition of how each config block reads in English — the same one the Questionnaire
Pack's setup listing uses — and it is `satisfies Record<keyof QuestionnaireConfigShape, …>`, so a
new config field is described the moment it gains a descriptor. The `chat/**` builders were the
obvious-looking alternative and are the wrong one: they emit second-person imperatives written _at_
the interviewer ("You have wide latitude with this question…"), and splicing one into a judge's
context instructs the judge rather than describing the interviewer. A test pins that the rendered
house-rules line contains no second-person directive.

**A rubric clause** stating that configured policy is the standard to judge against: a verbatim
must-ask must not lose `openEndedness`, an obeyed house rule is compliance rather than a
`violations` entry, and a policy that itself looks ill-judged belongs in `improvements` — not in a
low score for the turn that followed it.

**Per-question fidelity, resolved server-side.** `describeTurnFidelity` reads the level for the
question the turn actually targeted, through `resolveQuestionFidelity` so the version-level gate is
honoured (reading `slot.fidelity` raw would describe a dial the admin never switched on). Two entry
paths, because the two callers know the question differently: the saved-turn path reads
`targetedQuestionId` off the row; the live drawer sends the rendered card's `questionKey`. Either
way it is a **lookup handle, never a claimed value** — a crafted request body cannot assert a
fidelity the questionnaire does not have.

`TURN_RUBRIC_VERSION` moved to `1.1.0`, and a test now pins it, so a future rubric edit has to bump
it deliberately rather than drift past review.

## Confirmed decisions

- **The policy fields state the negative; they do not vanish when a feature is off.** This is the one
  place the codebase's off-is-silent convention is deliberately _not_ copied, and a test asserts the
  inversion. The interviewer needs silence — an empty block costs it nothing. A judge does not: told
  nothing about house rules, it cannot distinguish "none are in force" from "you weren't told", and
  it speculates. So the context carries "House rules: None" and "Conditional topics: Disabled".
  `tone` is the sole exception, and it predates this — its descriptor genuinely emits no rows when no
  dial and no persona is set, which matches the old summariser's behaviour.
- **The funnel arc is on by default** (`DEFAULT_INTERVIEWER_STRATEGY.enabled` is `true`), so the arc
  description is not an opt-in extra — every session runs one, and where in the arc a turn fell is a
  large part of how open it should have been.
- **`questionFidelityLevel` IS omitted at `balanced`**, unlike the four block descriptions. Balanced
  is the behaviour the rubric already assumes, so stating it spends tokens saying nothing and risks
  the model over-weighting a redundant line — the same reasoning that makes the `balanced` stop
  render no prompt clause at all.
- **The config select widened to the whole row** (`CONFIG_SELECT` + `toConfigView`) rather than
  adding four more columns to a hand-listed pair. The registry descriptors take a `ConfigView`, and
  a hand-maintained subset would need editing again for every future policy field.
- **The local `summariseTone` was deleted.** The registry's `tone` descriptor is strictly better —
  it carries the dials _and_ the persona, and correctly says nothing when a selectable persona has
  replaced the version's tone.
- **The live drawer's coverage is partial, deliberately.** Only a rendered answer control carries a
  question key on the client, so the live path covers `must_ask` turns and last-resort re-asks —
  which is where the mismatch actually bit — and falls back to version-level context elsewhere. The
  saved-turn path has no such limit. Threading a question key through the whole inspector dump to
  close a gap on a preview-only surface was not worth the coupling.

## Still open

- **Nothing verifies compliance.** The judge is now told what the policy was; no aggregate says
  whether must-ask questions were actually put as written across many sessions. That is Phase 4 of
  the ring (interviewer-policy analytics).
- **Nothing judges the policy itself.** "Is this a good house-rule set?" is Phase 5.
