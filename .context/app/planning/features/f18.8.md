# F18.8 — The interviewer-policy judge panel

> The largest item in [`f18-followups.md`](./f18-followups.md) §1. Question design has a judge
> panel; routing design has one; the layer that decides how every question is actually _put_ had
> only mechanical lints.

## What was wrong

`detectConfigConflicts` runs 20 checks over the interviewer policy, and they are free and mechanical.
They answer "is this well-formed". Nothing answered whether the policy is any **good** — whether a
rule is too vague to change a turn, whether a brisk funnel suits a reflective instrument, whether the
fidelity dial is set coherently across a scored battery, or whether "never use humour" quietly
overrides the humour dial the admin set to +2.

The reasoning, the dimension table, the op table and the module boundary are documented in
[`interviewer-policy-evaluation.md`](../../questionnaire/interviewer-policy-evaluation.md) — this
tracker records what shipped and when.

## Phase A — shipped

The pure core module (`lib/app/questionnaire/policy-evaluation/`), the `app_evaluate_policy`
capability, four seeded judge agents plus the capability row, the structure loader, the ephemeral
`evaluate-preview` route, a per-admin rate limiter, and the preview card on the Settings page.
Persists nothing.

## Confirmed decisions

- **A fourth sibling module**, not an extension of either existing panel — both their dimension
  tuples are compile-time locked to their own edit-op unions. Only the generic leaf types
  (`FindingSeverity` and siblings) are reused.
- **No reconcile step — but NOT for the scope panel's reason.** Its argument ("four dimensions, four
  objects, so collisions cannot occur") is **false here**: three dimension pairs can target the same
  field. The grounds are different — the overlapping fields are enums and numbers rather than prose,
  grouping does the presentation job, and per-op staleness does the safety job. Two consequences
  become load-bearing for phase B and are written into the module docs: resolve the run's review
  draft _before_ building comparison state, and compare only the op's own field.
- **The Zod is borrowed.** `houseRuleBodySchema` was extracted from `authoring/config-schema.ts` (by
  pulling its `superRefine` into a shared `refineHouseRuleTrigger`) so a judge's proposed rule is
  held to exactly the invariant a saved one is. The trigger rule is what judges get wrong most
  often, and a test pins both directions of it.
- **`set_fidelity_enabled` is the one permitted master switch**, in both directions, because
  flipping that gate destroys nothing and "you set forty sliders and never turned it on" is the best
  finding the panel can produce.
- **Per-dimension prompt sections.** Three of four rubrics have no use for the question list, and the
  DTO can carry 150 prompts. One DTO shape, four renderings — pinned by tests, and flagged in the
  module doc so nobody "fixes" it back to parity with the scope panel.
- **Sampling tells the truth.** Every non-Balanced question is kept, the rest fills in document
  order, and the prompt states what is not being shown.
- **Form-only questionnaires 409 before dispatch.** Four paid calls to learn the interviewer never
  runs is waste that reaches a bill — and a decision the scope panel never had to make.
- **The dirty-editor guard**, which has no precedent on the Topics tab: Settings holds unsaved state
  while the panel judges saved config.
- **The barrel does not re-export `run-panel.ts`.** Verified by a real `npm run build`, not just a
  type-check — three client components import from that barrel.

## Phase B — not yet built

Persisted runs and findings (two Prisma models), the review queue (accept / decline / edit / apply),
one-click apply with `forkVersionIfLaunched`, the run-history pages, `APP_SUBJECT_DATA_SOURCES`
entries, and the Questionnaire Pack section (a new top-level `PackInclude.interviewerPolicy` flag,
defaulting `false`).

One helper phase B needs that does not exist yet: **`patchVersionConfigBlocks(versionId, patch, tx?)`**.
There is no transaction-aware read-modify-write seam for the plain config blocks —
`patchAdaptiveScopeSettings` covers only adaptive scope, and the config PATCH route does an inline
upsert. Modelled on the former, down to the optional `tx`.

Also for phase B: **there is no provenance column to stamp on an applied edit.** Neither
`AppQuestionSlot` nor a house rule carries the `source` field `AppQuestionnaireTopic` has, so the
audit log is the only record that an AI suggestion — not a human — chose a value. Its metadata must
carry `previousValue`, or an enum change is unreconstructible from history.
