# F5.4 — Triage the run, then apply it as a batch

> Committable tracker for **F5.4**. F5.3 made each finding individually applicable; F5.4 makes the
> **run** the unit of decision. An admin triages every suggestion (accept / dismiss, optionally with
> a free-text instruction), then one button executes the accepted set together — in an order chosen
> so the changes do not sabotage each other, with an honest per-finding report of what did and did
> not land.

## Intent

Per-finding apply was the only path, and it made the reviewer decide the **order** of a dozen
structural edits by the order they happened to click, one confirmation at a time, with no way to
change their mind about the fifth after seeing the ninth. It also put four verbs on every card —
accept, dismiss, edit, apply — two of which are English near-synonyms that do very different things.

Reviewing now writes **nothing structural**. A queue of irreversible clicks becomes one reviewable
decision.

Shipped in three phases: the batch engine, the review surface, then the AI leg.

## Decisions (confirmed with the user)

- **The batch is a loop around `applyFinding`, not a second apply path.** Same re-validation, same
  fork-lineage rule, same 409 reasons. A parallel path drifts, and one of the two is the one with
  the hole.
- **`applyInstruction` is carried, never parsed.** The reviewer's steer is prose about _how_ to make
  a change they already accepted. `null` means "apply the judge's op exactly as proposed", so the AI
  leg is **opt-in per finding by typing something** — a run nobody steered is exactly as
  deterministic, and as cheap, as it was before.
- **`set_instruction` does not touch `status`.** A reviewer may note what they want before deciding
  whether they want it; losing that on the way to a decision is the kind of small betrayal that
  stops people using the box at all.
- **The typed `edit` op form left the card.** It asked the reviewer to express a preference as an
  exact edit. The action stays in `reviewFindingSchema` and apply still honours stored overrides —
  the capability is API-accessible, it is just no longer a control.
- **Always 200 when the run resolves.** "Every accepted change was already stale" is an answer the
  reviewer needs the per-finding detail of; an error envelope would throw that detail away.
- **A half-triaged run raises a confirmation, not a block.** "Do the ones I have looked at" is
  legitimate, so the dialog states what will and will not happen and lets it through.
- **The AI leg gets its own agent, not the Structure Edit Agent** (which the phase-2 notes had
  proposed). That agent's op vocabulary is whole-document and mechanical — it cannot express
  `split_question`, `change_type`, `edit_guidelines` or `add_question` — and its persona is
  explicitly "never rewrite wording". Two opposite mandates on one binding would have meant a
  parallel op vocabulary anyway.
- **A steer rewrites text and nothing else.** The model is never offered a slot key, an answer type,
  a section, an ordinal or a `typeConfig`, and an op-kind switch is refused outright: that is the
  model overruling the reviewer's own decision.
- **A failed steer applies nothing for that finding** — never the judge's op as a consolation. The
  reviewer asked for _their_ version of the change; giving them a different one under the same
  button is the silent substitution the whole leg exists to prevent.

## What shipped

### Phase 1 — the batch engine

- `applyInstruction` on `AppQuestionnaireEvaluationFinding` (nullable, `MAX_APPLY_INSTRUCTION`
  2 000, empty normalises to `null`), plus `set_instruction` in `reviewFindingSchema`.
- `_lib/evaluation-batch-apply.ts` — `APPLY_RANK` (deletes last, moves after content edits, ties on
  `(dimension, ordinal, id)` so the same set always executes the same way), a live structure re-read
  between findings, and a per-finding `applied` / `skipped` report.
- `POST …/evaluations/:runId/apply`, returning where the writes landed plus every finding re-derived
  so the queue re-renders from one round trip.

### Phase 2 — the review surface

- Two verbs per card, both future-tense about what applying will do; an accepted card says outright
  that it is **not applied yet**.
- Header tiles count Accepted and Dismissed apart; the batch bar is a permanent band reporting from
  the whole run, never the filtered view.
- The result panel stays up until the next batch — the only place a change that did not land is ever
  named, each reason in the reviewer's terms and noted as _still accepted_.
- New questions are slotted once for the whole batch rather than once per card.

### Phase 3 — the AI leg

- `evaluation/steer-schema.ts` — `STEERABLE_OPS` / `isSteerableOp`, `steeredEditSchema` (one member
  per steerable op, text fields only), `steerResultSchema` (`revised` + `note` + `unhonoured`), and
  `mergeSteeredEdit`, which refuses an op-kind switch and rebuilds every unoffered field from the
  judge's original.
- `evaluation/steer-prompt.ts` — the rules (keep the change; the instruction is about wording;
  say what you could not do), the op description that offers only rewritable fields, and
  `STEER_PROMPT_VERSION`.
- `evaluation/steer-edit.ts` — one structured completion per steered finding, cost logged and every
  attempt recorded as an `AppAiRun` of kind `evaluation_steer` (failures included).
- Batch wiring — steers resolve concurrently (`STEER_CONCURRENCY = 4`) **before** any write, ride
  into `applyFinding` as `editedOverride`, and report `steer_unsupported` (a wordless op) or
  `needs_ai` (a failed rewrite) rather than applying with the instruction discarded.
- `Suggestion Steer` agent (`app-questionnaire-suggestion-steer`), seeded by
  `098-suggestion-steer-agent.ts`, plus a prompt-catalog entry.
- The result panel names what the AI did with the reviewer's words and, separately, what it could
  not do.

## Known limitations (designed-for)

- **Three ops cannot be steered.** `delete_question`, `reorder` and `change_type` carry no wording.
  Reported as `steer_unsupported` without a model call; the reviewer clears the instruction or makes
  the change in the editor.
- **A steered batch costs model time.** One call per steered finding, bounded by the concurrency
  window and the existing `evaluationApplyLimiter` sub-cap. A very large steered run is still the
  slowest thing this route can do.
- **A steer reads the structure as the batch opened it**, not as the loop rewrites it. A rewrite
  depends on the change and the questionnaire the reviewer saw, not on what the other findings
  wrote; the apply-time staleness re-check still runs per finding.
- **The revised op is not persisted on the finding.** It is recorded on the `AppAiRun`, and the
  wording itself is visible in Build. A dedicated column was rejected as a migration for provenance
  the run row already carries.
