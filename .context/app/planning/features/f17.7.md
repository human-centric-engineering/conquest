# F17.7 — Authoring the Merlin5 Growth Assessor

> The first instrument that actually needs Adaptive Scope, and the one the phase was generalised
> from. Authored by `npm run author:merlin5 -- <workbook.xlsx>`.

## Confirmed decisions

- **A script, not a seed.** This is a client's intellectual property. A seed would create it on
  every `db:seed` of every install and commit 70 rows of someone else's question set to this repo.
  The script reads the workbook from a path at run time, so **the content never enters git** — only
  the mapping, which is ours.

- **A script, not the product's own ingest.** The product accepts `.xlsx` (`flattenWorkbook` → the
  extraction agent), and that is the right path for a document that only _implies_ its structure.
  This workbook does not imply it: it _states_ exact keys, types, scale bounds, per-point labels,
  weights, required flags and guidelines, in columns. Putting a model between that and the database
  can only lose fidelity, and a re-derived key differing by one character silently breaks every
  routing rule that names it. Extraction where structure must be inferred; this where it is declared.

- **Question 0.5 is not a question.** The workbook's handoff script — "based on what you've said I
  want to go deeper on [named sections]" — is a moment the platform already owns: the Scope Planner
  writes that sentence and `announce` delivers it in the interviewer's voice on the turn after the
  plan is decided. Persisting it as a question would put a second, static copy in front of the
  respondent, one of which could not name the sections because nothing had chosen them yet. Skipped
  deliberately and logged, never silently.

- **Weight 0 on the opening, as the workbook specifies.** Below the admin slider's 0.1 floor, and
  that is the point: it drops the four routing questions out of the weighted-coverage denominator,
  so an unscored opening cannot make a complete interview look incomplete. (Capability C1 of the
  research doc — the one thing we already had.)

- **The opening's data slots are hand-written, not generated.** They are load-bearing for routing:
  `isOpeningComplete` waits on the opening topic's data-slot keys, and G02's veto tests
  `commercial_outcome` _by name_. A generated set would name them differently every run and every
  rule would stop matching. `commercial_outcome` is deliberately separate from `growth_goals` even
  though both draw on 0.2 — the veto turns on whether they named a commercial outcome, which is a
  distinct fact, and one the extractor must be able to leave **empty**.

- **Criteria stay in the author's words.** Composed from the Routing tab's own SIGNAL, LISTEN FOR
  and NOTES columns rather than paraphrased, because the planner weighs criteria above its own
  judgement — the closer to what the client wrote, the closer the routing is to what they specified.
  Rules targeting one section are joined with an explicit "ANY of the following, the more the
  stronger", because the Routing tab is a **tally**, not a chain, and a multi-rule section read as
  needing all of them would almost never fire.

## The gap this closed in the platform

**G02 could not be expressed.** "Route Section 14 only if a commercial outcome is named" is a
_veto_ — a rule about something the respondent did **not** say — and the operator vocabulary had
only positive tests, with `scopeRuleMatches` short-circuiting on an unfilled slot. `rules.ts` even
cited that exact rule in its docblock as the motivating example, while being unable to evaluate it.

So `not_exists` was added: the one operator that matches on absence, evaluated before the
unfilled-slot guard, with the operand ignored. Without it, the client's most interesting guardrail
could only have been prose criteria for the planner to weigh — which is precisely the failure mode
hard rules exist to prevent.

## Still not built, and deliberately not faked

The script prints these on every run rather than leaving them to be discovered:

- **G03** — one probe maximum across the opening. There is no per-session probe budget.
- **G05** — hold the close (15.1/15.2) against the opening (0.2) and the scored result. The report
  has no open-vs-close reconciliation, and the workbook calls that disagreement "the most valuable
  output the tool produces".
- **G06** — normalise Section 14's 1–6 against everything else's 1–5. Scoring has no cross-scale
  normalisation, so **do not build a composite across Section 14 and the rest until it does.**
- **The 10-minute budget** — the cap is a topic COUNT (3), not seconds. The workbook _derives_ three
  from 600s, so a client asking for 15 minutes needs a code change today rather than a setting.
  This is capability C7 of the research doc and the largest remaining gap.

Also worth an admin's eye: a few criteria carry sentences the client wrote for whoever _builds_ the
thing ("See guard G02", "Ask nothing to elicit it"). They are inert to the planner, and trimming
them automatically would have meant deciding which of the author's sentences count — so they are
left for a human to trim on the Topics tab, which is what that surface is for.
