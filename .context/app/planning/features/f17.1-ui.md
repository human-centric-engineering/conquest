# F17.1-UI — The Topics authoring surface

> F17.1 shipped the model, the seeding, the fork behaviour and the API. Nobody could author against
> any of it. This is the surface.

## Confirmed decisions

- **A workspace tab of its own, not a section of Settings.** Most of the Conditional Topics knobs
  _address topics_ — the fallback set, the blind-spot preference and every hard rule name a topic
  key. Split across two tabs, an admin would be picking from a list they cannot see. It sits in the
  **Build** group, after Data slots, because a topic's membership is question and data-slot keys.

- **Two saves, two endpoints.** The topic set is a PUT that replaces the set; the settings are a
  PATCH of one blob. A single "save everything" button would mean an admin fixing one typo in a topic
  also rewrites their rules, and a partial failure would leave them unable to tell which half landed.

- **Findings are advisory, never a gate on the keystroke.** `validateConditionalTopics` runs on read. An
  admin mid-edit routinely has an incoherent set, and a surface that refuses the save is a surface
  they fight. Errors block **launch**; warnings never block anything.

- **The uncovered-question count is live, over the working set** — not only over what was last saved.
  With scope on, a question in no topic can never be asked and nothing else in the system reports it,
  so the number has to move as the admin edits.

- **Stale keys are shown, never silently dropped.** A topic naming a since-deleted question is
  skipped at runtime and flagged by the launch check; hiding it here would leave the admin unable to
  see — let alone remove — the thing the checklist is complaining about. Same for a rule pointing at
  a missing data slot: it stays selectable, marked `(missing)`.

- **The panel remounts on the server payload.** A save's normalised result — clamped numbers, dropped
  blanks, sorted rules — has to replace the local draft rather than hiding behind it. The admin must
  see what a later read will actually produce.

- **The launch check appears only for a version that opted in.** A permanently-green row for a feature
  nobody enabled is noise on every other questionnaire in the system. The orphan finding is still
  reported as a **warning** while scope is off, which is exactly what an admin needs to see _before_
  flipping the switch.

- **Key derivation stops once the admin touches the key.** A new topic's key follows its name; an
  existing one never moves on its own, because keys are how rules and plans address a topic and a
  silent rename would stop them matching.

## Follow-ups

- **No topic reordering by drag.** Up/down buttons only. Fine for a dozen topics, tedious for forty.
- **The membership pickers do not warn about a question claimed by two topics.** Scope tolerates it
  — the question is asked if _either_ topic is in scope, and `topicByQuestionKey` attributes it to
  the first in-scope topic in ordinal order — but an author almost never means it, and
  `validateConditionalTopics` does not currently check for it. The visible symptom would be a report
  attributing a question to the wrong topic.
