# F17.24 — De-risk the Adaptive Scope tab before splitting it

Phase 1 of the tab simplification. **No visible change** — four latent defects that today's
single-stack shell hides, plus the one payload field the future header needs.

Each is independently testable against the current layout, which is why they land before any
restructuring rather than inside it.

## The four defects

**1a. The busy lock released on any re-render.** `topics-panel.tsx` keyed
`useEffect(() => setBusy(false), [payload])`. `payload` is a fresh object on every RSC render — a
`router.refresh()` from any card on the page produces one, and so will every sub-tab change once
`?tab=` exists. So the lock released at moments that have nothing to do with the save completing,
which is exactly the window its own comment says it closes.

Now keyed on **`versionId`**, and the two cases are separated:

- **No fork** → released in `run` itself. `endpoint` still names a version the admin is on, so a
  second save there is merely a second save.
- **Fork** → stays locked. `endpoint` closes over the pre-fork version id and stays wrong until the
  redirect lands, so releasing there would write to the version the admin has just been moved off.
  The `versionId` effect releases it when the redirect arrives.

> The plan proposed a **content signature** instead. It is worse: an admin who presses Save without
> having changed anything produces an identical payload, the signature never changes, and the page
> stays locked with no way out. Recorded because it looks like the obvious fix.

**1b. The nonce handoffs would be spent while invisible.** `focusTopic` (routing map → topic list)
and `seedTopic` (analyst gap → topic list) fire on the next commit. Under the `forceMount` the
sub-tab split requires, the editor is mounted but hidden, so both effects would run: retire the
request via `onFocusHandled` / `onSeedHandled`, and then scroll a node with no layout. The admin
lands on the Topics tab having been scrolled nowhere, with no way to ask again — and in the seed
case, with a row appended that they never saw appear.

`TopicListEditor` now takes `active?: boolean` (default `true`), and it is a **dependency** of both
effects rather than merely a guard inside them: a request that arrives while hidden **waits** and is
acted on the moment the panel becomes visible.

**1c. The fork redirect dropped the query.** `router.replace` rebuilt the URL from scratch. Today
that loses nothing; once sub-tabs exist it would silently return the admin to the first sub-tab
after every fork — on the version they have just been moved to, which is the worst moment to lose
their place. The current `window.location.search` is now carried across.

Read off `window.location` rather than `useSearchParams()`: this runs in an async callback, so the
live value is the honest one and a hook's render-time closure could be a tab behind.

**1d. Nothing pinned the partial PATCH.** `patchAdaptiveScopeSettings` is a genuine
read-merge-write and every field on `adaptiveScopeSettingsSchema` is optional, so it depends on Zod
**omitting** absent optional keys rather than emitting them as `undefined` — `{ ...current, ...patch }`
would happily write `undefined` over a sibling.

A merge-preservation test already existed, but it hand-built `{ enabled: true }`, which is not what
the route hands in. The new test parses through the **real schema** first and asserts
`Object.keys(parsed)` is exactly `['enabled']` before checking that the cap, the planner
instructions, the fallback list and the rules all survive. This stops being hypothetical the moment
the persistent on/off switch ships, because it sends exactly that body.

## The payload field the header needs

`uncoveredQuestionKeys` and `uncoveredDataSlotKeys` are promoted out of `validateAdaptiveScope`'s
body and exported, and the Topics GET calls them to populate a new
`TopicsPayload.coverage` — `{ totalQuestions, uncoveredQuestions, totalDataSlots,
uncoveredDataSlots }`.

Server-computed through the **same functions** the orphan findings use, so a header reporting
"3 questions in no topic" and an issue list reporting a different number is not a state the payload
can be in. Deriving it in the browser was the alternative and is subtly wrong: the finding
suppresses itself when a version has no topics at all, so a naive client-side count would report
orphans against an issue list that is deliberately silent.

## What changed

| Path                                      | Change                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------- |
| `topics/topics-panel.tsx`                 | Busy lock re-keyed on `versionId`; non-fork releases in `run`; fork carries the query |
| `topics/topic-list-editor.tsx`            | New `active?: boolean`, a dependency of both handoff effects                          |
| `lib/app/questionnaire/scope/validate.ts` | `uncoveredQuestionKeys` / `uncoveredDataSlotKeys` exported; the findings call them    |
| `lib/app/questionnaire/scope/views.ts`    | `TopicsCoverage` + `TopicsPayload.coverage`, and its `EMPTY_TOPICS_PAYLOAD` default   |
| `.../versions/[vid]/topics/route.ts`      | Populates `coverage` from the same helpers                                            |

No migration, no API removal — `coverage` is additive.

## Tests

- `topics-panel.test.tsx` — the busy lock holds across an identical-content re-render, releases on a
  plain save, and stays locked after a fork until `versionId` changes; the fork redirect carries
  `?tab=rules`
- `topic-list-focus.test.tsx` / `topic-list-seed.test.tsx` — the request is not consumed while
  hidden, is acted on the moment the panel becomes visible, and `active` defaults to true
- `_lib/topic-routes.test.ts` — the schema-parsed lone-field PATCH preserves every sibling
- `topics-routes.test.ts` — `coverage` matches the issue list computed in the same request, and a
  fully covered version reports zero rather than omitting the block
