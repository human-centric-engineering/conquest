# F17.21 — Conditional Topics evaluation judge panel

> "I would like a way of judging the conditional topics stuff... I would like to end up with a set of
> recommendations in a similar way we get the questionnaire recommendations after the panel of
> judges. This evaluation and recommendations would also need to be included in the questionnaire
> pack."

## What was wrong

Conditional Topics had a deterministic coherence checker (`validateConditionalTopics`) and a cost model,
both mechanical and free — but nothing that judged whether the routing design was actually **good**
toward the module's own implicit goal: minimize respondent burden (skip topics that don't apply)
while never silently dropping a topic that genuinely does apply (hard rules always win, "when in
doubt, ask", exclude-beats-include). The question design already had exactly this kind of review
(F5.1–F5.3's judge panel); the routing design that decides which questions a respondent even sees
did not.

## What shipped

A four-judge structural panel over the authored scope config (topics, hard rules, planner
instructions, budget) — `criteria_quality`, `rule_integrity`, `budget_realism`,
`coverage_and_burden` — each explicitly told not to re-derive what `validateConditionalTopics` and the
cost model already catch mechanically. Findings carry one of eight machine-applicable edit ops
through an accept/decline/edit/apply review queue, and the latest run's scores and findings appear
in the Questionnaire Pack, nested inside the existing `conditionalTopics` section.

Full design rationale, the dimension table, the apply-op table, and the module boundary are
documented in [`conditional-topics.md`](../../questionnaire/conditional-topics.md#scope-evaluation-f1721)
— this tracker covers what shipped and when, not the reasoning already written there.

## Confirmed decisions

- **Structural only, v1** — the judges read authored config, not live session data or the
  routing-analytics engine (F17.16). A later phase could layer that signal in.
- **A new sibling module** (`lib/app/questionnaire/scope-evaluation/`), not an extension of
  `lib/app/questionnaire/evaluation/` — that module's `EVALUATION_DIMENSIONS` tuple and
  `ProposedEdit` union are closed and compile-time-locked to question/section/goal/audience
  vocabulary. Only generic leaf vocabulary (`FindingSeverity`, `FindingReviewStatus`,
  `FindingApplicability`) and the fan-out/persist/apply pattern are shared.
- **No cross-judge reconcile step**, unlike the design-evaluation panel — the four dimensions
  target different fields of different objects, so the collision case the reconciler exists for
  mostly cannot occur here.
- **Pack integration extends the existing `conditionalTopics` section** (`PackConditionalTopics.evaluation`)
  rather than adding an eighth top-level section or a new `PackInclude` flag — it is a judgement
  about the routing design printed just above it, not a separate subject.
- **Two PRs instead of three** for the persistence/review/apply split F5.2/F5.3 used — this
  surface is small enough (4 judges, topic/rule/settings targets rather than dozens of questions)
  that splitting run-history from apply would be an artificial seam.
- **`describeScopeRule` and a new `describeScopeProposedEdit`** are both promoted to shared,
  Prisma/React-free modules (`scope/rule-format.ts`, `scope-evaluation/describe-op.ts`) so the
  admin review card and the Questionnaire Pack render the same sentence from one implementation,
  never two that can drift.

## Tests

- `tests/unit/lib/app/questionnaire/export/build-pack-model.test.ts` — the new "scope evaluation
  appendix" describe block: `hasRun: false` shape, dimension order (including a dimension the run
  never mentions), by-target grouping with a plain-English `proposedEditSummary`
- `tests/unit/lib/app/questionnaire/export/build-pack-csv.test.ts` / `build-pack-markdown.test.ts`
  — the new scope-evaluation blocks/subsection, both empty and populated
- `tests/unit/app/api/v1/app/questionnaires/render-pack-pdf.test.tsx` — the PDF renders the
  scope-evaluation subsection in both its `hasRun: false` and populated states without throwing
- `tests/unit/app/api/v1/app/questionnaires/pack-route.test.ts` — the route loads the latest
  scope-evaluation run alongside topics/settings only when `conditionalTopics=true`, and threads it
  through to `buildPackModel`
- `tests/unit/lib/app/questionnaire/scope-evaluation/**` — the core module itself, added during the
  PR-gate pass: `dimensions.test.ts` (registry exhaustiveness — four dimensions, unique
  app-namespaced slugs, slug round-trip), `judge-schema.test.ts` (Zod contract + degradation for
  both the verdict and each `proposedEdit` op), `judge-prompt.test.ts` (rubric splicing, structure
  serialisation, the goal statement every dimension shares), `run-panel.test.ts` (the fan-out and
  all three fail-soft paths — missing agent, `{success:false}`, a thrown dispatch),
  `group-findings.test.ts` (by-target grouping and every sort mode over the kind-rank order),
  `structure-schema.test.ts` (the DTO's caps and enum fields), and `describe-op.test.ts` (one case
  per op for the plain-English rendering). Mirrors `tests/unit/lib/app/questionnaire/evaluation/**`
  minus the reconcile-only files (`reconcile-panel`, `reconcile-schema`, `group-actions`), which
  have no scope-evaluation equivalent — see the module's "no reconcile step" note.
- `tests/integration/lib/app/questionnaire/evaluate-scope-capability.test.ts` — the
  `AppEvaluateScopeCapability` dispatch, also added during the PR-gate pass: happy path,
  clean-pass, the dimension stamp, malformed-JSON retry-repair, no-silent-failure on final parse
  failure, cost-log metadata, the `reasoning` tier + system-default binding, and both
  provider-resolution fail-closed paths. Mirrors
  `tests/integration/lib/app/questionnaire/evaluate-structure-capability.test.ts` (F5.1).

Deferred: unit tests for the apply engine (one case per op × fork/no-fork × stale/target_gone) and
the `_lib/scope-evaluation-*.ts` DB-seam / route layer — Phases 1 and 2 were verified live against a
real dev server and the seeded Merlin5 instrument instead. This matches the design-evaluation
sibling's own coverage shape exactly: `evaluation/**`'s core module is thoroughly unit-tested, but
its `_lib/evaluation-*.ts` DB seam and `route.ts` handlers under `.../evaluations/**` carry no tests
either — an established pattern in this codebase, not a gap unique to this feature.
