# F18.1 — Interviewer house rules

> "We have a customise voice capability in the set up area — but as far as I'm aware we don't have
> the ability to have custom prompts per client questionnaire. This would be a useful addition to
> customise the experience (it would be optional via a toggle) and we would offer a few ideas to
> help the admin customise the experience — such as must dos, or must not dos, or things to say if
> certain questions are asked... Please suggest how we could create this and how to help the admin
> decide what custom prompts to include."

## What was wrong

An admin could already shape how the interviewer **sounds** (nine tone dials plus a 600-character
free-text persona) and how it **questions** (the funnel/open/targeted strategy). Nothing shaped what
it may and may not **do**.

The only outlet for policy was `tone.persona`, where it competed with voice instructions for the same
600 characters and landed in the `<tone>` prompt section — the wrong place, since tone is about
register, not rules. It got no validation, no examples, and no warning when it contradicted another
setting.

That gap bites hardest in client work, where each questionnaire carries its own boundaries: a
regulated client cannot have the interviewer appear to give advice; an anonymous survey needs a
consistent answer to "is this really anonymous?"; a client with house terminology wants
"colleagues", not "staff".

## What shipped

An optional, off-by-default `houseRules` config block: a list of typed rules — **Always**, **Never**,
**If asked, say** — rendered into a `<house_rules>` section on both the question phraser and the
wrap-up message.

Because the user's ask was explicitly half "how do we help the admin decide", four decision-support
mechanisms ship alongside the editor:

| Mechanism           | What it does                                                                    |
| ------------------- | ------------------------------------------------------------------------------- |
| **Rule ideas**      | ~20 presets across six categories, each with a "why you'd use this" line        |
| **Suggest rules**   | One-shot AI analysis of this questionnaire → 4–8 candidates, each with a reason |
| **Conflict checks** | Eight lints warning when a rule can't do what it says                           |
| **Preview**         | The real rendered block, from the same pure function the server calls           |

Delivered as four sequential PRs on `feat/interviewer-house-rules`: engine (inert), authoring UI +
library, conflict lints, AI suggester.

## Load-bearing decisions

**A typed rule list, not a free-text blob.** Each kind needs different prompt framing, rules toggle
individually, and the lints can only reason about structure. A blob would also invite quietly
overriding the safeguarding, anonymity, and reply-format rules the prompt depends on.

**Section placement is precedence, and it is the whole mechanism.** Prompt sections are ordered and
later ones win, so `<house_rules>` sits **after `<tone>`** (client policy outranks the voice dials —
"never use humour" must beat a humour dial set high) and **before `<output_format>`** (a rule can
never break the reply contract). Because that puts it past most of the prompt's own instructions, the
block opens with an explicit subordination clause. Both the ordering and the clause are asserted by
test — a presence-only check would miss an accidental reorder that silently inverts precedence.

**Off is provably silent.** The test compares the built prompt against one built with no `houseRules`
field at all, so an existing questionnaire's conversation is demonstrably unchanged rather than
assumed to be.

**`if_asked` is paraphrased, never recited.** A canned string read verbatim breaks the conversational
illusion the product rests on. Verbatim mode for compliance clients is deferred, not dismissed.

**The suggester proposes, never applies.** No apply endpoint exists. A rule the admin never read is
exactly what this feature exists to prevent, so propose-then-accept is the point, not a nicety — and
there is deliberately no "add all".

**Presets refuse to guess.** Several carry a literal `__` placeholder ("most people take about `__`
minutes"). A confident wrong answer to "who will see my answers?" is worse than no rule, and the
panel warns while any enabled rule still holds one.

## What the work turned up

**The type system caught a wiring gap.** `settings-registry.ts` is typed
`Record<keyof QuestionnaireConfigShape, SettingDescriptor>` — a compile-time manifest forcing every
config key to have a display descriptor. Adding `houseRules` broke the build until it had one, which
delivered the Questionnaire Pack summary a phase early.

**The migration tried to drop the pgvector indexes**, exactly as the house notes warn. Five
`DROP INDEX` statements plus a tsvector `DROP DEFAULT` alongside the one real `ADD COLUMN`; stripped
by hand, applied via `migrate deploy`, all five verified intact afterwards.

**Two lint patterns false-fired on ordinary wording** and were caught by tests, not by review:
`\bin order\b` matches "in order to", and a bare `\bpoints\b` matched "acknowledge the points they
raise". Both are narrowed with regression tests, and there is a test asserting an entirely ordinary
rule trips nothing at all — an admin who learns to ignore the panel is worse off than one who never
saw the warning.

**A real accessibility bug**: the master switch had no accessible name and could not be reached by
assistive tech. Fixed in the component rather than worked around in the test.

## Deliberately not built

- **A tone-contradiction lint** ("never use humour" against an enabled humour dial). House rules sit
  after `<tone>` and therefore win, so it is not a conflict — and the check would have to account for
  built-in persona mode replacing the version's dials entirely. Low signal for real complexity.
- **`recordAiRun` on the report-craft model.** The suggester _does_ record (`house_rules_suggest`),
  unlike the Respondent Report config assistant. That one is a multi-turn chat where the admin thinks
  aloud; this is a one-shot analysis whose proposals a human adjudicates into durable config — the
  Config Advisor's case, and `glossary_analysis`'s argument verbatim.

## Follow-ups

- **Verbatim `if_asked` responses** — a per-rule flag for compliance clients needing exact wording.
  Changes the prompt contract, so it deserves its own pass.
- **Per-topic rule scoping** — binding a rule to a conditional topic or section rather than the
  whole questionnaire.
- **Client-level rule libraries** — a shared set inherited by every questionnaire for a client, once
  the same rules are being retyped across engagements.
