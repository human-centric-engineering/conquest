# F17.23 — Three defects the Merlin5 audit exposed

## How they were found

An audit of a real imported instrument — `Merlin5_Growth_Assessor_Question_Set_v3`, an `.xlsx`
carrying a Routing tab and a Guardrails tab — compared what the Routing Analyst proposed against
what the workbook actually specified.

The proposal was good: it inverted all twelve of the workbook's routing rules onto the right topics.
Three things were wrong, and none of them were things the product could tell anyone about.

## What was wrong

**1. `light` depth on the opening topic, uncaught.** The proposal set the opening — five questions,
the workbook's own "primary routing input" — to `light`. `membersAtDepth`
(`scope/resolve.ts:133-148`) applies depth to **every** phase, so accepting it would have cut the
opening to `LIGHT_DEPTH_MEMBER_COUNT` (2) questions and decided the whole interview from half the
evidence. `validateAdaptiveScope` never inspected `depth` at all, so nothing anywhere would have
said so.

Not a one-off: the same proposal shape appeared again on a second test instrument
(`Merlin Adaptive Upload Test 01`) before this work started.

**2. The prompt invited it.** `analysis-prompt.ts` gave depth exactly one line — `"light" (a sample
of the most important few)` — which reads as a refinement rather than a deletion, with no mention
that depth applies to always-run phases.

**3. Guardrails the platform implements were filed as unformalizable.** The workbook's blind-spot
instruction ("carry 2 items from one NON-selected section — take from Data or Management") came back
under `gaps` as something the analyst "cannot formalize" — when `includeCheckTopic` +
`checkTopicPreference` + the forced-`light` check topic in `guardrails.ts:184-190` implement it
exactly. Its fallback rule was folded into three topics' criteria instead of `fallbackTopicKeys`,
which is a **different runtime path**: `applyGuardrails` fires the fallback only when nothing was
seated.

The platform already agreed both were machine-proposable — `ScopeProposedEdit` carries
`add_fallback_topic` and `edit_planner_instructions` (`scope-evaluation/types.ts:108-110`). Only the
analyst was mute.

## Confirmed decisions

- **Coerce, don't refuse.** The depth fix lives in `narrowProposedTopicSet`, not as a
  `routingAnalysisSchema` refine. A hard rejection would discard an otherwise-good fifteen-topic
  proposal and pay for a retry over one field. The analyst _does_ have a retry-once path
  (`analyse-routing.ts:246`), which was checked before choosing — it lowers the risk but does not
  remove it, and the failure is asymmetric.
- **Corrected but never silent.** `ProposedTopicSet.depthCorrectedKeys` carries the corrected keys
  and the review card renders an amber note. A silent fix leaves the admin unable to learn that
  their document's wording invited it.
- **Membership enforced at narrow time, not at the schema**, for the same asymmetry: an unknown
  settings key is inert at runtime, so refusing the whole response over one is the wrong trade.
- **`plannerInstructions` stays un-proposable.** It is prose steering the model; an analyst writing
  its own steering is a loop worth not building.
- **No judge-prompt change.** `scope-evaluation/judge-prompt.ts:157` builds its "already caught by
  the mechanical coherence checker, do not repeat" block dynamically from `validateAdaptiveScope`'s
  own output, so the new code flows into the module boundary automatically.
- **The accept path caps the two lists at 20, not the analyst's 5** — both paths write the same
  settings field, so a value acceptable through the PATCH must be acceptable through the accept.

## What was NOT done, and why

**A full `validateAdaptiveScope` pass over the pending draft.** The plan called for it, but the
checks it would add are already covered by narrower ones that exist: `routing-analyst-card.tsx:365`
already computes uncovered questions, `routingAnalysisSchema` already refuses a conditional topic
with no criteria, and the depth defect is now corrected at the narrow seam. A second validator path
would have duplicated three checks to add none.

## What changed

| Path                                             | Change                                                                                                                                   |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `lib/app/questionnaire/scope/validate.ts`        | New `light_depth_on_always_topic` issue — per-kind, silent below the member floor, error/warning on `enabled`                            |
| `lib/app/questionnaire/scope/analysis-prompt.ts` | New `## Depth` and `## Two settings that are not topics` sections; a "do not report these as gaps" line; two keys in the output template |
| `lib/app/questionnaire/scope/analysis-schema.ts` | Optional `fallbackTopicKeys` / `checkTopicPreference` (max 5) + `ROUTING_ANALYSIS_MAX_SETTING_KEYS`                                      |
| `lib/app/questionnaire/scope/types.ts`           | `ProposedTopicSet` gains the two lists plus `depthCorrectedKeys`; `narrowProposedTopicSet` coerces and filters                           |
| `lib/app/questionnaire/scope/schemas.ts`         | `acceptTopicDraftSchema` carries both lists (max 20, matching the settings PATCH)                                                        |
| `_lib/topic-draft.ts`                            | `acceptTopicDraft` merges both; docblock's "three deliberate choices" becomes four                                                       |
| `topics/routing-analyst-card.tsx`                | Renders both settings by topic **label**, renders the depth-correction note, sends both on accept                                        |

No migration — `AppQuestionnaireTopicDraft.topics` is a Json column and the settings live in the
`adaptiveScope` blob.

## Ship-day check

The new issue was counted against the dev database before shipping:

```
SELECT count(*) FROM app_questionnaire_topic WHERE depth='light' AND phase <> 'conditional';  -- 6
```

Of those six, **exactly one** fires: the `opening_situation_goals_challenges` topic on
`Merlin Adaptive Upload Test 01` (5 questions → 2). The other five are one- and two-member topics
that the per-kind floor correctly ignores. That version has scope **off**, so the finding is a
warning and **no existing version's launch gate changes**.

## Tests

- `scope/validate.test.ts` — new describe block: error on the opening with the feature on, warning
  with it off, fires on core and closing, silent on conditional, silent below the member floor, and
  fires on the data-slot side independently
- `scope/settings.test.ts` — the coercion (opening/core/closing corrected, conditional untouched,
  `depthCorrectedKeys` populated only when something was corrected) and the two lists (carried,
  omitted when absent, unknown keys dropped)
- `scope/analysis-schema.test.ts` — both accepted, both `undefined` rather than `[]` when absent,
  over-cap refused, and an unknown key deliberately **not** refused
- `scope/analysis-prompt.test.ts` — the depth prohibition by name, the member count, "full when the
  document is silent", both settings taught, the gap suppression, both keys in the template
- `_lib/topic-draft.test.ts` — the merge itself: omitted leaves the version's own values alone,
  present replaces them
- `topics-draft-route.test.ts` — the accept forwards both and carries no `enabled` key
- `routing-analyst-card.test.tsx` — both settings rendered by label, the correction note shown and
  suppressed, and the accept payload

806 tests pass across the scope, topics-component, draft-route and launchability suites.
