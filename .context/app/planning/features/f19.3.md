# F19.3 — A questionnaire chooses where the text ladder opens

> The text-size stepper was entirely respondent-owned and had no authored counterpart. A demo run on
> a boardroom screen opened at the same size as one read alone on a laptop, and the only fix was
> asking the room to press the "A" twice.

## What was wrong

`chat-text-size.md` argued the size was deliberately **not** a config knob: an admin cannot know a
respondent's eyesight, screen or viewing distance. That argument is right about the size itself and
is untouched here.

It was doing double duty, though. It also ruled out the _starting_ size — which an admin often does
know, because they know the room. Somebody demoing on a projector, or shipping an instrument dense
enough to want smaller type, had no way to say so.

## What shipped

`config.chatTextSize` (`small` | `standard` | `large` | `largest`), on the Settings tab's
**Respondent experience** group, labelled **"Text opens at"**. It names the rung a respondent opens
on. Nothing more.

**The ordering is the whole design**, and it is asserted from both directions:

```
useLocalStorage(CHAT_TEXT_SCALE_STORAGE_KEY, normalizeScaleIndex(chatTextScaleIndex))
                                              └── the authored rung, as `initial` only
```

`useLocalStorage` returns `initial` only while nothing is stored. So — nobody has stepped → the
questionnaire's rung; anybody has ever stepped, here or on any other questionnaire → their own, and
the authored value is never consulted for them again.

An author can choose what a first-time reader sees. They cannot pin, cap, or reset somebody's
accessibility preference, and there is still no switch that removes the stepper.

## Confirmed decisions

- **A starting point, never a cap — and the inverse was rejected outright.** "Authored value wins
  per session" would silently take larger text away from the person who had deliberately set it, on
  every new questionnaire they opened. That is worse than having no setting at all. A test asserts
  that a stored preference beats an authored `largest`, and another that stepping _down_ from an
  authored `largest` still works (a floor would pin every laptop respondent at 1.3).
- **The column stores the NAME, not the ladder index.** localStorage can keep an index because its
  key is versioned (`.v1`) and a retune can discard stale ones. An authored value has no such
  escape: a stored `2` would quietly mean a different size once the multipliers moved, where a
  stored `large` still means the large one. `CHAT_TEXT_SIZES` is index-aligned with
  `CHAT_TEXT_SCALES` to make both true at once, and the ladder tests assert the alignment rather
  than assume it.
- **`indexForTextSize` must never return `-1`.** It is forgiving like every other plain-TEXT enum
  read in this codebase (a rollback, a seed, or a newer deploy's rung name can all reach the
  column), and it resolves anything unrecognised to `standard`. `-1` would arrive at the
  transcript's `calc()` as a `NaN` and drop its `font-size` declaration entirely — blanking the
  size for the whole conversation. A test covers `null`, `undefined`, `''`, an unknown rung, a
  prototype key, and — deliberately — the string `'2'`, so a caller who confused the name for the
  index gets a readable conversation rather than the large rung.
- **Index 1's label moved from "Default" to "Standard".** It is visible: the stepper's
  `role="status"` announcement reads it aloud. "Default" is actively wrong on a questionnaire whose
  author set the default to Large.
- **Resolvers return an INDEX, not a name.** The one consumer needs an index, so
  `resolveChatTextScaleIndexForVersion` and the surface bundle both do the lookup server-side and
  the four surfaces pass a number they cannot mis-map.
- **The meeting parity test was extended, not just the code.** `resolveRespondentSurfaceConfig` is
  checked field-for-field against the per-field resolvers. Without adding the new field there, a
  participant whose questionnaire opened at Largest would have silently dropped to standard the
  moment they entered a breakout room — the exact class of gap that test exists to catch.
- **Additive migration, default `'standard'`.** That is the size every questionnaire had before the
  column existed, so every live version renders unchanged. Generated with `--create-only`; the
  phantom pgvector `DROP INDEX` block was stripped before applying, and all five vector indexes
  were verified present afterwards.

## Still open

- **The stepper is chat-only.** The form surface has its own type sizing and neither the stepper nor
  this setting touches it. Unchanged by this work, but now slightly more surprising: an admin who
  sets "Text opens at: Largest" on a `form`-mode questionnaire gets nothing.
- **No preview.** The admin picks a rung without seeing it. The Settings tab has no live respondent
  preview to hang one off, so this would need the `?preview=1` surface to accept an override.
- **It reads as a flat row in the Questionnaire Pack.** The registry entry is `tier: 'standard'`, so
  `buildSettingRows` puts "Text opens at: Large" into the pack's setup listing with no note that a
  respondent can change it. A client reading the pack could take it for a fixed property of the
  instrument. The row wording ("opens at" rather than "text size") is the only hedge.
