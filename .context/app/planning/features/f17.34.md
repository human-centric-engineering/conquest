# F17.34 — The design judges must know the interview is conditional

> Asked as a question about the evaluation judges: does Conditional Topics change what they should
> say? It does, and the panel could not tell. Looking for the answer also turned up a silent write
> defect, which is [`f17.35.md`](./f17.35.md).

## What was wrong

ConQuest runs three design-time judge panels. Two of them read routing; one did not.

| Panel                                  | Sees topics?                                                           | Evidence                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Scope panel (4 judges, F17.21)         | Yes — topics, phases, criteria, member prompts, budget arithmetic      | `scope-evaluation/types.ts` `ScopeStructureInput`                          |
| Policy panel (4 judges, F18)           | Yes — per-question `topicKeys`, a `ROUTING (CONDITIONAL TOPICS)` block | `_lib/policy-evaluation-structure.ts`, `policy-evaluation/judge-prompt.ts` |
| **Design panel (7 judges, F5.1–F5.4)** | **No** — goal, audience, sections, questions, nothing else             | `evaluation/types.ts` `VersionStructureInput`                              |

There was not one occurrence of `topic` anywhere in `lib/app/questionnaire/evaluation/**`, and
`design-evaluation.md` never mentioned the feature either.

So the **Duplicates judge** read one flat numbered list in which an `opening` signal-gathering
question and a `conditional` depth probe sat side by side, unmarked. Its rubric then told it to flag
pairs that ask substantially the same thing across sections and to target the later one — always the
probe — with a one-click `delete_question`.

That is backwards, and the product had already written down why. From
[`f17-progress-under-widening.md`](./f17-progress-under-widening.md) (F17.33): the opening exists to
make a respondent talk broadly, and the planner seats topics **because of what they said**, so the
overlap between the two is the selection criterion, not a coincidence.

Two more dimensions were wrong for the same reason: **Ordering** read phase transitions as sequence
defects, and **Goal-Match** read narrow role-specific probes as off-mission because it could not know
they only run for that role.

The net effect is worse than any single finding: a panel score was **not comparable** between a
topics-enabled and a topics-disabled version of the same instrument. A correctly-built conditional
questionnaire scored worse than a flat one.

Nothing mitigated it. The cross-judge reconciler only fires when ≥2 judges flag one target and can
only emit a rewritten prompt, so a solo Duplicates finding reached the admin unmediated.

## The question this raised, and how it was answered

**Should deliberate overlap be silent, or a reframed finding?** Reframed. Silence loses real
information: a respondent who _is_ seated on the topic genuinely gets asked near-identical things
twice, and `widening-rescan.ts` only mitigates that as a capped gap-fill (`inferred`, 0.45 free text)
that cannot close out a `must_ask` probe at all. So the judge still speaks — at `info`, proposing
`replace_prompt` to sharpen the probe, never `delete_question` — and the scale says outright that it
does not lower the score.

## What shipped

### The overlay — what the judges are given

`VersionStructureInput` gains an optional `routing` block and each question an optional `topicKeys`.
Three shapes are load-bearing:

- **`topicKeys` is an array.** Multi-membership is legal (reported as a `duplicate_membership`
  warning, not prevented), and a question in both a `core` and a `conditional` topic is asked of
  **everyone**. Collapsing to one owner would let the co-occurrence rule _downgrade a real
  duplicate_ — the inverse of the bug being fixed.
- **`phase` and `depth` are `string`, not the enums.** This DTO is persisted verbatim as a run's
  `structureSnapshot`, and `parseStructureSnapshot` degrades the **whole** snapshot to `null` on any
  parse failure, silently switching that run's staleness derivation off. A `z.enum` would turn one
  renamed phase into total loss across every historical run; a string costs one field. The same call
  `FindingTargetView.questionType` already makes.
- **Absence is the flag** — no `routing` block at all when the feature is off, rather than
  `{ enabled: false }`. That is what keeps the prompt byte-identical for the majority of
  questionnaires. An empty `topicKeys` is different and meaningful: routing is on and nothing claims
  this question, so it can never be asked.

Loaded through the version's own `config` and `topics` relations on the `findFirst` that already ran
— not a separate `loadTopics` — because `evaluation-batch-apply` calls `buildEvaluationStructure`
**once per finding**, so a second and third query would land on every finding in a batch. Member keys
that no longer resolve are dropped, so a topic never reads as larger than it asks.

### The rubrics — what they are told to do with it

Three dimensions gain a paragraph, and only when routing is configured.

An earlier draft keyed a rule on every pair of the four phases — a sixteen-cell truth table written
as prose, which a model collapses to whichever rule it read first. What survives is one principle and
the two consequences that are not already the status quo (`core` × `core` needs no words, because
nothing about it changes):

```
CO-OCCURRENCE — routing is on for this questionnaire.
Two questions are only duplicates if the SAME respondent is asked both.
- The opening is deliberately the broad version of what the depth topics probe later…
  Never propose delete_question for it, keep any such finding at "info", and do not let it
  lower your score.
- Two questions in different "asked-when-it-fits" topics may never both be asked. Say so in
  your rationale and drop the severity one level.
- Everything else is a duplicate exactly as it would be without routing.
```

Plus one line on the scale (without it, a judge told to stay quiet still marks down, and the score is
what an admin compares between versions) and one clause on `editGuidance` (narrow rather than delete
inside a conditional topic).

**Attention is bought where it is cheap — in the structure block, not the rubric.** Each question is
annotated in the same plain words the rule uses (`topic=talent/asked-when-it-fits`), so the judge
never holds a translation in mind; a question in no topic says outright that it is never asked; and
the ROUTING frame states the **proportion** as well as the rule, because a judge told "2 of 5
questions are conditional" calibrates severity far better than one handed the rule alone — the same
reasoning behind giving the scope panel's budget judge pre-computed numbers. The per-interview cap is
mentioned only where it can actually bind.

Clarity, Coverage, Type-Fit and Audience-Match are deliberately untouched, with a test pinning that
their prompts are byte-identical with and without routing.

### The review card — what the reviewer is told

`FindingTargetView` gains `routingReach: 'always' | 'conditional' | 'never' | null` and `topicLabel`.

It reports **reach, not phase**. A question can belong to several topics, and if any of them always
runs then so does the question — reporting one topic's phase would label a question everyone is asked
"conditional" and invite exactly the delete this change exists to prevent. `never` is the valuable
third value: an orphan on a routing-on version, free once the target carries `topicKeys`.

Gated on `routing.enabled`, **never** on "the version has topics": `persist.ts` seeds one `core`
topic per section on every ingest, so with the feature off — the default — nearly every version has
full topic coverage, and a presence test would chip every finding card in the product overnight.

On screen it is plain English — "Always asked · Spine", "Asked when it fits · Talent depth", "Never
asked — in no topic". Never `conditional`, never `phase`.

## Tests

`judge-prompt.test.ts` carries the inert-by-construction gate — no `routing` block means no
dimension mentions routing, asserted on the overlay's own markers rather than the bare word "topic"
(the Coverage rubric has always said "name the missing topic" in ordinary English, and always
should). `evaluation-structure.test.ts` covers off/on, the empty-vs-absent `topicKeys` distinction,
multi-membership, and dead member keys. `evaluation-staleness.test.ts` pins that moving a question
between topics does **not** stale a pending finding. `structure-schema.test.ts` covers the caps, an
old snapshot with no overlay, and a phase this build does not know.

## Deliberately not done

- **The design panel does not read hard rules.** Two conditional topics made mutually exclusive by a
  rule cannot co-occur, so their overlap is not a duplicate — but that is the scope panel's
  `criteria_quality` judge's job, and duplicating rule evaluation would put two implementations in
  charge of one question. The reduced-severity treatment is the honest answer instead.
- **Retrying a judge on a pre-F17.34 run stays unaware.** `retry/route.ts` replays
  `run.snapshot ?? buildEvaluationStructure(...)`, so a retry on an old run re-judges without the
  overlay and could still emit `delete_question` on a probe. Accepted rather than special-cased — a
  fresh run is the supported way to get the new judgement — but recorded here so it is discovered on
  purpose rather than in the field.
- **No retrospective re-scoring** of persisted runs. This panel has no `TURN_RUBRIC_VERSION`
  equivalent; old verdicts stay as they were scored.
- **The seeded judge agents' `systemInstructions` are not rewritten.** `018-design-evaluation-judges`
  only re-asserts `kind`/`isSystem` on update, so the changed `duplicates` summary reaches fresh
  installs only. The load-bearing rubric is the prompt builder, which changes immediately.
