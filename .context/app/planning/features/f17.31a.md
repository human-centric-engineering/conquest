# F17.31a — the recorded trigger

The first of the four phases in
[the trigger spec](./f17-mid-interview-triggers.md). Phases b–d — the evaluator that actually fires
a trigger — are a separate piece of work, deliberately: conditional routing from anywhere in the
conversation is a real feature and should be built as one, not shrunk into a metadata change
because that is cheaper.

## What this is for

Three of the ten routing-corpus documents ask for a section to be added on something said **during**
the interview. Scope is settled once, when the opening completes, so the analyst does the only thing
it can: it writes an opening-time approximation and files a gap saying so. R012 (doc 07) shows that
working — five blocks, five gaps, each quoting its own trigger sentence.

But the gap is a paragraph in a list on the analyst's card, and the topic it concerns is a row in a
different list. An admin reviewing the routing reads the topic and sees a tidy conditional section.
**This puts the difference on the topic itself**, and captures the author's intent in a form
something could later run.

## Three decisions worth keeping

**1. Recorded alongside the criteria, never instead of it.** A topic whose only routing lived in a
trigger would be selected by nothing and asked of nobody — strictly worse than today, where it is at
least asked when the condition is obvious from the opening. Behaviour is identical to before this
shipped; the analyst is told to write both, and the schema still requires criteria on a conditional
topic that carries a trigger.

**2. Read-only in the admin UI.** Authoring a trigger by hand buys nothing while nothing fires one.
What the editor MUST do — and is tested for — is not lose it: the Topics tab's save replaces the
whole set from an enumerated payload, so a field the editor forgot would be deleted by an admin
renaming an unrelated topic. Editing arrives with the engine that reads it.

**3. A warning, not an error, and independent of `enabled`.** `trigger_settled_at_opening` describes
the DOCUMENT, not the configuration. Nothing is misconfigured and no edit clears it, so an error
would be a permanent red mark on a correct setup. It is also **mutually exclusive** with
`trigger_on_always_topic`: on an always-run topic the settled-at-opening message is not merely
redundant but false — it says the topic is included only when the condition is clear by the end of
the opening, and an always-run topic is included for everyone regardless.

**The carriage list above is the whole feature.** `toProposedSet` is the only projection from the
validated analyst result to a persisted draft, and `ProposedTopic.trigger` is optional, so omitting
the field there costs no type error and silently discards it one line after the schema accepted it —
no card, no accepted topic, no column, none of the three warnings. It was missing on the first cut
and nothing but an end-to-end read caught it; `routing-analysis.test.ts` now pins it.

## The cue voice, found and fixed by running it

The first live run filled all five of doc 07's triggered blocks — and every cue was lifted straight
from the instruction: `"someone they live with"`, `"have lived with"`, `"tenancy block has already
been completed"`. Faithful to the document, and not one of them a phrase a person says while
answering a question.

Harmless while nothing reads them, and fatal later: cue quality is the whole of an eventual gate's
recall. So the prompt now splits the job — the instruction's own words go to `condition` and
`sourceQuote`, and `cues` asks for **what the respondent would say**, taught with a deliberately
unrelated worked example (a dietary restriction) so the corpus' own documents are not handed their
answers.

Re-measured on doc 07 the same day, same build otherwise:

| Block          | Before                                                            | After                                                        |
| -------------- | ----------------------------------------------------------------- | ------------------------------------------------------------ |
| Domestic abuse | "experiencing abuse", "someone they live with", "have lived with" | "he hits me", "I'm scared", "I fled home", "my ex abused me" |
| Care leaver    | "looked after", "local authority"                                 | "I was in care", "foster care", "children's home"            |
| Rent arrears   | "arrears", "tenancy block has already been completed"             | "behind on rent", "owe my landlord", "missed rent"           |

Same five triggers, same six gaps, same 36 questions — only the cues moved. The rubric is pinned by
tests so it cannot drift back, including the one asserting the worked example stays out of any
domain the corpus measures.

**The residual, recorded rather than fixed:** several cues are whole utterances (`"he hits me"`),
which carry a pronoun and a word order that a respondent saying "my partner hits me" would not
match. The distinctive fragment (`"hits me"`) is what a matcher needs. Filed in the spec's risk
table for whoever builds the evaluator — it costs nothing until something reads these.

## What this does not do

- Fire a trigger. Scope is still settled once, at the end of the opening.
- Change the analyst's gaps. Timing, termination and mutual exclusivity are all still reported.
- Touch the questionnaire pack export. The pack is client-facing, and printing "added whenever this
  comes up" in a branded document would claim behaviour the product does not have.

## The scoring question it does NOT settle

**T15** in the routing corpus ledger stays open. The corpus ground truth says a triggered block
belongs in `gaps[]` _because the product cannot express it_ — when it can, the right answer changes.
Recording the intent is not expressing it, so nothing about the ground truth moves here. That
decision belongs with the phase that ships the evaluator.
